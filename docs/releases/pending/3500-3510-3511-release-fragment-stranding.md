# Release-fragment pipeline stranding repaired: materialized v7.199.2/v7.200.1, alarm wiring, consumption-aware pins

## What changed

- **#3500** — Separator-aware provenance: published-block reconstruction now segments the separator-split parts completely (a fragment whose own content contains internal blank-line `---` horizontal rules spans multiple consecutive parts), enumerating every ambiguous segment as an alternative branch (never pruning it — a duplicate-content fragment previously admitted a wrong unique attribution), with ambiguity, parts, and work caps all failing closed and per-entry normalization memoized. Archived-claim resolution: a candidate PR's fragment already consumed by an earlier materialization resolves as a claim-only entry validated against the merged manifest by digest, with latest consumption winning when a fragment was consumed, re-added with different bytes, and consumed again (normal history — the live corpus carries 32 such double-claimed paths), instead of an ambiguity throw that would strand any release referencing one. DELETED pending-fragment entries in a candidate PR's file list are excluded from collection before claim resolution. Malformed manifests are a fail-closed throw, not a silent skip. Empty published bodies materialize as zero-consumption and cannot strand on claim-resolution failures (the previously stranded **v7.199.2 and v7.200.1 releases are materialized** in-repo, `releaseBodySha256` verified equal to the live GitHub bodies), and five byte-matched consumed fragments were deleted from `docs/releases/pending/` (including the separator-poisoned `transient-retry-subprocess-hardening.md` and `git-status-async-diagnosable.md`). A published block that references an already-archived fragment fails closed on BOTH the tagged-release path and the live update-release path (the live path previously rewrote the block silently without the archived sections) — duplicate-consumption hazard, with the archived paths named in the error.
- **#3510** — `release-health-summary` now needs `update-release-notes` and alarms when it fails; a skipped cleanup no longer reads as success, so a stranding release fails visibly the same day instead of surfacing in closeout archaeology. The healthy-path summary line now reports all three conclusions (`release-please`, `update-release-notes`, `cleanup-release-fragments`).
- **#3511** — Five suites (`ensemble-adr-2505`, `cross-surface-contract`, `ci-2552-fragments-closed-state`, `qa-gate-bootstrap-protocol`, `swarm-pr-review-runtime-friction-guidance`) resolve their pending-fragment pins consumption-aware (pending is the sole authority while present; once consumed, the obligation resolves through the fragment's manifest claim — the claiming tag's materialized body — never a name-blind aggregate of every release body), with fail-closed strength legs including claim-without-body and pending+claim coexistence. The ci-2552 negative claims-scan applies to pending text only — the consumed-state obligation is the positive citation pin.

## Why

Two published releases (v7.199.2, v7.200.1) had zero in-repo release history and both cleanup runs died in `update-release-notes` with `incomplete release provenance`; the designated alarm stayed green on both. Five suites would have stranded the NEXT materialization the same way PR #3496 was stranded for two days.
