# `fix(tools)`: pre_check_batch re-issues its Stage A receipt from inside the tool — nested Code Mode gate calls can no longer silently wedge Stage A

## Summary

- OpenCode 2.3.1/2.3.2 stopped dispatching plugin `tool.execute.before`/`tool.execute.after` hooks for tool calls invoked **nested inside a Code Mode `execute` program** (upstream regression: anomalyco/opencode#65742; verified 2.3.0 → 2.3.2 on the same machine — durable hook events for nested `pre_check_batch` calls stop exactly at the first 2.3.2 start). The guardrails hook chain was the plugin's only Stage A receipt producer, so every gate run an agent made through `execute` — the common architect pattern — completed green while the Stage A workflow attribution silently never fired: no task correlation, no `stage_a_passed` transition, no route event, no advisory. The wedge surfaced only much later at the Stage B dispatch (`TASK_WORKFLOW_STAGE_A_REQUIRED`), and every advertised remediation (`/swarm recover`, `recover_stage_a_task`) refused too because the background-dispatched coder settlement never landed — the observed session-wedging loop.
- Fix: `pre_check_batch` now re-issues the same receipt **from inside the tool** (`src/tools/stage-a-self-report.ts`), where the code always runs regardless of hook dispatch. It mirrors the guardrails attribution chain (session `currentTaskId`, then the durable COMMITTED-settlement fallback), records the `stage_a_passed`/`stage_a_failed` transition and the bounded route event, and pushes the two communication advisories:
  - unattributed **pass** → `STAGE A RECEIPT NOT ATTRIBUTED` (what was NOT recorded, why Stage B will be denied, and the terminal remediation — `/swarm recover <task>` when a background coder round's settlement is stale, a real coder mutation otherwise);
  - attributed pass over a task with **no accepted coder mutation** (the idle-after-repair + unsettled-background-settlement shape) → `STAGE A WRITE FAILED (TASK_WORKFLOW_CODER_MUTATION_REQUIRED)` with the same recover-first remediation — the exact failure whose only previous signal was a much later, non-terminating denial.
- Idempotent with the hook path for hosts where hooks still fire: a duplicate guard records `duplicate_result` when a `pre-check*` Stage A pass already exists for the generation, and the reducer's `stage_a_passed` from `pre_check_passed` arm is a no-op, so a hook/tool race is harmless. Gated on a real session context (`ctx.sessionID`, always present in host invocations) so context-free consumers and tests see no durable side effects. Fail-open by contract: the self-report can never break or alter a gate run.

## User-facing changes

- After an OpenCode 2.3.1/2.3.2 restart, agents invoking `pre_check_batch` through Code Mode get real Stage A workflow attribution again: green gate runs advance the task (`stage_a_passed`), failing runs record `stage_a_failed`, and when the receipt cannot land, the same turn carries a visible advisory naming the cause and the working remediation — instead of a silent drop that wedges the session a dozen tool calls later.
- The hook-side (non-nested) path is unchanged in behavior; its unattributed-pass advisory text now carries the same `/swarm recover` remediation for stale background settlements.

## Migration notes

None. No on-disk format changes; the self-report uses the existing workflow transitions (new `transitionId` prefix `pre-check-tool:`), the existing closed route vocabulary, and the existing bounded advisory queue.

## Discovery context

Found in the Wirtschaftssimulation loop (sessions `007e6133…` and `9b8ce452…`, task 1.13): after the OpenCode auto-update to 2.3.2 (first 2.3.2 start 2026-11-22T21:18Z), the architect's `execute`-nested `pre_check_batch` runs (22:11Z onward) produced zero `stage_a_gate_route` events where identical runs had produced them until 19:56Z under 2.3.0; the retry-circuit repair and a real background coder settlement round both completed, yet the workflow stayed `idle`/gen 1 with the settlement WAL `ABORTED` ("ownership transferred to durable background completion"), leaving Stage A unattributable and Stage B blocked. Live-verified on 2.3.2: a nested `tools.pre_check_batch(...)` call succeeds without any hook dispatch. Pinned by `tests/unit/tools/stage-a-self-report.test.ts` (attributed pass, unattributed-pass advisory, mutation-required advisory with the recover remediation, hook-path duplicate idempotency, fail verdict, invalid-result silence) and the hook-side advisory tests in `tests/unit/hooks/guardrails-stage-a-route-events.test.ts`.
