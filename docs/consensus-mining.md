# Consensus mining

The consensus miner reads evidence that already exists under `.swarm/` and reports what several independent runs agree on. It is a **proposals-only boundary**: it activates no skill, writes no knowledge entry, promotes nothing, edits no project file, and mutates none of the evidence it reads. Every recommendation it produces is a suggestion a human or a separately-gated workflow may act on; nothing downstream is triggered by mining.

Two artifacts are written. `src/consensus/` itself writes exactly one — the immutable report under `.swarm/evolution/consensus/` (plus retention deletions of its own prior reports). The `consensus_mine` tool additionally records the run's proposals in the shared recommendation dedup ledger, so a recommendation the miner already made is not re-proposed by the curator sweep or the skill improver. Two details about that ledger are easy to get wrong. First, a proposal whose recommendation text is already in the ledger gets **no** entry and is counted as `cross_producer_duplicate_count` instead — and the ledger key deliberately drops the producing mechanism, so that count is *not* a count of other producers (see [Reading `cross_producer_duplicate_count`](#reading-cross_producer_duplicate_count)). Second, the ledger's root is `resolveKnowledgeStoreDir`, so it normally sits at `.swarm/learning/recommendation-ledger.jsonl` but lands in the shared cohort root when a knowledge-link pointer is configured.

Both writes create their containing directory and take a lock, but **not in the same place**. The report goes through `withEvidenceLock`, whose sentinel is under this project's `.swarm/locks/`. The ledger goes through `transactFile`, which locks the ledger file's own containing directory — producing `<resolveKnowledgeStoreDir(directory)>/learning.lock`, which under a knowledge link is not in this project's `.swarm/` at all.

## Corpus

`src/consensus/corpus.ts` normalizes eight existing sources into one flat stream of `CorpusObservation` records — `{ runId, taskId?, taskCategory?, agentRole?, modelId?, seed?, success, signals[], evidenceRef }`. It adds no new store: evaluation runs come from `readEvaluationRun`, gate audits from `listGateAuditResults` (which already returns each run's cells, so the corpus never needs `readGateAuditResult`), gate ground truth from `readGateGroundTruth`, per-task trajectories from `listEvidenceTaskIds` + `readTaskTrajectory`, PRM session trajectories from `readTrajectory`, skill compliance from `readSkillUsageEntries`, knowledge outcomes from `readKnowledge` + `computeOutcomeSignal`, and retrospectives from `loadEvidence`. Only two read-only enumerators are new — `listEvaluationRunIds` over `.swarm/evolution/runs` and `listTrajectorySessions` over `.swarm/trajectories` — because the underlying stores read one artifact at a time and never needed a listing of their own.

Evaluation runs are the only source carrying task category, model id, and seed together; every other source supplies a subset, and a field that a source cannot attribute stays absent rather than being defaulted.

`runId` is the *support unit*, and it is namespaced — but by **trial identity, not by source**. Eight sources share six namespaces, and both overlaps are deliberate: per-task trajectories and per-task evidence bundles are two views of the same trial and share `task:<id>`, while gate audits and gate ground truth describe the same audit run and share `gate-audit:<runId>`. Counting either pair separately would double the apparent agreement. The remaining four (`evaluation-run:`, `prm-session:`, `skill-usage:`, `knowledge:`) are one namespace each.

Every loader takes an injected `directory`; there is no `process.cwd()` fallback anywhere in the subsystem (AGENTS.md invariant 4). Prompts and reasoning traces are never read into an observation at all — only outcomes, verdicts, categories, and bounded excerpts. Every free-text fragment that survives into a signal, statement, or evidence reference passes through `redactSecrets` **before** the `consensus.max_excerpt_chars` length bound, so a secret straddling the truncation point is replaced rather than half-copied. A source that throws is recorded in `unreadableSources` and the rest of the corpus still loads; a partial corpus that says so is better than a silently empty one.

### The corpus path writes nothing to disk — deliberately

Nothing in the corpus path creates or modifies a file, a lock, or a marker. That is a chosen property, not a free consequence of "only reading". `loadEvidence` (`src/evidence/manager.ts`) performs a **lazy in-place upgrade** of a legacy flat retrospective by default: it rewrites `.swarm/evidence/<taskId>/evidence.json` into bundle form under an `evidence-loader` lock, creating a lock sentinel under `.swarm/locks/`, and remaps legacy `task_complexity` values (`medium` → `moderate`) on the way through. A mining run that did that would be mutating the very evidence it claims only to count. `defaultReaders` therefore binds it as `loadEvidence(directory, taskId, { migrate: false })`, which returns the same wrapped bundle to the caller and skips the write entirely. `LoadEvidenceOptions.migrate` defaults to `true`, so every pre-existing caller keeps its historical behaviour.

Three upstream readers do populate **process-local** caches, which is worth stating rather than hiding behind the phrase "read-only": `readTrajectory` fills the PRM in-memory trajectory cache (`src/prm/trajectory-store.ts`, FIFO, `MAX_TRACKED_TRAJECTORY_SESSIONS` = 500 **sessions**), while `readKnowledge` and `loadEvidence` fill two **separate** maps in `src/utils/swarm-artifact-cache.ts` — the parsed-artifact cache and the text cache, each independently FIFO-bounded at `MAX_CACHE_ENTRIES` = 128 entries, so the module holds up to 256 entries in total. None of these caches is on disk — nothing about them writes a file and none survives the process — but they are not inert either. (The readers themselves obviously do read files; the read-only claim in this section is that nothing here **writes**, not that nothing here opens a file. The artifact cache in particular `stat`s the file on every lookup to check freshness, and on a miss invokes the caller's read function and `stat`s again before storing the result.)

Two in-memory effects are worth knowing before you mine a large tree while sessions are running. Because all three caches evict, mining **can** evict entries another subsystem was relying on and change what that subsystem next observes in memory. And the PRM trajectory cache is a plain `Map` with no revalidation: `readTrajectory` **replaces** the cached list for every session it reads, re-bounded by its own `maxLines` default rather than by whatever bound the live writer was using — a session whose list exceeds 1000 entries is cut to the newest `floor(maxLines / 2)` = 500 **entries of that one session**, which is a different 500 from the 500-session cap above; the two constants merely share a value. Nothing on disk changes; what a concurrently-running session next reads out of that cache can.

`migrate: false` skips only the *persistence*. The bundle handed to the corpus is still the wrapped, normalized view, including the `task_complexity` remap, which happens before the write branch. So the corpus reads normalized values while the file on disk keeps its legacy ones — which is the correct split for a read-only consumer.

### Truncation does not systematically favour successes — but it is still a cut

The whole corpus is capped at `maxEvidenceItems` against a fixed source order and a deterministic per-source sort, so the same tree always yields the same truncated corpus.

Within a source, when the cap binds, the retained slice **alternates between failing and succeeding observations** rather than taking a lexicographic prefix. Evidence refs are structured (`gate-audit:<runId>:<taskId>:<index>`), so a prefix cut correlates with run and task identity — and therefore, whenever failures cluster in one run or one task, with outcome. The effect of that was exactly backwards: failing observations vanished while succeeding ones survived. Failures are now taken first within each pair, so an odd budget rounds toward negative evidence; a source with no failures still fills its whole budget; and the retained subset is re-sorted on the way out, so ordering and determinism are unchanged.

**What this does and does not buy, precisely.** The balancing removes the *systematic* bias — truncation no longer prefers successes as a rule. It does **not** guarantee that a given attribute keeps its counterexamples, for two reasons worth knowing before you read a truncated report:

1. The balance is struck **per source**, not per signal. A source's failures may all belong to signals other than the one you are looking at, so a particular attribute can still lose every counterexample while its successes survive — and because `confidence` rises with the successful-run ratio, that attribute's confidence goes **up**.
2. Once the budget is spent, every remaining source in the fixed order is dropped **wholesale**, with no balancing at all. With the default `max_evidence_items` of 50 spread over eight sources this is the normal case, not an edge case: later sources (`skill-usage`, `knowledge`, `evidence-bundle`) frequently contribute nothing.

This is why `truncation.corpus` is persisted on the report. A truncated report is a **partial view and says so**; read `failureSupport: 0` on one as "no failing run survived the cut", not as "nothing failed". Raise `max_evidence_items`, or narrow the request with `run_ids` / `task_categories`, when you need a conclusion the cut cannot have shaped.

Narrowing helps because the request's filters are applied **inside** the corpus loader, per source, before the budget is spent — `mineConsensus` hands its filter predicate to `loadConsensusCorpus` as `LoadCorpusOptions.filter`. Until that wiring existed the order was the other way round: the cap ran first and the filters ran second, so narrowing to the one category that mattered removed observations from an already-capped corpus and could take 50 observations to 0. The filters run *after* each source's `corpusHashes` entry is computed, so a hash still fingerprints what the source contained rather than what one request asked for; `truncation.observations` is what declares how many were actually tallied.

## Thresholds and diversity

Support is **distinct runs**, never observations: one chatty run emitting the same signal fifty times contributes exactly one. `successSupport` and `failureSupport` are likewise distinct-run counts, and a single run may appear in both when it carries the signal on a succeeding and a failing observation — they do not have to sum to `support`.

An attribute is emitted when `support >= minSupport` and `successSupport >= minSuccessfulRuns`, defaulting to `consensus.default_min_support` and `consensus.default_min_successful_runs`. It becomes **proposal-eligible** only when it additionally clears `taskDiversity >= 2` and draws support from more than one run. `taskDiversity` counts distinct task identities (`taskId`, else `taskCategory`) among the contributing observations. Below that bar the attribute is still emitted, with `proposedTarget: 'none'`, as an **investigation note**: one anecdote can only create an investigation note, and suppressing it entirely would hide the evidence a human needs in order to go looking for a second task. Knowledge-derived attributes carry no task attribution and therefore surface as investigation notes by construction.

`modelDiversity` counts distinct model ids among the contributing observations and is **0 when no contributing observation carries a model id at all** — the normal case for trajectory-, usage-, and knowledge-derived attributes. Zero means *"not measurable from this corpus"*, **not** *"measured as none"*, and it never gates emission or proposal eligibility on its own. Reading a zero as evidence of single-model agreement is the misinterpretation this rule exists to prevent.

Negative evidence can never be silently dropped. `failureSupport` and `counterexampleRefs` are populated on every attribute that has failing runs, and `ConsensusAttributeV1Schema` **rejects** an attribute that declares failing support while carrying no counterexample references. Failing runs also lower `confidence`, which is a deterministic function of support saturation, the successful-run ratio, and a halving while below the diversity gate.

The schema rule is the part that is absolute: **whatever survives into an attribute, a non-zero `failureSupport` always ships counterexample references.** What is *not* absolute is which observations reach the attribute in the first place — `counterexampleRefs` (like `evidenceRefs`) lists at most `MAX_CONSENSUS_REFS` = 200 entries per attribute, and the corpus cap can drop failing observations, including all of a given signal's (see the truncation section above). Truncation is no longer *biased* toward doing so, but it can still do so, and the report declares that it was truncated so the reader can tell.

## Proposals

A proposal-eligible attribute produces at most one `ProposedSkillChange` — none when its fingerprint was already proposed by an earlier report — carrying `sourceAttributeId` — the id of the attribute whose arithmetic produced it. That back-reference is what makes a report auditable: a reader can point at the exact attribute behind any recommendation, and `ConsensusReportV1Schema` rejects a proposal naming an attribute that is not in the report, or naming one that is an investigation note. (The note guard used to compare `provenance.sourceEvidenceRefs` — corpus refs like `evaluation-run:r1:t1:0` — against the set of attribute ids `cattr_<16hex>`. Those namespaces are disjoint, so the check could never fire on real miner output.)

Provenance is **scoped to the observations that actually fed the attribute** (AC23): `sourceRunIds`, `sourceModelIds`, `sourceTaskIds`, and the `validationSelector` all come from that attribute's own tally, never from the whole filtered corpus. Computing them once corpus-wide and stamping them onto every proposal made each proposal claim provenance it did not have and made every proposal in a report indistinguishable — and a validation run driven off such a selector would measure the wrong slice. The selector prefers task categories, then task ids, then run ids, falling through to the next key whenever the current one can name nothing. It never truncates an identifier: an entry is dropped **whole** — and the omission declared as `;omitted=<n>` — either because it would push the selector past its 1024-character bound or because the identifier itself exceeds a 256-character per-entry cap. A mid-identifier truncation would designate a slice that does not exist, and an all-dropped key would designate the empty one; if every key is unrenderable the selector falls back to `attributeId=<id>`, which always names exactly the finding the proposal came from.

The fingerprint is computed from the deterministic `statement`, so a model rewording the same finding cannot mint a new one and defeat deduplication.

## Optional LLM restatement

All deterministic work — filtering, counting, gating, negative-evidence retention, proposal construction, and fingerprinting — completes **before** any model is consulted. Summarization, controlled by `consensus.llm_summarization_enabled` (default `true`) and bounded by `consensus.llm_timeout_ms`, runs last through an injected dispatcher with a fixed budget of 20 calls per report.

It **adds** `llmSummary`; it never replaces `statement`. The deterministic rendering stays authoritative and stays hashed, and `llmSummary` is excluded from `integrityHash` — see the next section for why that is load-bearing rather than tidy. Summarization cannot change a count, a gate outcome, a target, a confidence, or a fingerprint. When no dispatcher is wired, the config disables it, the call times out, the dispatcher throws, or the response is rejected, the attribute simply carries no `llmSummary` — graceful degradation, never a hard dependency. The tool reports three counters. `summarized_count` is derived from the **persisted report** — how many stored attributes carry an `llmSummary`. `summarized_but_not_shown` is how many of those sit outside the inline `attributes` echo. It is zero on any report with 25 attributes or fewer, and can rise to the full `summarized_count` above that: restatements go to the highest-confidence attributes while the echo is the first 25 in canonical signal order, so with confidence inverted against signal order a report legitimately prints `summarized_count: 20` with **zero** `llm_summary` values visible. Read that as "they are in the report file", not as a contradiction. `restatements_accepted_this_run` is what *this* invocation's dispatches produced. They differ when an immutable re-mine returns the already-stored artifact: because `llmSummary` is outside the integrity hash, a differing restatement is not a conflict, so the stored text wins and this run's restatements are discarded. `summarization_skipped_reason` (`no_attributes`, `disabled_by_config`, or `no_dispatcher`) is added only when summarization never ran at all — a dispatch that ran but produced nothing usable (a timeout, a throw, or a response the guard rejected) shows `restatements_accepted_this_run: 0` with no skip reason, because the pass did run.

### What model prose can reach disk

AC18 requires that a chain of thought is not persisted. No system prompt can deliver that: asking a model for one sentence is a request it is free to ignore, and the excerpt sanitizer only redacts secrets, collapses control and format characters, and truncates — none of which removes reasoning. What the miner delivers instead is a **whitelist** that bounds what model output can reach disk at all. Read the bullets as the bound they are, then read [the property, stated exactly](#the-property-stated-exactly) for what that bound does and does not amount to.

- The response must contain a line matching `FINDING: <sentence>`. Only the captured group is ever considered; everything else in the response — preamble, reasoning blocks, bullet lists, trailing commentary — is discarded, and the first such line wins. The split recognises every mandatory line break, not just `\n`: `\r`, `\v`, `\f`, U+0085 (NEL, which JavaScript's `\s` does not match), U+2028, and U+2029 all end a line, so none of them can smuggle a second line into the captured group.
- The extracted sentence is rejected if it contains bracket markup — an angle bracket, a square bracket, a brace, or a CJK bracket (`<think>`, `[think]`, `{think}`, `【think】`). The envelope is *line-scoped*, so `FINDING: <think>…</think> Scoring succeeded.` would otherwise carry the scratchpad along inside the capture. Rejecting markup wholesale beats stripping tags: a restatement of a statistical finding has no legitimate need for it, and rejection costs only the paraphrase. The sanitizer's own `[REDACTED:<type>]` placeholders are masked before this test, since they are the miner's output rather than the model's — which is safe only because a placeholder the *model* wrote is rejected first (next bullet).
- It is rejected if it carries a `[REDACTED:<type>]` marker of its own. Only the sanitizer may introduce one, and it has not run at that point — so a marker in the raw capture is forged, and would both assert a redaction the miner never performed and slip past the bracket test, which masks the miner's own placeholders.
- The extracted sentence is rejected if it carries reasoning markers (`reasoning`, `rationale`, `chain-of-thought`, `analysis`, `step-by-step`, first-person planning, and similar).
- It is rejected if, **after masking**, it carries a sentence terminator anywhere but in a single trailing run. The terminator class is not ASCII-only: it is Unicode's `Sentence_Terminal` property — `.`, `!`, `?`, `‼`, `⁇`, `⁈`, `⁉`, the CJK and fullwidth stops including halfwidth `｡`, Arabic and Urdu, Devanagari danda and double danda, Armenian, Ethiopic, Khmer, Myanmar, Mongolian and the small/vertical presentation forms — plus a hand-added ellipsis and leader family (`…`, `‥`, `⋯` and the two vertical forms) that Unicode classifies as neither sentence terminators nor terminal punctuation, even though `runs…then i count` is a shape models actually emit. `[.!?]` treated every non-ASCII one of these as an ordinary character, and several were observed chaining clauses past the old bound. **Clause-level marks are not counted** — see [the property, stated exactly](#the-property-stated-exactly) for why that is a decision rather than an oversight.
  Two constructs are masked before the count: decimal points, and **at most one** `e.g.` / `i.e.` / `etc.` that is followed by a lower-case word (optionally after a comma). Both halves of that abbreviation rule are load-bearing — masking the token unconditionally erases a real boundary (`… etc. The tallies were compared.`), and allowing an unbounded number of masked abbreviations lets a chain of them (`… the signal etc. then i count … etc. then i divide …`) reassemble multi-clause narration. Because masking removes those periods only for the *count*, the persisted text can still contain several: `Scoring succeeded on 0.8 of the runs, e.g. the refactor pair.` is admitted and holds four — the decimal point, the two inside `e.g.`, and the trailing one. Three are masked, which is what leaves the single trailing run the rule permits.
- It is rejected if it exceeds `MAX_CONSENSUS_STATEMENT_CHARS` (600) **without being truncated to fit**. Clipping model output to a length bound is precisely how a trailing fragment of reasoning survives one, so the guard refuses instead of trimming.

Every rejection is silent and non-fatal: the deterministic statement stands. Whatever survives is still redacted, and its control and format characters are collapsed, like any other excerpt.

That whitelist rejects a great deal of legitimate prose, and deliberately so. A token carrying a period with more characters after it *inside the token* — a file path (`src/consensus/miner.ts`), a URL (`https://example.com/report`), an initialism (`U.S.`) — is rejected wherever it appears, including at the very end of the restatement. A token whose only period is its last character — `Dr.`, an unmasked `etc.`, `...`, `…` — is rejected only when more text follows it; standing at the end it *is* the single trailing run the rule allows, and is admitted. The abbreviation exemption is narrow in the same way: it needs a lower-case continuation, so `Runs using e.g. 3 different models scored higher` and `Runs using e.g. Claude and GPT scored higher` are both rejected, as is any restatement using two *lower-case-continued* abbreviations. A second abbreviation standing at the very end is not masked and simply becomes the permitted trailing run, so `Scoring succeeded e.g. the refactor pair etc.` is admitted. Rejection costs a paraphrase; a missed terminator costs the bound.

#### The property, stated exactly

**What is enforced.** Per attribute, per mining run: at most one `FINDING:` line from one dispatch is considered, everything else in that response is discarded, and the surviving text is length-bounded, markup-free, forged-marker-free, reasoning-marker-free, and — once decimal points and at most one lower-case-continued abbreviation are masked — carries no sentence terminator except a single trailing run. Read that masking clause literally: the bound counts *unmasked terminators*, not periods, so admitted text may hold several `.` characters. It lands in `llmSummary`, which is excluded from the integrity hash and never displaces `statement`. A report carries at most `MAX_LLM_SUMMARIES` = 20 of them, one per attribute.

**What is not enforced, plainly.** *A single grammatical sentence chained with commas, semicolons, colons, dashes, tabs, or the one permitted abbreviation can still read as a multi-step narration, and this guard does not stop that.* `first i list the runs; then i count the passes; then i divide` carries no terminator to count, so it is one sentence by every rule above, and it is admitted. So is the comma version, so is `first i list the runs etc. then i count the passes` (two clauses, one masked boundary — bounding the exemption at one stops the *chain*, not the single join), and so is `first i enumerate the runs། then i count`, because the Tibetan shad U+0F0D is `Terminal_Punctuation` and not `Sentence_Terminal`. `miner-restatement-guard.test.ts` pins every one of those as admitted, so the limitation cannot be quietly claimed away again.

That last case is the honest shape of the whole limitation. Unicode files clause-final marks under `Terminal_Punctuation`, a set of 121 characters the terminator class does not include — and that set contains **the comma**. Since a restatement containing a comma has to stay admitted, the clause-chaining channel stays open no matter where a line is drawn among the other 120; adding the shad would close no channel the comma does not already leave open, and `-` and `—` are in neither property, so a dash chain walks through regardless. Earlier revisions of this document claimed the guard kept a reasoning *trace* off disk — first via a boundary detector, then via a terminator count. Both claims were false for exactly this reason, and no refinement of terminator rules will make either true. The reasoning-marker list is a second line of defence against the common shapes, not a classifier: it is pattern coverage, and pattern coverage is not a guarantee. What *is* structural is the bound — one envelope line, one unmasked terminator run, 600 characters, in a hash-excluded field beside an authoritative deterministic statement.

## Reports, integrity, and retention

`ConsensusReportV1` records `reportId`, `generatedAt`, the `request`, `inputIds`, per-source `corpusHashes`, `configHash`, `integrityHash`, `attributes[]`, `proposals[]`, `truncation`, and `redactionPolicyVersion`. Reports live at `.swarm/evolution/consensus/<reportId>.json` and are written through the shared `writeImmutableArtifact` pipeline (`src/evidence/immutable-store.ts`) that the evaluation store also binds, supplying only their own lock actor, canonical serializer, and conflict-error type.

The integrity hash covers the whole report except:

- `integrityHash` itself and `reportId` (which is *derived* from the hash, so including it would be circular);
- `generatedAt`, and each proposal's entire `provenance.writeOrigin` — the `producedAt` clock plus the `sessionId` / `agentRole` identifying whoever ran the mine (the shared write-origin schema also allows an `agentId`; the consensus path never populates it, and excluding the whole object covers it either way);
- each attribute's `llmSummary`.

The first bullet is *circular* — a hash cannot cover itself, and `reportId` is derived from it. The second is *who and when*, not *what*. Excluding the identity fields is not cosmetic: `sessionId` comes from `ctx.sessionID`, so while only `producedAt` was excluded, two sessions mining a byte-identical corpus produced different `reportId`s — the same symptom as hashing the model's wording, from a different field. The third exclusion is not a nicety either: `llm_summarization_enabled` defaults to `true`, so while a model's wording sat in `statement` it sat in hashed content, and two mining runs over a byte-identical corpus produced **different** `integrityHash` values and therefore different `reportId`s. That defeats content addressing, defeats the store's `isEquivalent` check, and turns every re-mine into a new artifact. The deterministic `statement` that the summary paraphrases *is* hashed, so nothing about the finding escapes coverage — only the paraphrase does.

The hash is computed subtractively, so a field added to the contract later is covered automatically. It is verified before persist and again on read: a report whose declared hash does not match its content is refused rather than written, and on-disk tampering is caught rather than trusted. The trade-off of excluding `llmSummary` is stated plainly: editing a stored `llmSummary` is *not* detected as tampering, because it is not content. Every field that carries a finding — `statement`, all the counts, the refs, the proposals, the truncation record — is protected. A divergent payload written to an existing report id is rejected with `ConsensusConflictError`; a payload differing only in timestamps or in `llmSummary` is recognized as the same artifact, and the stored one wins.

### What "reproducible" does and does not mean

The property is: **identical hashed inputs ⇒ identical `integrityHash` and `reportId`.** There are five hashed inputs: the corpus, the `request`, the `configHash`, the set of already-proposed fingerprints, and `redactionPolicyVersion` (a coarse fingerprint of the redaction contract — the salt plus the secret-pattern family count — so a report produced after the redaction rules change is a different artifact). In particular, *who* ran the mine is not an input: each proposal's `provenance.writeOrigin` (`sessionId`, `agentRole`, `producedAt` — plus the `agentId` the shared schema allows and this path never sets) is recorded on the artifact but excluded from the hash, so two sessions mining an identical corpus produce the same report rather than two competing ones.

Of the five, two surprise people:

- **`configHash` covers the whole `consensus` config block**, including knobs that have nothing to do with a finding. Flipping `report_retention` from 50 to 7, or toggling `llm_summarization_enabled`, changes `configHash` and therefore the report id — even over a byte-identical corpus. That is deliberate: a report declares the configuration it was produced under, and two reports produced under different settings are different artifacts. It does mean "same corpus ⇒ same id" is only true at a fixed config.
- **Re-mining an unchanged corpus is not a no-op**, because the second run dedupes its proposals against the fingerprints the first run stored. It legitimately produces different content — zero proposals — and is written as a second report recording that nothing new was found. Once proposals are exhausted the content stops changing and further runs converge on one stable report id.

What is genuinely invisible to the report's identity is the *model*: whether a dispatch succeeded and what wording it returned cannot move the hash, because `llmSummary` is excluded. (Whether summarization was *enabled* can, via `configHash`.)

### Producer-side bounds

`attributes` and `proposals` are capped at 1000 by the schema, and the miner enforces the attribute cap itself before parsing. A schema-only bound would turn a large `max_evidence_items` (the tool accepts up to 10 000) into a `parse` throw at the very end of mining, so **no report would be written at all** — the caller would lose every finding rather than the weakest tail. When the cap binds, survivors are the strongest by confidence, then support, then id — not the alphabetically first — and the retained set is restored to canonical signal order. There is no separate proposal cap: the miner emits at most one proposal per attribute and deduplication only removes, so `proposals.length <= attributes.length <= 1000` holds structurally.

### Declared truncation

The persisted `truncation` block records `corpus` (whether `maxEvidenceItems` cut the corpus), `observations` (how many were actually tallied), `inputIds` and `totalInputIds` (whether the run-id list was cut at 200, and its pre-cut size), and `attributesDropped`. It is hashed like any other content, because a report that dropped evidence is not the same artifact as one that did not. Without it, a stored report is indistinguishable from a complete one, and `failureSupport: 0` cannot be read as either "nothing failed" or "the failures were truncated away".

Four bounds are *not* counted in that block, and are worth knowing when reading a very large corpus:

- the per-attribute `MAX_CONSENSUS_REFS` = 200 cap on `evidenceRefs` and `counterexampleRefs`;
- `MAX_REFS_PER_CLASS` = 50 in `src/learning/provenance.ts`, which caps each `provenance.source*` list — so a proposal drawn from 120 runs lists 50 of them, while `validationSelector` on the same proposal *does* declare its own omissions;
- `MAX_ENUMERATED_ENTRIES` = 2000, bounding how many evaluation runs and PRM sessions are enumerated per source;
- `unreadableSources`, which is returned to the caller but not persisted — a source that threw shows up on the stored report only as a missing `corpusHashes` entry.

`consensus.report_retention` bounds how many reports are kept. Pruning keeps the newest N by `generatedAt`, is a total order (ties broken by id), never deletes a corrupt report — an unparseable artifact is data-quality evidence — and treats a configured `0` as *retention disabled* rather than *delete everything*, so it can never remove the report just written.

## Tool surface

`consensus_mine` (`src/tools/consensus-mine.ts`) is the entry point, available to `architect`, `curator_phase`, and `curator_postmortem`. It accepts optional `run_ids`, `task_categories`, `agent_roles`, and `model_ids` filters plus `min_support`, `min_successful_runs`, and `max_evidence_items` overrides, all defaulting from the `consensus` config block. When `consensus.enabled` is false it returns a disabled result and writes nothing. Because its only write targets are its own report and the shared dedup ledger — never a project file — it is classified as a pathless write-like tool in `src/full-auto/policy.ts` alongside `write_retro` and `knowledge_add`, and it is denied in read-only dispatch lanes. It is deliberately absent from `WRITE_TOOL_NAMES`, whose members are the tools that write project file contents, and it deliberately declares no `prWorkflow` capability so it stays fail-closed in PR review and feedback modes.

### Response shape

The tool returns pretty-printed JSON. When `consensus.enabled` is false the response is only `{ success: false, disabled: true, message }`. Otherwise:

| Field | Meaning |
|-------|---------|
| `success` | Always `true` on this branch — the report was written. |
| `report_id`, `report_path` | The content-addressed id, and its path relative to the project root (`.swarm/evolution/consensus/<report_id>.json`). |
| `generated_at`, `integrity_hash`, `config_hash`, `redaction_policy_version` | Copied from the persisted report. |
| `thresholds` | `min_support`, `min_successful_runs`, `max_evidence_items` as actually applied, plus `min_task_diversity` sourced from the miner rather than restated. |
| `input_run_count` | Size of the report's `inputIds` list — distinct run ids, after the 200-entry cut. `truncation.total_input_ids` is the pre-cut count. |
| `corpus` | One `{ source, observations }` row per readable source, from `corpusHashes`. Counts what the SOURCE held, before the request filters and before the budget. |
| `corpus_truncated` | Whether `max_evidence_items` cut the corpus. |
| `truncation` | The persisted truncation record: `corpus`, `observations_tallied`, `input_ids_truncated`, `total_input_ids`, `attributes_dropped`. |
| `unreadable_sources` | Sources that threw. Returned only — the stored report shows them as a missing `corpusHashes` row. |
| `attribute_count`, `investigation_note_count`, `proposal_count` | Totals over the persisted report. Investigation notes are attributes with `proposedTarget: 'none'`. |
| `deduped_proposal_count` | Proposals suppressed because an earlier **consensus report still on disk** already carried the fingerprint. |
| `cross_producer_duplicate_count` | Proposals that got no ledger entry because the recommendation's cross key was already there. See below — this is not a count of other producers. |
| `summarized_count`, `summarized_but_not_shown`, `restatements_accepted_this_run` | See [Optional LLM restatement](#optional-llm-restatement). |
| `summarization_skipped_reason` | Present only when summarization never ran: `no_attributes`, `disabled_by_config`, or `no_dispatcher`. |
| `attributes` | The first 25 attributes in canonical signal order, each as `{ id, statement, llm_summary?, support, success_support, failure_support, task_diversity, model_diversity, confidence, proposed_target, counterexample_count }`. |
| `attributes_truncated` | Whether the report holds more attributes than the inline echo shows. |
| `retention` | `{ configured, pruning_enabled, deleted, failed }`, plus `retained` **only when `pruning_enabled` is true**. Under `report_retention: 0` pruning is disabled, so nothing is deleted and nothing is enumerated — there is no retained count to report, and printing `retained: 0` would say every report had been discarded. |
| `guarantees` | Fixed strings describing properties the code enforces. Each is covered by a test. |

### Reading `cross_producer_duplicate_count`

The name is narrower than the behaviour, so read it as **"recommendations the shared ledger had already seen"**, not as "recommendations another producer made".

The ledger's dedup key (`crossKey`, `src/services/recommendation-ledger.ts`) deliberately drops the producing mechanism — that is the whole point of a cross-producer ledger — so the miner's own earlier emissions collide with it exactly like the curator's or the improver's. Two bounds make that routine rather than theoretical: `consensus.report_retention` defaults to 50 while the ledger keeps 500, and the miner's within-producer dedup (`deduped_proposal_count`) only reads reports that still exist. Once a report is pruned, its proposals are re-derived and re-emitted, and then match the miner's own surviving ledger entry — counted here.

Matching is also exact over normalized text, so genuine cross-mechanism suppression stays uncommon: the miner and the improver build statements from fixed templates while the curator emits free-form lessons.
