# release-owner-guard: merge-base diff semantics

## What

The CI release-owner guard (`scripts/check-required-check-contract.ts`,
`--release-owner` mode) now resolves `git merge-base <base.sha> <head.sha>`
before diffing the release-please-owned files (`package.json`, `CHANGELOG.md`,
`.release-please-manifest.json`) instead of running a two-dot diff directly
against the trusted base SHA. The merge-base result is validated as a single
40-hex SHA (fail closed otherwise), and merge-group events additionally assert
that their declared `base_sha` is the merge-base of the group head — failing
closed on any mismatch rather than silently drifting from the declared-base
range. `changedFilesForGuard` and `TrustedGitHubContext` are exported for the
new regression suite, and `docs/ci-required-check-contract.md` documents the
semantics.

## Why

GitHub's `pull_request.base.sha` is the current `main` tip at event time — a
moving target. A two-dot diff against it contains the reversed diff of every
commit `main` gained after the PR forked, so whenever a release-please merge
landed while a PR was open, the guard accused that PR of "unauthorized edit to
release-please-owned file(s)" it never touched, failing `release-owner-guard`,
`quality`, and `unit-passed`. Observed on PRs #2798, #2940, and #2993 (plus a
#2917-era incident worked around by rebase); at the repo's release cadence
(~20 release commits since 2026-09-01) this fired at essentially every release
boundary. Sibling change-detection consumers (`check-pending-fragment.ts`
BOT-H1, `check-skill-assertions.ts`, `src/review/diff-source.ts`) already used
merge-base for exactly this reason. As a side effect, a genuine violation's
message now names only the files the PR actually edited (previously the
main-side edits inflated the accusation list).

## Caveats

- The issue's optional stale-base advisory ("rebase required" notice) is
  deliberately not implemented: at ~20 release commits/month it would fire on
  nearly every PR open across a release boundary, and its mandatory clause
  (never an unauthorized-edit accusation for staleness) is satisfied by the
  merge-base semantics itself.
- The merge-group equivalence assert fails closed if GitHub ever changes how
  group heads are constructed; an emergency fix on `main` activates
  immediately for all runs because the guard job executes the protected base
  copy of the checker.
- The guard now requires both event SHAs and a shared ancestor in the local
  object database (that is what `git merge-base` resolves); the guard job's
  `fetch-depth: 0` checkout provides it. A future shallow-fetch optimization
  on that job would make the guard fail closed (`cannot resolve merge-base`)
  instead of evaluating — deliberately, per the fail-closed posture.
- The `release-owner-guard` job's bootstrap `else` leg (checker absent at the
  base SHA) still uses a two-dot shell diff; it is unreachable for any PR
  based on current `main` and was left untouched (no workflow hash churn).

## Tests

New suite `tests/unit/scripts/required-check-contract-2997.test.ts`: the
issue-requested two-dot vs merge-base contrast across a release-please-style
merge (clean PR accepted), genuine-edit true positive with message precision,
merge_group equivalence for single-PR and chained two-PR batches, and both
fail-closed legs (unresolvable merge-base; merge_group base that is not the
merge-base). A review round added mutation pins for the two fail-closed
sub-conditions: the merge_group base comparison is pinned case-insensitive
(uppercase declared base), and a sha256-object-format fixture exercises the
non-40-hex merge-base value leg that the orphan-history test cannot reach.
The existing `required-check-contract-wiring-2677.test.ts` pins
are unchanged (`releaseOwnerDiffArgs` still emits the bounded two-dot pathspec
diff; it now receives the resolved merge-base).

# Default swarm models rotated onto the verified zen keyless roster; model-unavailable fallback now fires (issue #3022)

## What changed

- **Default models rotated (all hosts).** `opencode/minimax-m2.5-free` (coder) and `opencode/gpt-5-nano` (test_engineer, critic_\*, curator_\*, and every fallback chain) were dropped from the opencode zen keyless roster — fresh installs failed at first delegation with `Model unavailable: <id>` and zero fallback advances. Defaults now use roster-verified ids: coder `opencode/nemotron-3-ultra-free`, cheap tier `opencode/mimo-v2.6-flash-free`, everything else `opencode/big-pickle` (unchanged). Verified live 2026-10-02 on OpenCode 2.0.21 (`opencode run -m` matrix).
- **Roster guard.** `tests/fixtures/opencode-zen-keyless-roster.json` snapshots the 8 live-verified keyless ids (with the refresh procedure in `_meta`); `tests/unit/config/default-models-roster-guard.test.ts` fails when any default or fallback leaves the roster, and `src/config/project-init.ts` now derives its example fallback chain from `DEFAULT_AGENT_CONFIGS` instead of a hardcoded duplicate. `tests/unit/config/multilevel-fallback.test.ts` was rewritten to import the real constants (its local copy had drifted into fiction).
- **`Model unavailable` classifies retryable-with-fallback.** `classifyProviderFailure` now routes `Model unavailable: <id>` / `ModelUnavailableError` (OpenCode v2 `SessionRunnerModel.ModelUnavailableError`, provider code `provider.no-route`) to `provider.unavailable` / `retry_fallback` — advancing to the next `fallback_models` entry instead of dropping the error as `provider.unknown`/`do_not_retry`. The transient pattern gains `model.?unavailable`; the guardrails tool-output advisory is unaffected (its provider-marker pre-filter carries no model vocabulary — pinned by negative controls).
- **OpenCode v2 fallback advance works end to end.** The v2 event mapper accepts both error-event dialects (`session.execution.failed` with a `data` payload — the live plugin stream — and the SDK's `session.error`/`properties`) and maps `session.status` type-preserving so live `busy`/`retry` transitions can never terminalize a running session. The pump seeds session identity from `session.created`/`session.agent.selected` (`data.agent`) into the same map the v1 chat boundary writes, unblocking the no-route advance arm. The advanced model is applied on v2 by re-invoking the host's `ctx.agent.transform` surface and rewriting the registered agent's `model` reference (`src/host/v2/model-apply.ts`, keyed on the exact registered name — no phantom bare-role agents on multi-swarm configs; no-op on v1).
- **v2 startup model preflight.** v2 hosts carry no OpencodeClient, so the catalog-backed preflight was silent there. Setup now runs the pure `collectModelRosterWarnings` (new in `src/services/model-preflight.ts`) against the checked-in verified roster — inline at the setup tail, withTimeout-bounded and fail-open (live probing showed the v2 plugin realm never runs post-setup timers, so a deferred schedule would silently never fire) — and surfaces one bounded warning per off-roster opencode-zen configured model at startup instead of failing at first delegation.

## Upgrade notes

- If you pinned `agents.*.model` or `fallback_models` to `opencode/minimax-m2.5-free` / `opencode/gpt-5-nano` in your `opencode-swarm.json`, rotate them to a roster-verified id (the startup preflight will name them). Historical release notes still mention the retired ids — they describe the roster as it was.

# v2 model-apply follow-up: sticky-error narrowing, normalized fallback model, registration lifecycle (PR #3029 review)

## What changed

- **The v2 model apply now uses the normalized fallback chain's model.** `advancePendingTaskModelRoute` returns the `modelString` of the entry the fallback actually advanced to. `fallbackIndex` counts positions in the **normalized** chain (`normalizeModelChain` output — deduped, parse-filtered), so indexing the raw `fallback_models` list by it could apply the failing primary or an unparseable entry when a fallback duplicates the primary or fails to parse. The `session.error` advance arms in `src/index.ts` now pass that field to `applyV2AgentModelOverride` instead of computing from the raw list.
- **The host-global v2 apply is narrowed to sticky-appropriate errors.** The applied model persists on the registered agent until restart, so both advance arms now apply it only when the error is `model unavailable` or a quota error — the classes where permanently rerouting the agent to the next chain entry matches the v1 sticky fallback semantics. Transient network-class failures advance the per-session fallback selection (unchanged) but no longer rewrite the agent's registered model.
- **Repeated applies no longer accumulate live registrations.** `applyV2AgentModelOverride` holds the `Registration` returned by each `ctx.agent.transform` in a map keyed by the exact registered agent name and disposes only the SAME agent's previous registration when a new apply succeeds; `clearV2AgentTransformSurface` (v2 cleanup) disposes all of them. Keying matters because the host's `Registration.dispose()` is the undo path for that transform's rewrite — disposing a *different* agent's registration would revert that agent's sticky model rewrite and reintroduce the #3022 unavailable-model failure for it. The map is FIFO-bounded (128 entries) so pathological agent-name churn cannot grow it without limit.
- **Sticky gate as a tested predicate.** The sticky-appropriate error classes (model unavailable, quota) are centralized in `isStickyModelError` (`src/utils/provider-error-classification.ts`), used by both v2 advance arms and pinned by classification-matrix rows; the arms' use of the gate and of the normalized-chain `modelString` is pinned at their `src/index.ts` call sites.
- **Regression coverage.** `tests/unit/host/v2/review-followup-3029.test.ts` pins the normalized-modelString advance (duplicate-of-primary + unparseable fallbacks in the raw list), the registration dispose lifecycle, the pump's identity-seeding call site, and the guardrails advisory negative control; `tests/unit/failures/classification-matrix.test.ts` pins `Model unavailable` classifying to `provider.unavailable` / `retry_fallback`.
