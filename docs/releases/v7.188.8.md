# Knowledge receipts: dispatched child agents can file against their dispatch's directive block (#3036)

## What changed

- **Dispatched child agents can now file `knowledge_receipt` against the directive block in their own Task prompt (#3036).** The `delegate_directive` receipt membership is stamped with the architect's session id (the architect-side Task-prompt injection commits it), while the dispatched child files with its own session id — every foreground child filing was rejected `wrong_session` with no durable lineage to reconcile and no remedy in the rejection text. A `/swarm reset-session` made it worse by evicting child sessions wholesale (host-minted fresh ids per re-dispatch), which is how it was reported.
- The plugin now tracks dispatch lineage in memory (bounded, FIFO, TTL'd, reset-cleared — AGENTS.md invariant 8): the delegation gate records the host-observed (parent, child) pair at `taskMetadata` time for every dispatch (including reviewer/test_engineer children, which previously returned before the registration point), and the architect-side injection queues a dispatch fact a fresh child session adopts at registration. The `knowledge_receipt` tool resolves the filer's dispatch parent server-side and passes an authorized-filer set to the ledger; a membership whose stamp is that parent's is fileable when the filing agent role matches the exposure target (swarm-prefix normalized). The committed terminal still records the actual filer. Unregistered sessions never acquire a parent and stay fail-closed `wrong_session` — the shipped fence suites run verbatim and stay green, and the per-item rejection shape is byte-identical.
- **`wrong_session` rejections now name the mismatch and a remedy (#2817 visibility posture).** The receipt path surfaces "knowledge captured in session X but filed from session Y; file from the capturing session or its dispatched child (after a reset-session, a re-dispatched child is authorized), or surface fresh knowledge via knowledge_recall" — on the all-rejected detail and per rejected item. The `/swarm reset-session` partial-release line names the remedy on session-mismatched releases, and the two knowledge-application-gate escape-hatch errors append their batch rejection reasons.

## Why

Issue #3036 (follow-up to #3032): both reviewer and test_engineer agents had their `knowledge_receipt` filings rejected `wrong_session` after `/swarm reset-session`, with no session-visible remedy. Root cause: the fence compares two structurally different session ids for the same logical exposure (the architect's stamp vs the child's filing), which also fired on every foreground child filing regardless of reset.

## Notes

- Known residuals (by design, disclosed): same-role sibling cross-filing within one architect parent remains possible (the exposure was addressed to that role under that parent); a cross-parent window exists where a child registered before its dispatch's host event may transiently adopt a different architect's same-role pending within the 10-minute TTL window — inside that window the role check does NOT discriminate (both sides derive from the same dispatched role), so the child is transiently authorized against the wrong architect's stamps until the host-observed pair overwrites; the dominant in-window effect is a fail-closed false rejection of the child's own filing, and a wrong-accept additionally requires the child to cite the foreign architect's trace_id. Memberships stamped by dead child sessions (background-lane flows) stay fenced and are now named-with-remedy instead of silent.
- Tests: `tests/unit/state/dispatch-parent-lineage-3036.test.ts` (10), `tests/unit/hooks/knowledge-receipt-authorized-session-3036.test.ts` (8), plus close-command transitive stubs for the new state exports.
