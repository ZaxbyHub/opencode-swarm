# feat(workflow): external-evidence task class + `/swarm attest` — an in-machine exit for git-external deliverables

## What changed

- Plan tasks can now declare `evidence_class: "external_git"` with pinned
  `evidence_anchors` (read-only git assertions like
  `git rev-list --count origin/main..HEAD` expecting `0`). A new
  `/swarm attest <task_id>` command runs the anchors as bounded no-shell
  spawns and records a durable external-evidence bundle; completion is then
  admissible for that task WITHOUT any coder settlement ever existing — the
  in-machine exit for tasks whose deliverable is a commit/push or other
  git-external operation (previously permanently wedged: "Task N has no
  exact-task QA evidence" with `/swarm recover` a no-op).
- `save_plan` now warns when a commit/push-shaped task has an empty scope and
  no external declaration, naming both remedies (declare `external_git` +
  attest, or run it as a thin coder dispatch).
- `/swarm recover` distinguishes "no coder dispatch or settlement evidence was
  found" from a stuck settlement and lists concrete next steps (attest,
  manual close, thin-coder re-plan).
- Fail-closed by construction: undeclared tasks keep the byte-identical
  completion refusal; anchors admit only positively-known read-only git
  subcommands/flags (unknown flags, global options, `--output=`,
  `--show-signature`, `ext::` URLs, `status`/`ls-remote` all refuse); output
  beyond the evidence storage bound refuses instead of truncating; a
  declaration change revokes stale proofs (fresh attest required), while
  terminal evidence is preserved for audit.
- Plan hashes include the new optional fields (legacy plans hash
  byte-identically); `check_gate_status` and the plan/checkpoint markdown
  projections render the declaration.

# Fix: inherited-key lookups in lean-turbo scopes and /swarm concurrency, and numeric-entity decoding in web-fetch

## What changed

Same-class follow-ups to the `web_fetch` entity-decode fix, surfaced during review of that fix and closed in the same change set:

- `runPartitionPreflight` (`src/turbo/lean/partition-common.ts`) checked a caller-supplied `scopes` map with `task.id in scopes`. A plan task whose id was an inherited `Object.prototype` name (for example `constructor`) resolved to the `Object` function instead of a file list, and the planner threw `TypeError: ... is not iterable`. The lookup now uses `Object.hasOwn(scopes, task.id)`; a task id that is an own key of `scopes` still uses its declared scope, and any other id falls through to the normal undeclared-scope path (`.swarm/scopes/` file, then `files_touched` when `require_declared_scope` is false, otherwise the serialized no-scope path).
- `/swarm concurrency set <value>` (`src/commands/concurrency.ts`) checked presets with `normalizedValue in PRESETS`. `constructor` or `__proto__` matched, and the `Object` function was stored as the session concurrency override. The check now uses `Object.hasOwn(PRESETS, normalizedValue)`, so those inputs are rejected as invalid values.
- `decodeEntities` (`src/tools/web-fetch.ts`) now matches decimal references with `#[0-9]+` and hex references with `#x[0-9a-f]+`. Previously a decimal reference containing hex letters, such as `&#1e5;` or `&#12ab;`, was truncated by `parseInt` and silently dropped characters; it is now left as literal text. Numeric references that are NUL, a surrogate, or beyond U+10FFFF decode to U+FFFD (as the HTML spec specifies) instead of emitting a control character or lone surrogate, or vanishing. A digit run so long that it overflows to Infinity (hundreds of digits) is still left as literal text rather than decoded.

## Why

All three are the same class of bug as the main fix: a lookup or parse that accepts input it should reject, on values that originate from untrusted HTML or operator input. They sit next to the code the main fix touches, so they are closed here rather than left open.

## Impact

- `/swarm concurrency set constructor` (and similar) now returns the invalid-value message instead of storing a function.
- A pending lean-turbo task with a non-standard id such as `constructor` no longer fails planning when an explicit `scopes` map is supplied.
- `web_fetch` text no longer loses characters after a malformed decimal reference, and no longer carries NUL or lone-surrogate characters from numeric references.
- Declared scopes keyed by real task ids, real concurrency presets, and well-formed numeric references behave exactly as before.

## Migration

No migration required.

# Fix: HTML entity decode in web-fetch returned Object.prototype.constructor for &constructor;

## What changed

`decodeEntities` in `src/tools/web-fetch.ts` looked up HTML named entities with the `in` operator against a plain object literal (`NAMED_ENTITIES`). Because `in` traverses the prototype chain, `&constructor;` (any casing) resolved to `Object.prototype.constructor` and was decoded as `function Object() { [native code] }`, corrupting both `extractTitle` titles and `htmlToText` body text delivered to the agent from untrusted HTML.

Switched the lookup to `Object.hasOwn(NAMED_ENTITIES, key)`, which consults only own properties. Valid entities (`&amp;`, `&lt;`, `&gt;`, `&nbsp;`, etc.) continue to decode correctly.

## Why

Defense against corrupted agent-visible content when `web_fetch` processes attacker-controlled HTML. Reading a property name that happens to exist on `Object.prototype` (such as `constructor`) is not prototype pollution itself, but it is the same class of key-confusion bug. `Object.hasOwn` is the repo's established convention for own-property checks (see `src/failures/action-identity.ts`, `src/tools/create-tool.ts`).

## Impact

- `&constructor;`, `&CONSTRUCTOR;`, `&Constructor;` no longer decode to `function Object() { [native code] }`; they are left as-is (unknown entity).
- All previously-working named entities remain unaffected.
- Related numeric-reference fixes and two same-class sibling lookups are described in `inherited-key-lookups-and-numeric-entities.md`.

## Migration

No migration required. Pure bug fix restoring intended decoding behavior.
