# 8.x release pipeline completion: hardened publish path, fragment tooling, and a clean healing-release changelog

## What

- `release-please-next.yml` publishes can no longer run concurrently (workflow-level `concurrency` group, queue-not-cancel), no longer interpolate the `force_publish` input into shell text (job-level `env: FORCE_PUBLISH`), and refuse to publish from any ref other than `refs/heads/next` before the first `npm publish` executes — the documented `force_publish` dispatch recovery from `next` keeps working.
- The publish-step guardrails are now proven by EXECUTION, not line-shape: a test harness runs each real workflow publish step under a fake `npm` on PATH and asserts the exit codes discriminate npm failure / version-conflict / tolerance / success. The three known neutralization shapes (`set +e` after the required set line, always-true tolerance, `exit 1` nested under a never-true `if`) each ship as executed mutants that neutralize — exactly the class the real-step legs catch.
- Breaking-commit detection in the release-please config guard now scans commit BODIES line-anchored (`^BREAKING[ -]CHANGE:`), closing the false negative where the space-form footer is invisible to git's trailer machinery. The original trailer-leg filter (`key=BREAKING CHANGE`) was executed-proven vacuous (matched neither spelling) and is corrected to the hyphen-key form.
- The bootstrap changelog bound moves from the March breaking commit to the dormant tip `23f051f11`: the healing release PR's changelog now contains only the October 8.x-line changes instead of seven months of dormant-branch noise. `packages/telemetry` (zero post-bound commits) still releases in lockstep via release-please's linked-versions synchronize mechanism — verified from the plugin source and pinned by the rewritten group-coverage test.
- The main line's release-fragment pipeline is ported to the 8.x line: `scripts/release-notes-fragments.mjs` (release-PR body enrichment, per-component-tag GitHub Release body enrichment with a per-package CHANGELOG fallback, and consume-and-remove cleanup whose deletions are anchored to the release merge SHA and the published body), plus `scripts/check-pending-fragment.ts` + `scripts/user-visible-paths.ts` behind the new `fragment-gate.yml` workflow — user-visible 8.x PRs now require a pending release-note fragment, same as main.
- New `update-release-pr` / `update-release-body` / `cleanup-fragments` jobs decouple release notes from publish success (a failed npm publish can no longer strand the GitHub Release body), derive tags fail-closed from a lockstep-identical manifest, and open a cleanup PR that deletes exactly the fragments the release published.

## Why

Issues #3150/#3151 stayed open because the healing release never shipped: release PR #3235 was closed unmerged and nothing regenerated it, while npm's `next` dist-tags still point at the broken pair (core with the leaked `workspace:*` spec, plugin with the bare-fn default export). This change is the release-path completion — the next release PR generates through a hardened pipeline, carries a clean changelog, and its release notes aggregate the pending fragments. Issues #3229 (workflow hardening backlog incl. both review residuals) and #3228 (fragment pipeline parity on the 8.x line) close with it. The release PR merge itself remains a maintainer step (verify the proposed changelog covers only this line's changes, then merge).
