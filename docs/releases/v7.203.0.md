# swarm-pr-feedback drives a PR to merge; new session-retrospective skill

`swarm-pr-feedback` used to stop once known feedback was closed. Driving CI, merging, and reviewing the session each needed a separate instruction every session. Run on a PR, the skill now carries the PR through to the end.

## Drive to merge (new `references/drive-to-merge.md`)
- **Intake.** The run takes this session's own review findings and every PR comment with findings, and runs the existing Stage A → Stage B → closeout gates.
- **Dispositions.** It plans every unfixed item's disposition before the closeout gate. It publishes them after the push is verified, or after a verified no-change outcome, and publishes any disposition added later before it checks the merge preconditions.
- **CI to green, within a budget:**
  - one rerun per infrastructure signature;
  - failures proven on the base branch become `PRE_EXISTING` dispositions, not PR fixes;
  - at most 2 fix attempts per signature and 5 fix cycles per run, counting CI-driven and review-driven rounds alike.

  Under Profile A each fix is a new controller generation.
- **Merge:**
  - **Authorization.** Only the user's own words asking for the merge in the current run authorize it, or a yes to the run's own "merge now?" question; a question, negation, hypothetical, or quoted mention of merging never does. A skill invocation, `[MODE: PR_FEEDBACK]` signal, default prompt, monitor wake, or loop activation never authorizes a merge. An injected event or PR-monitor wake also neither answers that question nor ends the wait for it.
  - **Merge command.** It uses `--match-head-commit` on the gated head. Inside the run every `gh pr`, `gh run`, and `gh repo` call and every GraphQL query is bound to the PR's resolved owner and repository (`--repo <owner>/<repo>`); swarm-ci-monitor's merge commands carry `--repo` too. It passes no strategy flag on a merge-queue base, and passes the repository's single allowed method on a direct base (or asks when several are allowed).
  - **Monitoring.** It monitors the merge queue until the merge commit is on the base. Any merge precondition that cannot become true, an unanswered question, or a monitoring ceiling ends the run with a report and the close-out steps; stopping monitoring never dequeues the PR. The final report says whether a PR monitor is still subscribed and, if the PR did not merge, asks whether to unsubscribe it.
- **Close out, merged or not:**
  1. re-verify every disposition on its live artifact;
  2. run a session retrospective;
  3. run the memory closeout.

  "Fixes only" skips CI and the merge; "don't merge" skips only the merge. Runs started by a PR-monitor wake keep their triage scope.

## Follow-up dispositions
- `references/followup-dispositions.md` now states two rules explicitly:
  - anything the PR introduced is fixed in the PR;
  - a verified, consequential defect is never closed on the agent's own judgment.
- In practice FILE means Priority items or user-approved Improvements.
- Every ASK item, follow-up proposal, Improvement, and enhancement idea goes through its own critic call before it reaches the user, and the critic's verdict travels with the question. The closeout critic gate does not count as that call.
- Priority FILE items also get a critic call before filing. A kill or downgrade makes one an ASK. If the critic is unavailable, the item is still filed, marked "not critic-reviewed" in the issue body and the ledger, and listed in the final report.
- A reviewer's severity label (`nit`, `non-blocking`) never replaces verification.

## New `session-retrospective` skill
- An evidence-based retrospective of the whole session, reconstructed from the harness's own history:
  - Claude Code transcript JSONL;
  - ZCode `~/.zcode/cli/db/db.sqlite`, read-only;
  - Codex rollout JSONL;
  - OpenCode session store.
- It reports:
  - what worked and what failed;
  - tool and skill friction;
  - prioritized improvements;
  - new skill and tool proposals.
- Every proposal is critic-adjudicated before the user sees it. Analysis only.
- It lives at `.claude/skills/session-retrospective/` with an `.agents/skills` adapter, so ZCode, Codex, Claude Code, and OpenCode load it in this repository.

## swarm-ci-monitor
- Step 4a no longer tells agents to omit the merge-strategy flag on every base. A non-interactive `gh pr merge` refuses without one on a direct-merge base, so the step now requires the repository's allowed method there. Step 3 records the head SHA it verified, and Step 4a always passes `--match-head-commit` with that SHA, so a commit pushed after the re-check cannot be merged unchecked.

## Surfaces
- Both references, the canonical skill and its two adapters.
- The new skill and its adapter, classified `agents-only` in `src/config/skill-mirrors.ts`; the editing-skills guide now says such skills need that entry.
- `swarm-ci-monitor`.
- The `/swarm pr-feedback` help text and the regenerated `docs/commands.md`.

# Feedback rounds now re-fetch PR comments at every round boundary

## What changed

The `swarm-pr-feedback` skill contract now makes mid-round feedback intake explicit and enforced (issue #3607), with the new contract text pinned by the skills contract tests so a deletion fails the suite:

- **Round-boundary re-fetch.** Intake is no longer one-time: at the start of every fix round and again before the closeout gate, the PR's issue comments, inline review comments, and reviews are re-fetched and every external finding gets a ledger row. Automated reviewers (per-head bot reviews, Copilot inline comments) post findings against intermediate heads mid-round; findings that land after the ledger was built are now structurally caught instead of discovered by luck. The fetch commands and bot markers live in `references/intake-surfaces.md`.
- **Final-critic enumeration challenge.** The closeout gate's final critic now fetches every PR comment and review fresh and reconciles each external finding against the ledger — an approving reviewer delta round is invalid while newer external feedback has no row.
- **Published closure ledger.** Before the final critic runs, the closure ledger is recorded in the runtime session task-gates artifact (bound to the reviewed head SHA and fetch time), which the critic reconciles against its own fresh fetch; the ledger is published as a PR comment only after the reviewed commit is pushed and the remote head verified (PR-comment publication is gated until then in every profile).
- **Gates log from round start.** The runtime session task-gates artifact (durable-session-state, e.g. `.zcode/session/tasks/<slug>/gates.md` on ZCode) is opened at round start and appended after every reviewer/critic verdict, so compaction or handoff re-entry reads state from disk.
- **Probe entry-state guard and attributed kills (issue-tracer).** Mutation/revert probe scripts that restore via `git checkout --` must refuse to run on a tree with uncommitted work (the restore silently reverts the fix and then reads clean), and a mutation counts as killed only with baseline-green → mutation-landed → named-test-red → restored evidence — a generic `(fail)` anywhere in the output is not a kill. Details in the issue-tracer acceptance-check contract and the feedback operational-gotchas reference.

The `swarm-pr-feedback` "what counts as feedback" enumerations moved to `references/intake-surfaces.md` (progressive disclosure); the entry skill stays under its disclosure baseline.

## Why

A session retrospective of the PR #3592 round (2026-11-07) found that two per-head automated reviews (one with a HIGH finding) and a Copilot inline comment landed mid-round with no ledger disposition until the final critic's closure-ledger enumeration caught them — costing an extra fix round. The same retrospective found the feedback round's gate log created only near the end (a compaction mid-round made recovery depend on the summary), and a mutation probe's file restore wiped uncommitted fix work despite the trap being documented three times in memory — knowledge stored but not enforced. These changes turn each of those catches from luck into contract.

Issue: #3607

# Issue-Tracer: rebind rows and mutation-battery honesty

## What

Two evidence-honesty upgrades to the issue-tracer skill (v3.0.1), both from
the retrospective of the ragappv3 #1075/#1076 session (PR #1093):

- **Rebind rows for post-approval head drift.** New
  `trace-check.sh rebind --gate <plan-critic|implementation-review|final-critic> --reason <text> --slug <slug>`
  subcommand validates the drift and prints an explicit append-only Gates row
  (`... | 06-critic-review.md rebind(<reason>) |`) that re-binds a gate's
  existing approval to the current HEAD/tree. The validator stays read-only;
  the caller appends the row. Phase 3 accepts the explicit chain (historical
  APPROVE row matching the artifact's identity pair + a rebind-marked row at
  the current head) and emits `OK artifact-identity-<gate>-rebind-chain`;
  phases 4.5/4.6 keep the strict check, so those gates still require a fresh
  delta-review artifact (06b/09b) when they drift. A rebind is bookkeeping
  for head drift, never a substitute for a fresh critic round when the
  reviewed artifact changed. This replaces the previous state where
  post-implementation phase-3 re-sweeps produced two unexplained FAILs that
  had to be disclosed as prose.
- **Mutation-battery honesty checklist** in
  `references/evidence-artifacts.md`: one cwd change for the whole battery,
  per-probe verdicts from the pytest summary only (KILLED/SURVIVED/
  PROBE-ERROR, never counting PROBE-ERROR as KILLED), per-probe logs,
  repo-relative capture paths, and re-anchoring after any post-battery edit —
  the exact failure mode the vacuous first battery of ragappv3 PR #1093 hit
  (8/8 "KILLED" while pytest never ran).

`references/evidence-artifacts.md` gains a "Rebind rows" section documenting
the row shape and the not-a-re-approval boundary; SKILL.md's Gate Table
paragraph points at it. metadata.version 3.0.0 → 3.0.1 (installed skill
copies will show handshake `STALE` until refreshed, by design).

Tests: `tests/unit/scripts/trace-check-rebind.test.ts` (7 tests: emit shape,
no-drift refusal, no-prior-row refusal, gate/reason validation, phase-3 chain
acceptance, phase-3 strict failure without the row, phase 4.5 stays strict).
