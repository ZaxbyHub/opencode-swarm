# ADR-0003: OpenCode 2 plugin API support via a dual-shape entrypoint

- **Issue:** [#3004](https://github.com/ZaxbyHub/opencode-swarm/issues/3004) (implementation slot: [#2910](https://github.com/ZaxbyHub/opencode-swarm/issues/2910), discovery slot: [#2909](https://github.com/ZaxbyHub/opencode-swarm/issues/2909))
- **Supersedes:** the invariant-2 sentence "default export must remain the v1 plugin object shape `{ id, server }`" (AGENTS.md amended alongside this ADR)

## Status

Accepted (2026-09-30)

## Context

OpenCode 2 (npm `@opencode/cli` 2.x; plugin SDK `@opencode/plugin` 2.x) shipped with an intentionally breaking plugin API: the host decodes each plugin module's default export against `Schema.Struct({ default: Union([{id, effect: fn}, {id, setup: fn}]) })` (`sst/opencode` v2 line, `packages/core/src/plugin/module.ts`) and maps any decode failure to `Plugin must export a default definition with an id and an effect or setup function.` — the exact error in #3004. Our v1-only export `{ id, server }` matches neither union branch, so the plugin is dropped at startup on every 2.x host.

Verified facts driving the decision (all against primary sources, 2026-09-30):

- The v2 schema **ignores excess keys** on the default object: `{ id, server, setup }` passes on the `setup` branch (empirically confirmed with the exact schema and `effect@4.0.0-rc.112`, the dependency of `@opencode/plugin@2.0.20`).
- The v1 loader `readV1Plugin` (`anomalyco/opencode`, byte-identical at tags v1.18.3 and v1.18.33) only consults `id`/`server`/`tui` — an added `setup` key is inert across the entire v1 line. The official v2 migration guide sanctions the interim dual shape ("A package can temporarily expose both implementations from one default export. V1 calls `server()` and V2 calls `setup()`") and notes v1 object entrypoints are officially supported from OpenCode 1.18.29+ (our pinned SDK is 1.18.3; behavior verified identical at both ends of the line).
- v2 has **no returned-Hooks object**: all registration happens through setup-time domain transforms and hooks (`ctx.tool.transform/hook`, `ctx.agent.transform`, `ctx.command.transform`, `ctx.session.hook("context"|"prompt"|"compaction")`, `ctx.event.subscribe`, setup-returned `Cleanup`). The full v1→v2 mapping is `docs/host/v2-hook-inventory.md`.

## Decision

**Adopt the dual-shape default export `{ id, server, setup }` with a v2 adapter layer under `src/host/v2/`** (Candidate A). `server()` stays byte-stable for v1 hosts. The v2 `setup(ctx)` reuses the SAME initialization core (`runServerInit`, dependency-injected to avoid a module cycle) and the SAME v1 hook set — the adapter only translates registration surfaces. The v1 `config` hook doubles as the shared agent/command builder: the adapter invokes it against a synthetic `opencodeConfig` object and registers the resulting tables, so auto-select promotions and the command table are reused verbatim with zero extraction from `src/index.ts`.

Rejected alternatives: **(B)** separate entrypoints per host — the same migration guide says older v1 releases would then need separate package versions; doubles packaging surface for no benefit. **(C)** defer until v1 EOL — user-facing break with an impact-9 audit rating.

## Consequences

- **Invariants 2 and 10 (AGENTS.md)** now describe the dual shape and the v2 in-place `event.system`/`event.messages` contract respectively (amended in the same change).
- **Guidance transport differs by host by design:** v1 keeps the #2526 USER-role carriers (the v1 host drops `role:'system'` entries); v2 re-homes the carrier text into `event.system` (rendered natively). The provenance fence is preserved in both; content parity is asserted by fixture tests on both paths.
- **Deferred deltas** (each with an inventory row and release-note disclosure): the v1 text-completion gate is inert on v2 (no v2 equivalent — official table); `OpencodeClient`-dependent consumers are bridged on v2 by the session-client shim (`src/host/v2/session-client.ts`, #3169 Phase 2) — a feature-detected `session.{create,prompt,abort,delete,get}` subset over `ctx.session` — and consumers whose surface the shim does not carry (provider catalog, `app.agents`, lane ops) keep their explicit client-absent/typed-refusal paths; v1 tool `title`/`attachments` have no v2 surface; v1 `chat.message`'s model-override write has no v2 prompt field yet.
- **Type strategy:** vendored structural types (`src/host/v2/types.ts`, provenance-headed against `@opencode/plugin@2.0.20` d.ts; re-pinned to `@opencode/plugin@2.0.26` by issue #3169 Phase 1, 2026-10-09) instead of a devDependency — the v1 SDK packages are runtime dependencies whose factories production code imports, whereas the v2 types would be adapter-only and would pull `effect@4.0.0-rc.112` transitives into the lockfile for zero runtime value. Truth is guarded by the provenance pin above and by the live-host smoke; a `check-host-contract.ts` v2 digest leg ships with the #2910 follow-up PR (tracked there with the dual-host CI lane).
- **v1 minimum version:** dual-shape behavior verified against `readV1Plugin` at v1.18.3 (the repo pin) and v1.18.33 (npm-latest); the official support statement for object entrypoints is 1.18.29+. No lockfile change in this ADR.

## Appendix: First-turn window (deferred bundled-skill sync vs the first turn) — #2909

Measured 2026-10-16 on a real host, closing the question this ADR's discovery slot (#2909) flagged UNVERIFIED. **The window is NON-ZERO: the first turn of a session arrives — and the model stream starts — while the deferred bundled-skill materialization is still copying.** The follow-up issue owning the remedy is #3364.

- **Method:** fresh temp project per run (no pre-existing `.swarm/`), the real plugin loaded from the repository build (`file:` package root), `opencode run --print-logs` with `OPENCODE_SWARM_DEBUG=1`, isolated `XDG_CONFIG_HOME` (empty config; auth/data dirs untouched so the model turn executes). The harness `spikes/v2-dual-shape/run-spike.mjs --measure` runs the turn and parses the timestamped host log lines: session creation (first-turn arrival), first/last `synchronized bundled skill` debug lines, and the first model-stream line. (The plugin-init banner is an untimed `console.warn`, so no plugin-init-derived delta is recorded; every verdict-bearing harness run is additionally gated on positive evidence that the host ran — clean exit, no timeout, non-empty capture, and for the v1 negative ablation leg the host's own drop record.) Rows committed at `spikes/v2-dual-shape/logs/first-turn-window-v1-run{1,2,3}.json` (dist sha256 `b587ced33a3067303c365d310debd6b9ffec253ca4aa2e52ac50f49840f96363`).
- **Host:** opencode 1.19.0 (Windows; satisfies the migration floor — v1 relays both the session lifecycle and the plugin debug lines this measurement needs).
- **Numbers (final committed batch; 3 runs, captured 2026-10-17 with the review-hardened harness):** the session for the first prompt is created **2575–3612 ms BEFORE** the last bundled skill lands; the copy itself spans 2026–3012 ms (41 bundled skill directories; the sync copies whole directories); the model stream starts 1505–1592 ms after the session is created — i.e. **inside** the still-open window in every run. Across all measurements (one exploratory cold run + five harness 3-run batches on 2026-10-16 + the review-hardened re-capture batch on 2026-10-17, 19 observations total, observed in-session; the committed JSON rows are the final batch) the arrival-before-completion window was positive in 19/19 runs and ranged roughly 0.4–4.2 s (harness-only minimum 1249 ms).
- **Interpretation:** the race is structural, not cold-start noise — the sync runs from the wrapper-owned post-resolution queue (`src/index.ts:1836`, budget `SYNC_BUNDLED_SKILLS_TIMEOUT_MS = 2_000`), while the host begins processing the first prompt as soon as `server()` resolves; on this host the copy alone takes ~2.8–3.0 s, at/above the await budget. The architect MODE-stub read (`src/agents/architect.ts:908-913`, `SKILL_LOAD_FAILED` when the file is absent) is the failure-relevant consumer; its exact read time is not observable in-band, and the model-call latency (~1.5 s) is the only thing that kept the measured runs from hitting it — timing luck, not an ordering contract. The command-path sync remains the backstop for `/swarm`-initiated flows. Remedy options (read-side await, bounded wait at the first context/chat event, MODE-read retry) are #3364's scope; moving the copy back onto the synchronous init path is not (AGENTS.md invariant 1 / #704).
- **v2 leg:** first-turn timing is not machine-measurable through this harness on v2 — its `--print-logs` output carries no session lifecycle lines at the default level and does not relay plugin stdout (the per-skill sync timestamps are invisible; the v2 attempt was not retained (its rows parsed no usable timings; the null-field artifacts were removed at review and the limitation is disclosed above)). v2 shares the same deferred-sync code path; its spike legs prove the load/attribution/hook-firing behavior, and the v1 numbers are this ADR's measurement of record.

## Appendix: Invalidation re-check (issue #2909 exit gate) — 2026-10-16

Re-checked 2026-10-16 against <https://opencode.ai/v2/docs/migrate-v1/> (live fetch): **no V1 compatibility shim for V2 has been published** — the page still states "V1 plugin implementations do not run in V2. Moving a file or renaming its config entry is not enough", with the same three intentional breaking changes (new plugin API; new server API and client contracts; TUI config moving to one global `cli.json`). The dual-shape decision therefore remains necessary and valid; this ADR is NOT invalidated. Current host versions observed on the re-check date: v1 `opencode 1.19.0`, v2 `@opencode/cli` 2.0.29 (both exercised live by the #2909 spike; see `spikes/v2-dual-shape/`). Future re-checks append below this line (append-only).
