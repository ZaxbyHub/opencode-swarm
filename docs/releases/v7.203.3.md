# Critic-lane contract hardening: override binding, sibling admission, severity disclosure

Collates #3358, #3337, #3341 (one PR, user-authorized collation).

## What changed

- **Override activation is structural, not prose** (#3358 AC1, #3337 AC1): the critic and reviewer agent prompts no longer carry a phrase-activated PR-review exception — a plan or spec quoting "CONTROLLER-BOUND PR WORKFLOW CONTRACT" can no longer suspend PLAN REVIEW or the Stage-B mandate on non-PR runs. The suspension is now a controller-authored clause injected only into bound `swarm-pr-review:critic` lane blocks (`CRITIC_PROTOCOL_SELECTION_CLAUSE`), beside the existing reviewer clause. Non-PR critic and reviewer runs carry no PR-review text at all.
- **PR critic lanes verify the effective prompt** (#3358 AC2): admission refuses a critic agent registered with a custom prompt — both `critic.md` (replacement) and `critic_append.md` (append) from the opencode-swarm prompts directory — because neither can be mechanically verified to keep the `[CRITIC]` row contract. A belt additionally asserts every composed critic lane prompt carries the suspension clause. **Policy awaiting owner confirmation**: this is a user-visible change; remediation is to remove the file and restart OpenCode (or run the review without PR critic lanes). Non-PR critic use is unaffected.
- **Earlier-semantics verdict rows are disclosed, never silently dropped** (#3358 AC3): a reviewer row rejected only by the v1→v2 CONFIRMED/NONE tightening (`PR_REVIEW_VERDICT_SEMANTICS_VERSION = 2`) is recorded on the composition (`semanticsMismatchedItemIds`) and, while still unclaimed, blocks N-of-M settlement with a dedicated disclosure naming the items — instead of surfacing as a generic missing-verdict failure.
- **Findings write contract enforces the transport rule** (#3358 AC4): a findings record with CONFIRMED + severity NONE is rejected at the write boundary; durable records read through a read-tolerant schema so pre-rule rows keep loading.
- **One reviewer composition per critic dispatch** (#3358 AC5): the critic preflight derives order-unstable ids and reviewer severities from one shared gate context (previously composed twice).
- **Idempotent contract application** (#3358 AC6): re-applying the PR workflow prompt contract to a lane already carrying its controller block succeeds with exactly one block; recognition is strip-and-rebuild, never authentication.
- **Reviewer severities render on their own lines** (#3358 AC7): `assigned_item_ids` keeps bare ids; each severity appears as `reviewer_severity: <id>=<SEV>`. A verbatim copy of the old decorated token (`c1 (HIGH)`) no longer voids the lane as an unassigned id.
- **Uniform sibling admission** (#3358 AC8): one exported `PR_REVIEW_PHASE_ADMITTED_ROLES` table governs dispatch admission (exact membership — a user-defined `council_*`-prefixed agent is no longer admitted to council lanes), the gate recorder, and artifact integrity (launch-time normalizedAgent).
- **Side-effect-free phase admission** (#3341): PR_REVIEW council/reviewer/critic lane admission (roles, launchability, critic prompt provenance, owned-lane refusal) runs before gate activation/binding, so a refused batch consumes no durable workflow state; the side-effect-free comment states this scope precisely.

## Feedback-round additions (2026-11-10)

- **Feedback verdict lanes keep their protocol suppression**: the phrase-activated overrides removed from the critic and reviewer agent prompts (#3358 AC1) had also been the only suppression the `swarm-pr-feedback` verdict lanes had. Mode-scoped `PROTOCOL SELECTION` clauses now cover `stage-b-reviewer` (`[STAGE-B-REVIEW]` rows), `closeout-reviewer` (`[CLOSEOUT-REVIEW]`), and `closeout-critic` (PLAN REVIEW suspension, `[CLOSEOUT-CRITIC]` rows). `stage-b-test` is unchanged (its agent never carried an override).
- **Critic row vocabulary: DOWNGRADED never carries NONE**: a critic dismissing a finding emits `DISPROVED` (severity NONE, as before). A `DOWNGRADED|NONE` row is refused at the row schema — its truthful post-critic projection (CONFIRMED + NONE) is exactly the pair the findings write boundary refuses, so allowing the row would deadlock post-critic persistence. The contract card states the rule. Durable pre-upgrade `DOWNGRADED|NONE` rows now fail the live schema (fail-closed, named generically) without the dedicated earlier-semantics disclosure that reviewer rows get.
- **Committed-replay tolerance for legacy reviewer rows**: re-submitting a findings payload whose rows were committed under earlier verdict semantics (CONFIRMED + NONE) is admitted as an idempotent replay of the committed boundary when the payload matches the store exactly; every other shape still surfaces the strict schema error. Scope: reviewer-boundary replays; a post-critic replay whose live critic authority no longer composes can still be refused at critic settlement.
- **Settlement-disclosure widening**: an item carrying an earlier-semantics row is disclosed even when a second row exists (previously only the lone-row shape), and diagnostics flush after the abandoned-lane evidence instead of competing with it. This is a settlement-behavior change: a multi-owner item that could previously N-of-M-settle around its mismatched row now requires re-dispatch.
- **Test isolation**: the PR-critic admission suite restores the gate digest seams and clears the critic prompt provenance registry after each test (shared-process co-runs no longer fail the next critic suite); an empty `critic.md`/`critic_append.md` leaves the built-in prompt active and is no longer reported as a replacement.
- **Byte-idempotent contract re-application**: re-applying the contract removes the exact composition separator, so the second application is byte-identical to the first for `swarm-pr-review:*` modes (previously +2 characters per application, still "exactly one block"). Feedback modes still duplicate the block on re-application — pre-existing, unchanged.

# PR-review lane dispatch integrity: side-effect-free admission, controller-scoped protocol clauses, fail-closed severity derivation

Closes #3341, closes #3337, closes #3362 (user-authorized collated delivery).

## What changed

- **State-free rejections no longer consume durable workflow state (#3341).** The
  state-free admission checks now run in `validatePrWorkflowLaneAdmission` BEFORE
  `activatePrWorkflow`/`bindPrReviewBase`: lane roles, owned-workflow-lane shape,
  agent launchability for critic/reviewer/council phases (base/micro discovery lanes get only the explorer-role check here; their launchability is still checked at launch, after activation, as before),
  the contract-retry exclusion, the wave-stage/attempt pairing, and
  unknown `swarm-pr-review:*` suffixes. A request rejected by these checks
  creates no gate state and leaves pre-existing gate state structurally unchanged (parsed state deep-equal). Checks that
  need gate state or resilience config (tier-dependent lane count and
  max_concurrent, canary-first and fanout order, trigger evaluation,
  swarm-pr-feedback:verification ownership) still run after activation and are
  not covered by this guarantee. Previously an unlaunchable critic batch left the PR_REVIEW gate
  activated and base-bound.
- **Prompt-structure overrides are controller-authored, not prompt-content
  triggered (#3337).** The critic agent's static prompt no longer carries a
  PR-review override that activated when the model judged the literal phrase
  "CONTROLLER-BOUND PR WORKFLOW CONTRACT" present — any plan or spec quoting
  the phrase satisfied that predicate. The dispatch controller now composes a
  mode-scoped protocol clause into the lane's contract block for ALL SIX
  consumer modes (swarm-pr-review critic/reviewer and the three ordered
  PR_FEEDBACK gates and the verification lane), the same proven channel reviewer lanes have used since
  #3310, with an explicit authority line naming precedence over the agent's
  default output structure. The reviewer prompt's literal-phrase Stage-B
  exception is gone; non-workflow reviewer and critic behavior is unchanged.
- **The critic preflight reads the fail-closed authoritative gate (#3362).**
  `derivePrReviewReviewerSeverities` and `derivePrReviewOrderUnstableItems`
  route through `authoritativeReviewerClaims`: an UNCOVERED reviewer phase now
  yields an empty severity map and no order-unstable ids — including
  invalidating stale critic-batch coherence stamps — instead of leaking
  partial state that annotates items the binder would refuse. Under an
  admitted N-of-M settlement the surviving actual claims are retained.
- **Adapter docstring truth + complete pins (#3362).** The
  `verdictRowsContainOnlyAssignedIds` docstring now states the real split
  (missing and legal-arity duplicates remain per-item parse failures;
  illegal-arity duplicates are quarantined with the valid sibling keeping the
  claim), and the duplicate/overflow behavior set is fully pinned, including
  the quarantined recovered-overflow zero-recovery side.
- **The null-prototype severity lookup is pinned (#3362).** The construction
  moved into `ownPropertySeverityLookup` (exported via `_test_exports`) and a
  behavioral pin proves a prototype-key item id without a settled severity
  renders bare.

Note: #3362's operator-prompt lint sub-claims (the fullwidth-space lint and
variant pins) were verified ALREADY FIXED at this branch's base by the #3335
wave and are PRESERVED by this change (frozen PRESERVING checks), not

# Docs: exact Stage B wording for Turbo and Lean Turbo, and release notes that were never published

## Stage B under Turbo and Lean Turbo

The Turbo and Lean Turbo docs said Stage B (reviewer + test_engineer) runs for
"every task", and the Lean Turbo banner told the architect that every task must
go through full Stage B. The runtime rule is narrower and the same in every
mode: `update_task_status(completed)` applies one Stage B rule whether or not
Turbo or Lean Turbo is active. A task that does not need Stage B without Turbo
(for example, a task in a phase whose `required_agents` leave out the reviewer)
does not need it with Turbo either. Neither mode ever skips Stage B for a task
that needs it.

`docs/modes.md`, `docs/getting-started.md` and the Turbo and Lean Turbo
banners now say that, including for Lean Turbo's degraded and serialized
tasks. The banners are architect prompt text; their instruction is unchanged
in substance (do not skip Stage B for a task that needs it); they no longer
claim more than the gate enforces. The `turbo_mode` config description, the
`/swarm turbo` README row and the README mode table get the same correction.
The config description and the mode table also state that Turbo's early coder
re-dispatch applies only to a non-Tier-3 task whose planned `files_touched`
are known and non-empty.

The phase-wrap skill said "Turbo mode skips all gates automatically". Turbo
makes `phase_complete` bypass the completion-verify, drift-verifier,
hallucination-guard, mutation-gate, phase-council and todo-gate checks, not
every gate: it does not skip the final-review, final-council, full-auto or
architecture-supervisor gates (each still fires only under its own enable and
trigger conditions). The skill now says so, both in its gate-evidence note and
in the drift, hallucination and phase-council steps, which now skip under Turbo
as the mutation step already did.

## Truncated replies fail closed (notes from #3172, not published until now)

These notes describe a fix that shipped in v7.192.3 but were left out of every
release since.

When a reply is cut off by the output limit, the host records it on the
assistant message, either as `info.error` set to `MessageOutputLengthError` or
as `finish: "length"` with the partial text and no `info.error` (the shape a
static check of the OpenCode 1.18.35 binary points to; not yet confirmed
against a live truncated reply). The shared provider-error reader
(`readProviderMessageError`) reports both, the `finish` shape since v7.192.4.
Every consumer that reads a reply through it treats a cut-off reply as a failed
dispatch: the full-auto oversight critic and intercept, the curator and
skill-improver delegates, the ephemeral agent dispatcher, the mutation-test
generator and the Lean integration critic. A reply truncated right after
`VERDICT: APPROVED` therefore no longer reads as an approval. A
`content-filter` finish is handled the same way.

Only the Lean lane runner exempts a cut-off or content-filtered reply, so a
lane keeps the behavior it had before it started reading `info.error`.

The v7.192.4 notes already describe the `finish` half; this section is the
original #3172 change those notes build on.

On OpenCode 2 the `finish` shape fails closed too, now that the v2 adapter
passes `finish` through; the separate OpenCode 2 note (#3634) gives the exact
conditions.

## Correction to the v7.192.3 Lean runner notes

The v7.192.3 notes say that a rate limit (429), quota (402) or server error
(5xx) fails over to the lane's next fallback model, and that an authentication
or configuration refusal (403, `ProviderAuthError`) fails the lane without
failing over. The exact rule: a lane fails over when the formatted provider
error reads as transient. That covers, for example, 429 and 402, quota and
rate-limit messages, timeouts, network errors, an unavailable model, and the
statuses 408, 500, 502, 503, 504 and 529. A lane dispatch timeout and a refused
lane scope handshake never fail over. Other 5xx statuses (501, 505) fail over
only when their message reads as transient, for example "server error" or
"overloaded". An authentication or configuration refusal (403,
`ProviderAuthError`) fails the lane without failing over, unless its message
text itself reads as transient (tracked in #3165 G.6).

## Tests

#3171 added a complement regression suite for the Lean runner's provider-error
handling (`tests/unit/turbo/lean/runner-provider-message-error-3162.test.ts`).
It is test-only; its own fragment is folded into this one.

## Migration

None.

# Ancestor write-denial messages no longer disclose raw profile paths

## What changed

- Both ancestor denial arms in `checkWriteTargetForSymlink`
  (`src/hooks/guardrails/file-authority.ts`) — the lstat-failure arm and the
  symlink/junction arm — now render the resolved ancestor path through the
  same bounded-and-redacted contract that issue #3587 established for the
  four main denial doors: home/profile prefix folded via `redactPath`
  (`src/scope/path-identity.ts`), control and bidi characters neutralized,
  and length capped at 320 chars via `sanitizeDiagnosticText`. For absolute
  paths this is byte-identical to `renderDenialTarget`
  (`src/hooks/guardrails/tool-before.ts`); it is inlined in file-authority
  because importing the helper back from tool-before would create an import
  cycle.
- The lstat arm's error detail previously interpolated `String(err)` raw and
  unbounded. A system error string embeds the lstat operand verbatim
  (e.g. `statx '<path>'`), so on a workspace under the user profile the
  message leaked the profile prefix twice. The fix folds every occurrence of
  the raw ancestor inside the error text into its already-redacted render
  before sanitizing and capping the detail at 160 chars.
- The denial DECISION logic is untouched: ENOENT still walks through,
  any other lstat error still fails closed, and a symlink/junction ancestor
  still refuses the write.
- New `_internals` seam in file-authority (`lstatSync`) so suites can inject
  lstat outcomes for workspaces that do not exist on the host, and a new
  regression suite
  `tests/unit/hooks/guardrails-ancestor-denial-redaction-3606.test.ts`. Its
  unit legs use a fabricated `/home/<name>` workspace and run on every host.
  Its end-to-end write-tool leg uses a real symlink directory and reports an
  explicit skip on hosts that cannot create symlinks.

## Why

Issue #3606 (follow-up from PR #3592): the two ancestor arms of
`checkWriteTargetForSymlink` interpolated the workspace-resolved ancestor path
raw into operator-facing `WRITE BLOCKED` messages. When the workspace sits
under the user profile, that disclosed the runtime profile prefix verbatim —
the same disclosure class #3587 closed for the four main denial doors — and
the lstat arm additionally embedded an unbounded system-error string.

## Migration steps

None required. Denials fire identically; only the message text changes.
Tooling that matches the literal message shapes (`WRITE BLOCKED: lstat
failed on …`, `… is a symlink/junction …`) keeps matching; anything that
parses the quoted path slot must now expect a `~`-folded, ≤320-char render.
`ShellWriteBlockedError.writeTarget` keeps the exact value in memory. The
audit row's `path` and `reason` fields are written through the audit writer's
own redaction, as before.

## Known caveats

- The audit row's `reason` field carries the same bounded reason string. The
  audit writer already redacts `path` and `reason` on serialization
  (`src/hooks/guardrails/audit-log.ts`), so this change's on-disk delta for the
  audit row is the 320/160-char bounds and the ancestor fold in the reason text.
- The same `checkWriteTargetForSymlink` text also reaches `declare_scope`
  `errors[]`, the `prepare_pr_feedback_scope` failure message, and
  `scope-validate` (boolean result only). On those surfaces the quoted path is
  now a `~`-folded render, not a copyable absolute path.
- The sibling ancestor walk guarding recursive deletes
  (`dcLstatAncestorWalk` in `src/hooks/guardrails/destructive-command.ts`)
  still renders raw ancestors; that surface belongs to the #3616 residual
  cluster and is intentionally out of scope here.
- The new tests live in a dedicated file rather than the #3587 suite because
  that suite sits at 480 lines and the FR-006 cap ratchet fails any modified
  test file that grows past 500.
- The planted-link denial in the linked-worktree containment path
  (`findPlantedLinkBelow` in `src/hooks/guardrails/file-authority.ts`) renders
  its quoted symlink path through the same redacted, 320-char-bounded contract.
  This is a source-verified change; no test pins its rendering on this release.
- Pre-existing residual, not changed here: `redactPath` does not fold the
  extended-length `\\?\` prefix, WSL `/mnt/c/Users/<name>`, `/var/home/<name>`,
  or `/export/home/<name>`. A username in those shapes can still appear in
  `WRITE BLOCKED` text. Recorded in the PR's considered-not-filed table.

# Fix: Turbo checks no longer leak across sessions; dead Stage B bypass removed

## What

`checkReviewerGate` (`src/tools/update-task-status.ts`) still carried two
branches that let Turbo Mode and Lean Turbo skip Stage B: a Lean Turbo branch
for a task in a completed lane, and a Turbo branch for a task whose
`files_touched` contain no Tier 3 path. They ran only when the caller passed
neither a session id nor a fallback directory, and then checked Turbo with no
session, which means "any session has Turbo on". Completion never relied on
them: the locked check under the plan lock always passes a fallback directory
and applies the same Stage B rule in every mode.

They did have one visible effect. Without a session id, the pre-lock check
passed no fallback directory, so it could admit a completion that the locked
check then refused with a `TASK_COMPLETION_CAS_MISMATCH` error instead of the
normal "Gate check failed: required QA gates not yet satisfied" result.

- Both branches are removed, together with
  `src/turbo/lean/task-completion.ts` (`verifyLeanTurboTaskCompletion`), which
  had no other caller.
- The pre-lock check now passes the same fallback directory as the locked
  check, so both reach the same decision. A refused completion without a
  session id now reports the normal gate failure with the exact-task reason
  (for example "Task X has no exact-task QA evidence. Delegate the required
  Stage B agents, then retry completion." when there is no evidence at all).
- The reviewer-gate telemetry reason codes `lean_turbo_completed_lane` and
  `standard_turbo_non_tier3` are no longer emitted and are removed from
  `ReviewerGateReasonCode`. Older `telemetry.jsonl` rows may still contain
  them.

`completion_verify` had the same "any session" leak. Its Turbo bypass called
`hasActiveTurboMode` with no session id, and the `phase_complete` completion
gate never passed one, so one session's `/swarm turbo` let another session's
`phase_complete` skip completion verification. Now:

- The bypass applies only to an explicit session that has Turbo on.
- The `phase_complete` gate passes its session id.
- The `completion_verify` tool takes the session from the plugin context
  before a session id supplied in its arguments.

Turbo Mode still skips the Stage A re-delegation block for non-Tier-3 tasks
(`src/hooks/delegation-gate.ts`); that is unchanged. `hasActiveTurboMode()`
without a session id still means "any session" for `/swarm status` and
`epic start`, which use it on purpose, and for the system-prompt Turbo banner
when a hook input carries no session id (advisory text only). Neither Stage B
nor completion verification reaches it any more.

## Migration

None. Stage B was already required at completion in every mode.

`completion_verify` now runs the verification whenever the CALLING session
does not have Turbo on, even while another session does. That includes a call
with no session id, and a call from an agent session (for example
`critic_oversight`) while only the architect's session has Turbo on: such calls
were previously bypassed and can now block.

## Known caveat

A completion call without a session id that previously failed under the plan
lock with `TASK_COMPLETION_CAS_MISMATCH` now fails earlier with the normal
gate message. Anything that matched on that error text for this case should
match the gate message instead.

# Trim `subagent_type` identity derivations (route role + incremental-verify trigger gate)

## What changed

- `src/index.ts` (route registration in the `tool.execute.before` Task handler):
  the pending model route's `role` is now derived via
  `stripKnownSwarmPrefix(toolBeforeArgs.subagent_type.trim())` — the same
  one-token trim the sibling `swarmID` derivation already applies — instead of
  feeding the raw `subagent_type` spelling to the suffix extractor.
- `src/hooks/incremental-verify.ts` (trigger gate): the dispatched
  `subagent_type` is trimmed once at extraction, and all three trigger-match
  forms (canonical role, raw name, base-compat prefix-stripped form) derive
  from the trimmed spelling.
- New regression legs:
  - `tests/unit/index-task-model-routing-v2-apply-gate.test.ts`
    `padded-role-parity (#3625)` — dispatches `' Case_coder '` and asserts the
    stored route role equals `resolveTaskRouteModelChain`'s trimmed derivation
    (`coder`), and end-to-end that the chat boundary matches the route so the
    advanced fallback lands instead of a `mismatch` no-op.
  - `tests/unit/hooks/incremental-verify-negative-trigger.test.ts`
    `padded-trigger (#3625)` — whitespace-padded dispatches match configured
    `triggerAgents` entries through the canonical, raw-name, and base-compat
    forms, and a padded suffix near-miss (`' Case_test_engineer '` against
    `engineer`) stays gated.

- `src/sandbox/linux/bubblewrap-executor.ts` (`buildBwrapArgs`): when the
  temp root is neither equal to nor inside any scope or read-only root (the
  production case: temp is always `/tmp`), the size-capped `--tmpfs <temp>`
  is now the FIRST mount, ahead of the read-only roots, scope binds,
  `--dev /dev`, and the system binds. When temp equals or lies inside a
  scope or read-only root, the previous order is kept (tmpfs after the
  binds) so temp stays a private tmpfs. New suite
  `tests/unit/sandbox/bwrap-tmpfs-mount-order.test.ts` pins both branches.
- `tests/unit/sandbox/sandbox-integration.test.ts`: AC-008 now bounds the
  absolute per-call overhead (< 50 ms) instead of a relative < 10% (a fixed
  few-ms namespace setup measured 206% of a bare bash spawn on
  ubuntu-26.04), and AC-010's broad scope is the user's home directory
  instead of root-owned `/home`, which the runner user cannot write even
  outside the sandbox.

## Why (sandbox mount order)

bwrap mounts in argument order. The tmpfs was emitted after the scope
`--bind`s, so a scope under `/tmp` (the default temp root, and where an
`os.tmpdir()` workspace lives) was hidden by the tmpfs: in-scope writes
landed in the sandbox-only tmpfs and never reached the host. GitHub's
`ubuntu-latest` moved from 24.04 (no `bwrap` installed, so the Linux sandbox
integration tests returned early) to 26.04 (bubblewrap 0.11.1, working user
namespaces), which made those tests run for real for the first time. A
diagnostic run on ubuntu-26.04 confirmed that the old order loses the
in-scope write and that tmpfs-first writes it to the host.

Known limit (fails closed): if temp is inside one mount while a scope sits
under temp, that scope stays hidden; writes are lost and nothing on the host
is widened. It occurs only when the workspace root or a writable scope is
exactly `/tmp` (or a scope is `/`); writes under `/tmp` are then lost, as
they already were before this change.

## Why

Follow-up from PR #3617 (issue #3625): two sites still fed the raw
`subagent_type` spelling into suffix-based identity extraction, so a
whitespace-padded dispatched name (e.g. `' Case_coder '`) derived a different
identity than the same dispatch trimmed. `getCanonicalAgentRole`'s suffix scan
cannot recognize a real `_<role>` ending through surrounding whitespace, so:

- the stored `route.role` kept the padded spelling while
  `resolveTaskRouteModelChain` derives the bare role, making
  `resolveTaskChatModelOverride` return `mismatch` at the chat boundary (the
  route's fallback never applied); and
- a `subagent_type` with trailing whitespace matched no unpadded configured `triggerAgents` entry on any
  of the three incremental-verify trigger arms.

Both paths are unreachable with today's host (the v1 and v2 hosts resolve the
Task subagent by exact lookup before any child session exists, with no trim
anywhere), so this is belt-and-braces parity with the documented contract —
the derivations now match "the same identity the chat boundary reports" and
survive a future host that tolerates whitespace or aliases.

## Migration steps

No config key, schema, or public tool surface changed. One behavior change is
user-visible: a `triggerAgents` entry that is itself spelled with surrounding
whitespace (for example `' coder '`) matched an identically padded dispatch
before this change and no longer matches, because configured entries are not
trimmed. Remove the surrounding whitespace from any such entry.

## Known caveats

- Unchanged by design (out of scope per the issue): PRR-008 duplicate-advance
  hardening and the partial-v2-host advisory edge remain RECORD items in the
  PR #3617 body; route-registration `swarmID` was already trimmed by PR #3617.
- The stored route `agentName` still receives the raw dispatched string;
  `normalizeRoute` (`src/models/task-model-routing.ts`) trims it on write, so
  behavior is unchanged there.
- A padded dispatch whose fallback chain is exhausted now fails closed with
  `MODEL_FALLBACK_EXHAUSTED` at the chat boundary. Before this change the role
  mismatch made the boundary ignore the route. An
  unpadded dispatch with an exhausted chain already behaved this way. The host
  does not currently produce padded names.
- A malformed leading-whitespace name such as `'  _coder'` no longer matches
  trigger `coder`, because the trimmed `_coder` has no swarm prefix.
- A whitespace-only `subagent_type` now trims to `''` and can match a
  trigger entry that is itself `''`. Only an empty-string config entry can
  produce this.

## CI: coverage-aggregator diagnostics discriminate their failure layer; macOS crash fixture terminates the process group (#3250, #2738)

- The merge-queue `coverage` aggregator's fail-closed error now names the
  upstream `quality` job result (via a direct `needs` edge and an env var),
  so a cascade failure identifies the layer that caused it instead of only
  the shard-matrix verdict.
- The aggregator's final `Upload coverage report` step now runs only when the
  merge step actually executed (`steps.merge-coverage.outcome != 'skipped'`).
  Previously the unconditional `if: always()` upload warned
  "No files were found with the provided path: coverage/lcov.info" on every
  failed aggregation — a misleading headline that misattributed upstream
  failures (forensics: 11 of 14 signature runs were quality-job
  pending-fragment failures, 3 were genuine shard test failures; no run ever
  lost a file) to a missing file. The warning firing again now means a real
  merge-ran-but-no-file event. Reports from threshold-failure merges are
  still uploaded — they are the diagnostic.
- The repository-validation crash fixture now signals its own process group
  (`kill -KILL 0`) instead of a parent-pid target that depended on Bun's
  worker topology. On macos-latest / Bun 1.3.13 the old target missed the
  spawned `bun test` process, which observed a worker failure, exited 0, and
  made the harness record `passed` (9/9 deterministic CI failures). The
  crash arm fails loudly on every termination miss, with an explicit
  "child survived the delivered signal" diagnostic for the recorded
  exit-0 miss shape (the #2738 signature: harness recorded passed on a
  surviving child).
- The macOS quarantine entry for
  `tests/unit/scripts/ci/repository-validation-real-process-2675.test.ts` is
  retired (its stated criterion: the signal-fixture root fix lands and the
  file passes on macos-latest); the file runs again on macOS CI. A new
  durable contract suite pins the group-kill target, the survival
  diagnostic, the ledger retirement, and the `detached: true` spawn that
  makes the group kill safe.

## What

- Linux sandbox: the `/lib64` read-only bind is now host-conditional in BOTH
  bwrap arg constructors — the capability probe (`probeLinuxBehavior`) and
  the production executor (`buildBwrapArgs`, including the namespace smoke
  args). On a host without `/lib64` (usr-merged or non-multilib images, e.g.
  Alpine/musl) wraps and capability probes now work instead of failing
  wholesale; on hosts with `/lib64` the arg list is byte-identical to before.
- Sandbox probes: a failure during probe temp setup (mkdtemp ENOSPC/EACCES,
  mkdir EACCES, profile build error) now returns a bounded weak probe result
  with the temp root cleaned up, instead of escaping as an unhandled throw
  that leaked the probe temp root (both the Linux and macOS behavioral
  probes).
- CI tooling: new `scripts/capture-required-check-evidence.ts` — the
  repeatable refresh path for `docs/ci/required-check-evidence.json`
  (`--self-test` offline validation reusing the validator's own evaluator,
  `--dry-run`, `--output <path>`, default write) with a runbook
  (`docs/ci/required-check-evidence-capture.md`) naming the exact commands,
  owner surface, and cadence (re-capture at least every three weeks, before
  each 30-day `MAX_EVIDENCE_AGE_MS` wall; the wall twice blocked every open
  PR's unit matrix until re-attested by hand).

## Why

Closes #3332 (probe/executor `/lib64` tolerance + bounded setup failures)
and closes #3653 AC2 (the 30-day evidence wall had no in-repo regeneration
path). #3647 is verified already fixed on main by PR #3639's bwrap
mount-order change (evidence recorded on the issue; this PR keeps its
regression guard green while editing the same file family).

## Tests

- tests/unit/sandbox/bwrap-executor-lib64-absent.test.ts /
  bwrap-executor-lib64-present.test.ts — production wrap args per host shape
  (module-load deterministic, one leg per file).
- tests/unit/sandbox/capability-probe-lib64.test.ts — probe args per-call
  host-conditional bind.
- tests/unit/sandbox/capability-probe-setup-failure.test.ts — bounded setup
  failures on both platform branches (no throw, weak dimensions, reasons,
  temp-root cleanup; mkdtemp-failure and profile-build legs included).
- tests/unit/scripts/capture-required-check-evidence.test.ts — validator
  -accepted generated artifact, refusal semantics (missing required context,
  local/captured divergence), self-test PASS/FAIL branches.
- Updated bwrap-namespace-smoke.test.ts and linux.test.ts to derive the
  expected `/lib64` bind from host availability (non-circular).

## Known limitation

The capture script's live mode requires `gh` authentication and a local
checkout whose workflow files match the selected capture SHA (the script
refuses on divergence instead of guessing).
