# `fix(gate)`: an infrastructure-only pre_check failure no longer burns the task's retry budget

## Summary

- The retry circuit counted EVERY `stage_a_failed` transition toward a task's bounded retry contingency (3), regardless of what the failure said about the code under gate. For infrastructure failures that is a guaranteed wrongful escalation: observed live in the consumer-project loop (task 2.18, 2026-11-27), the `sast_scan` evidence bundle had crossed its byte cap, so EVERY further gate run's evidence save threw, each run recorded `stage_a_failed`, and the task burned its full retry contingency on infrastructure alone — `TASK_RETRY_USER_ESCALATION_REQUIRED` with a user-authorized repair demanded, while no coder attempt had ever failed on content (the 2.16 sibling wedge, a scope-prep refusal self-escalating the same circuit, was fixed separately; this closes the general class).
- `decodePreCheckResult` now classifies what a FAILING batch says about the code: the fail verdict carries a `cause` — `'infrastructure'` ONLY when every failing hard-gate signal is positively an execution/persistence error (a gate wrapper error, a scan-process error with zero findings, the evidence-save throw, a malformed batch input) and no gate shows findings, an error-free fail verdict, a baseline mismatch, truncation, or a contradictory shape. Everything unprovable is `'content'` — conservative by construction, so the retry budget may only be spared when the failure is PROVEN to say nothing about the code. The producer contract drives the classification: only `secretscan` and `sast_scan` can fail the batch, and the producer marks execution failures with BOTH a fail verdict and an error — the verdict alone is ambiguous and never proves content.
- Both Stage-A failure writers (the guardrails `tool.after` hook and the tool-side self-report) apply the same writer-level rule the scope-prep refusal fix established: an infrastructure-classified failure writes NO `stage_a_failed` transition at all. `retryCount`, `retryHistory`, `lastOutcome`, and the workflow state stay untouched (the durable stock says nothing new about the task); the architect instead gets a bounded `pre_check_infra_failed` route event in the core event store plus an always-visible advisory stating that the retry budget is untouched and the remediation is to repair the environment and re-run the gate — not to re-dispatch a coder. A content failure still records `stage_a_failed` exactly as before, and mixed batches (an infra error on one gate, real findings on the other) classify as content.

## User-facing changes

- A swarm whose gate environment degrades (a missing scanner binary, a scan-process crash, an evidence-bundle write failure) no longer escalates its tasks to the retry user-escalation wall. The task stays in its pre-failure workflow state with a clean retry budget; once the environment is repaired, the next `pre_check_batch` run proceeds normally — no `/swarm recover`, no re-dispatch, no user authorization needed.
- The new route appears in `.swarm/events.jsonl` as `stage_a_gate_route` with `route: "pre_check_infra_failed"`, and `docs/configuration.md`'s route table documents it.

## Migration notes

None for consumers. The `PreCheckVerdict` fail variant gains a required `cause: 'content' | 'infrastructure'` field (built only by `decodePreCheckResult`; consumers reading `.cause` should treat unknown values as content). The Stage A route vocabulary gains `pre_check_infra_failed` (closed-vocabulary ratchet and docs-parity tests updated). Recorded-by-history: already-burned retry counts from past infrastructure failures are NOT retroactively healed — the durable event chain carries no cause marker, so old `stage_a_failed` events keep counting (conservative default).

## Discovery context

Found in the consumer-project loop (task 2.18, 2026-11-27; the architect's own diagnosis: "Infrastruktur-Blockaden wurden als erschöpftes Retry-Kontingent gewertet, obwohl kein Coder-Versuch inhaltlich scheiterte"). The wedge chain: evidence-bundle size throw → `pre_check_batch` execution_error → `stage_a_failed` ×N → retry budget exhausted → `TASK_RETRY_USER_ESCALATION_REQUIRED`. Pinned by `tests/unit/hooks/pre-check-result-infra-cause.test.ts` (15 decoder classifications: the 2.18 persist-error shape, wrapper and scan-process errors, and malformed input are infrastructure; findings, error-free fail verdicts, baseline failures, error-with-findings mixes, truncation, the degraded-shape-without-flag, and no-signal contradictions are content) and `tests/unit/hooks/guardrails-stage-a-infra-no-retry.test.ts` (5 writer tests: no transition with state/retry/lastOutcome untouched, route event + advisory visibility, the content-failure falsification recording `stage_a_failed` exactly as before, five repeated infra failures neither spiraling the counter nor wedging the state, and content-after-infra counting from zero) plus `tests/unit/tools/stage-a-self-report.test.ts` (2 new tool-side writer tests: no transition + infra route, and the repeated-infra no-spiral).
