# fix(council): resolve stale_verdict_detected deadlock on round 2+ submissions

## What changed

- Fixed a critical deadlock in `submit_council_verdicts` and
  `submit_phase_council_verdicts` where ALL council member verdicts were rejected
  as `stale_verdict_detected` at round 2+, even when the council members were
  freshly dispatched and `collect_lane_results` reported all lanes as fresh
  (`stale: 0, all_settled: true`).
- The staleness check previously defaulted an omitted `verdictRound` field to `1`,
  which is always `< roundNumber` at round 2+. Since no production code path
  stamps `verdictRound` onto collected verdicts (council member agents never emit
  it; the architect prompt does not list it; `collect_lane_results` has no concept
  of council rounds), this made every round-2+ submission permanently deadlocked.
- The default is now the CURRENT round (`roundNumber`), so fresh re-dispatched
  verdicts that omit `verdictRound` are correctly accepted as fresh. Explicit
  stale values (e.g. `verdictRound: 1` carried into `roundNumber: 2`) are still
  caught and rejected, preserving the anti-replay guarantee for the case it was
  designed for.

## Why

This was a regression-introduced deadlock (v7.52.0). The prior change
(`council-quorum-review-followups.md`) intended to prevent stale-verdict bypass
but the `?? 1` default made the guard impossible to satisfy in production,
turning `council_mode` into an unrecoverable gate impasse: `update_task_status`
could not advance because no council evidence was ever written (the tool
returned `success: false` before reaching the evidence-write path), and the
ratchet prevented disabling `council_mode`.

## Migration steps

No user action required. Any project that disabled `council_mode` as a
workaround can re-enable it.

## Breaking changes

None. The change narrows an over-strict check; round-1 behavior is unchanged
and explicit-stale detection is preserved.

## Known caveats

If an architect explicitly carries forward a prior-round verdict by setting
`verdictRound` to an older value, it is still rejected. The only behavioral
change is for verdicts that omit the field entirely — these are now treated as
fresh (belonging to the current round) rather than round-1. This matches the
field's documented intent ("Optional source round for freshness checks on
resubmission") and the architect's prompt-enforced obligation to re-dispatch
members for each round.
