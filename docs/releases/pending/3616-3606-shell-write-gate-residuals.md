## Security (write-gate fail-open closures)

- **Ambient shell-state keys** (#3616 item 1): in-command assignments naming `BASH_ENV`, `ENV`, or `BASH_FUNC_*` (unquoted spellings incl. `%%`-suffixed keys; a key word inside a QUOTED argument — e.g. a leading-quote form like `"BASH_ENV=x"` — is not matched by the textual scan) now deny the whole command before parsing. Startup-file values need not look command-bearing and imported functions execute later, so all key-naming assignments are refused regardless of value shape. Residual (documented, not fixable at this layer): the host's outer bash inherits the OpenCode process environment before any plugin hook runs.
- **GNU long-option abbreviations** (item 3): `rm --rec src` / `rm --f src` are now classified recursive/forced exactly like their full spellings (unambiguous-prefix matching against GNU rm's real option universe). Previously `rm --rec src` admitted where `rm -rf src` denied.
- **Word-position `$(...)` writes** (item 4): writes inside command substitutions in For word lists, command suffixes, assignment prefixes, and Case subjects are now detected and resolved at their tracked walk state (parameter-expansion DEFAULT/ALTERNATIVE bodies like `${x:-$(...)}` are not scanned — pre-existing) (`for i in $(echo x > ../esc); do :; done` previously reported zero writes).
- **`sudo -D` behind launchers** (item 5): `time sudo -D /etc tee src/ok.txt`, `bash -c "sudo -D /etc tee …"`, and their launcher+shell COMPOSITION (`time bash -c "sudo -D …"`, `env -i bash -c …`) now reach the chdir rewrite — the launcher peel is shared grammar, the shell `-c` payload recursion fires behind a launcher prefix too, and the nested rewrite fallback routes through the same shell-payload helper — so the write resolves under DIR instead of the ambient cwd. `env` itself is never peeled across a flag that could change the directory or re-split the command (`-C`, `-S`, `--chdir`, `--split-string`, clusters, unknown flags), so `env -C .. sh -c …` keeps its chdir.
- **`sudo -i` relative writes** (item 6): a write-bearing tail under `sudo -i`/`--login` withdraws fail-closed (sudo chdirs to the target user's home, which is unknowable statically). The withdrawal fires behind a launcher prefix (`time sudo -i …`) and for the interactive spelling too (`sudo -i sh …` — arg-taking sudo options such as `--user root` are skipped when locating the command word), after the `--` option terminator (`sudo -i -- tee src/ok`, where only option parsing ended, not the login chdir), and for a nested GNU `time -o FILE` tail (the relative report file is a write under the login home); a shell `-c` payload under the login counts as write-bearing wholesale, so a compound payload (`cd src && tee ok`) can no longer hide behind a non-write first token; a payload with no write at all still admits when no other rule fires (`sh -c "sudo -i sh -c 'echo hi'"` — the wrapped no-write control; the bare `sudo -i sh -c 'echo hi'` is separately denied by the pre-existing interactive-shell refuse). `sudo -s` (cwd kept), no-write tails (`sudo -i make build`), and absolute targets are unchanged.
- **`env` between launchers** (item 7): an interposed `env` (assignments, `-i`, `-u NAME`, `--`, and other chdir-free flags) is stepped over by the launcher hop filter, so `nice env sudo -i …` and `nice env time -o ../x true` are judged like their env-free twins.
- **`env`'s `-` alias and split payloads**: a lone `-` is env's obsolete `-i` spelling — an option, never the command word — so the words after it run as the command (`env -u X - sh -c …`, `env - time -o FILE …`, `env -S '-' CMD…`, `env -S '' CMD…` are all judged like their dash-free twins now, previously unanalyzed). `-S`/`--split-string` hands its payload to env as argv for every spelling (exact, abbreviated, glued cluster): a `-C ..` inside the payload (or a chdir before `-S`) moves the judged landing exactly as env does; the split is an argv splice — an empty/option-only payload leaves the following words as the command, words after a payload command are that command's arguments; a payload env would expand at run time (or one carrying a literal redirect-operator word) fails closed when words follow; a payload `>` stays a literal argument, as env passes it. A bare `time` after the dash is re-emitted quoted so the GNU binary grammar analyzes its payload while the launcher `-o` write is still detected.
- **`pushd .`** (item 8): pushes the duplicate directory-stack entry exactly as bash; the following `popd` no longer removes the wrong entry and later writes resolve at bash's real landing.
- **Symlink-lexical `rm link/../x`** (item 9): `resolvePath` now walks components left-to-right consulting `lstat` — a symlink/junction component is replaced by its target and the target's own components are walked first (realpath order, so multi-hop chains `link1 → link2 → elsewhere` resolve fully) before `..` collapses, so `link/../src/x` (link → another tree) resolves through the real tree instead of being admitted as in-scope `src/x`. Non-ENOENT lstat/readlink failures, and link chains longer than 40 hops (cycles), fail closed with an "unverifiable path" reason for relative operands and on Windows. On Windows a `..` that crosses a junction is WRITER-DEPENDENT — native binaries collapse `..` lexically while bash walks physically — so the gate denies fail-closed when the two landings diverge (F-17, PR #3651 review); an absolute POSIX operand falls back to its lexical form there (the kernel's own 40-hop ELOOP bound stops such a chain before any write).
- **macOS `.git` case-folding** (item 12): the destructive gate's protected-component compare now routes through a platform seam (`dcProtectedComponentEqualsForPlatform`) that case-folds on darwin as well as win32, so `rm -rf .GIT` is protected on macOS's default case-insensitive filesystems (a case-sensitive darwin volume only over-denies). Linux stays exact.

## Behavior change (owner decision 2026-11-09)

- **Flagged rm under `block_destructive_commands: false`** (item 10): destructive rm operands (recursive/forced, any flag spelling) are now emitted as ordinary write targets judged by the scope layer instead of being owned by the disabled destructive arm. Configurations that relied on deleting outside the declared scope with the destructive policy off will start getting denials — a flag can no longer make a delete *less* checked.

## Denial messages & diagnostics

- **Class-accurate deny reasons** (item 15): the dynamic-path deny names its true cause — tilde expansion, unresolved loop landing, withdrawn directory context (popd/`cd -`), unresolvable wrapper chdir (`sudo -D`), unverifiable path, or dynamic text — instead of the single misleading "shell variable or command substitution" label.
- **Bounded, sanitized diagnostics** (items 13-14): all seven destructive-rm deny sites (plus the junction/symlink-creation sites) route through the canonical sanitizer — control characters and the bidi marks U+061C/U+200E/U+200F are neutralized, truncation is code-point-safe (never splits a surrogate pair), and the unexpanded-variable site caps the rendered target at 160 chars.
- **Ancestor denials redacted** (#3606): both `checkWriteTargetForSymlink` arms (lstat-failed, symlink/junction) render the ancestor home-redacted within a whole-message 320-char bound, and the error detail renders the error CODE only — no raw profile-prefixed paths or unbounded error strings reach operator-facing messages. Residual (F-21, PR #3651 review): the home fold matches literal `/home`, `/Users`, and drive `Users`/`home` roots — profile shapes like `/srv/nfs/alice/...`, `/var/home/alice/...`, `/root/...`, Samba `homes` shares, and the Windows extended-length form (`\\?\` + drive path) still render with the account segment.

## Explain

- **Coder explain without `--scope`** (item 2): renders `block` with a `scope_unevaluated` firing rule instead of an unqualified "allow: no rule matched" for commands the live gate denies under the coder's active scope binding. Architect and other-role paths are unchanged.

## Performance

- **Oversized-word sentinel** (item 11): a whitespace-delimited word longer than 4096 chars denies before parsing (the parse itself dominated; a 40k unclosed-brace `curl -o` operand measured ~0.5-1.5 s per walk), and the quadratic brace regex is capped at every call site, not just the For path.

## Not in this change

- **Item 16** (post-exempt-loop landing adoption): scoped out by owner decision — the loop landing is not statically knowable under the issue's own item-1 ambient-shadowing finding; PR #3615's conservative over-deny is preserved bit-for-bit and pinned as a PRESERVING check. #3616 remains open pending AC16 re-specification.

The merge keeps THIS change's `renderAncestorDenial` mechanism (a single composer for both ancestor arms — lstat-failed and symlink/junction — with a code-only error detail — never `String(err)` — and the F-22 ancestor-slot cap at 200 so the class text survives the 320 compose) and supersedes #3637's inline arms; the ancestor-slot bound differs from #3637's 320-slot pins accordingly. #3637's planted-link redaction (de9d15706) is retained bit-for-bit; its now-superseded release fragment is removed. Known bounds: `--v`/`--ve`/`--ver` (ambiguous between `--verbose`/`--version`) fall through as unknown tokens — GNU rejects ambiguous abbreviations before deletion, so nothing deletes either way. The ambient-key scan is textual, so a non-assignment word that spells a key assignment (e.g. `echo ENV=x > src/a`) is also denied — a deliberate over-deny in the safe direction. Also deny-direction and pre-existing: the D6 write-vector heuristic treats any `>`-bearing word under `sudo -i` as a write vector, and the #3588 interactive-shell refuse denies tails whose rejoin would parse as shell structure — both can over-deny unusual shapes in the safe direction. Pre-existing and unchanged here: an operand with no `..` is still resolved lexically, so a NEW file created through an in-scope directory link (`echo x > src/leaf/new` with `src/leaf` → outside the workspace) is admitted by the shell write gate — existing-file writes and deletes through such a link are already denied, and the full fix needs the scope root and the target canonicalized together. Also pre-existing (found in review): a PARENTHESIZED login sudo (`( sudo -i sh -c 'cd src && rm -rf x' )`) escapes the withdrawal — the wrapper matcher requires `sudo`/`env` as the segment head, so a leading `(` defeats both the chdir wrapper match and the launcher-uncertainty scan. Also pre-existing: sudo's `--chroot`/`-R` root is not modeled as a chdir — a write under it is judged at the invoking cwd while it lands inside the chroot (exact and abbreviated spellings alike, before and after this change). Also pre-existing and dash-orthogonal (plain `time -o in-scope sh -c …` admits the same way): the GNU time `-o` model reports the `-o` target but does not analyze the timed payload, so an in-scope `-o` can mask the timed command's outside write. Also deny-direction: a `cd` inside a payload wrapped by the quoted-`time` rewrite (`env - time sh -c "cd src && echo x > ok.txt"`) over-denies — the rewrite drops the `cd` landing state, so the write is judged at the session root rather than `src/`; the same class as the succeed-mode cd-landing surface reserved for the AC16 re-specification. These eight bounds, the AC16 re-specification, the ambient host-shell residual (item 1), and a future executor-level env scrub are collected in a collated follow-up issue filed at this change's closeout and linked from its pull request.
