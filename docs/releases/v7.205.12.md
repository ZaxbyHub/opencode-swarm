# `fix(workflow)`: a Stage-B re-dispatch can actually reclaim its route slot — the `reviewer_run` unwedging path works

## Summary

- The `test-engineer-exempt` wedge fix (re-dispatch the reviewer; the fresh exemption-aware receipt completes and the durable state advances) did not work in the field: the fresh reviewer dispatch's background completion was **terminally rejected** (`ingestion outcome: rejected`, advisory "reviewer task 1.8 ingestion failed") and the durable workflow stayed at `reviewer_run`, so `update_task_status` kept reporting `Missing gates: []` / `Contradictions: [all required proof exists but workflow state is reviewer_run]`.
- Root cause: route slots are single-assignment per dispatch. The wedged task's prior reviewer settlement had already appended a durable route binding for the identity (`1.8:reviewer:1` bound to the OLD `callId`/`childSessionId`, generation 1). When the fresh re-dispatch completed:
  1. `resolveBackgroundStageBRoute` found every reviewer slot occupied by the OLD dispatch (the in-memory evidence was lost at the host restart, so the durable requirements chain was consulted) → no binding for the fresh dispatch → the admission consult failed with `ROUTE_RECEIPT_DISPATCH_REQUIRED` → the completion was consumed terminal-negative, never recording evidence and never advancing the state;
  2. even if a binding had been computed, the persisted chain would later read BOTH the old and new rows for the same identity → `ROUTE_RECEIPT_DUPLICATE` on every downstream barrier.
- Fix (four surfaces, one semantic): a Stage-B re-dispatch of the same gate cycle **replaces the obsolete binding's slot** instead of finding it occupied forever —
  1. `resolveBackgroundStageBRoute` (`stage-b-gates.ts`, background completion ingestion): when no free slot exists for the role, a prior binding whose identity is listed in the CURRENT route receipt is reclaimed (same identity/slot, fresh `callId`/`childSessionId`); an exact replay of the same dispatch keeps its existing retry-replacement path; a foreign identity not listed in the current receipt is NOT reclaimed (fail-closed control pinned by test).
  2. `routeEvidenceFromTaskGateRequirements` (`evidence/task-gate-requirements.ts`): the durable chain is reconstructed latest-row-wins per `(role, identity)` — the superseded dispatch's row stays in the append-only audit chain but can no longer read back as a duplicate identity. Distinct identities (sibling slots) remain distinct entries.
  3. `delegation-gate.ts` foreground twin: `bindReviewRouteSlots` applies the same reclamation at dispatch time, the settlement's `prospectiveRouteEvidence` composition supersedes same-role+same-identity entries, and the settlement now falls back to the durable requirements chain when the (process-local) in-memory route evidence is empty — the post-restart shape that previously lost every sibling identity.
  4. `reserveStageBRouteEvidence` (`state.ts`, PR-review follow-up F-001/F-002): a fully-bound reservation now lands the reclamation on the **live** in-memory array too — it replaces the obsolete binding of the same route slot (role + identity), not only the exact dispatch-tuple replay. Previously the fresh same-identity binding was APPENDED next to the obsolete one, so the live array read back as `ROUTE_RECEIPT_DUPLICATE`: the durable workflow advanced while the in-memory advancement and every live-read consumer (`update_task_status`, later settlements) stayed blocked — the same-process variant of the wedge. Sibling slots are preserved, a foreign identity is never rebadged, and a failed durable write restores the slot's LAST VALID binding: reservations on one slot form a chain, each rollback marks its own token failed, and the restore walks past failed tokens — so overlapping reservations converge under any failure order (A replaced by B, then both failing, lands back on the binding that was valid before A, never on a failed dispatch's token), a rollback whose slot a newer settlement already took over is a no-op, and a fully-failed append-rooted chain releases the slot so a retry can reclaim it. A SUCCESSFUL durable write settles the reservation (`settle()` on the rollback handle, invoked by both the background ingestion and the foreground settlement after their `recordGateEvidence` succeeds, and internally by `recordStageBRouteEvidence`): settling prunes the reservation's chain metadata, so a long-lived slot retains no predecessor links from settled re-dispatches, a later predecessor failure still cannot overwrite the settled state (the resolve walk stops at the record-less settled token), and settle-after-rollback is a no-op that cannot un-fail a chain link. Finally, the background completion's post-await re-record of its captured binding is fenced (PR 3919 closeout): a NEWER settlement of the same gate cycle that lands while `collectReviewerReceiptFromTranscript` awaits owns the slot — the stale re-record is skipped (warn-logged) instead of overwriting it, while the completion still records and the advancement decision evaluates the effective settled route. Direct recovery callers (which resolve the binding synchronously against current state) and the foreground settlement (which reserves immediately before its durable write and never re-records after an await) are unchanged.
  5. Final-critic hardening: pending reservations hold capacity and block stale overwrites but never satisfy route completeness; advancement and `update_task_status` merge settled live bindings with durable siblings instead of choosing one incomplete view. Both settlement surfaces pass a lock-scoped `beforeCommit` ownership check, so a superseded reservation cannot publish a late successful row that disagrees with the live winner. Route completeness is then recomputed inside the task evidence lock over durable siblings plus the current fresh binding, preventing two overlapping sibling completions from both persisting stale `routeComplete: false` decisions and leaving the workflow at `reviewer_run` after both receipts settle. Foreground live advancement consumes a fresh post-settlement decision and the current live state, so overlapping completions cannot leave durable `tests_run` beside live `reviewer_run`. A route-receipt publication is fenced by a write-ahead marker (`<task>.receipt-repair-pending`, state `PREPARED`) that is durable before the workflow evidence changes and removed once the receipt is durable. If the receipt append fails, the locked prior evidence is restored (or the newly created file removed) and the typed append error is rethrown; the caller then rolls back its live reservation, and the marker is removed. The coder-settlement commit transaction is the carved-out exception (issue #2525): its receipt-append failure PRESERVES the committed evidence — the settlement replay (`alreadyApplied`) re-publishes the missing receipt from the durable chain tip — and only the write-ahead marker drops so the replay is not fenced; every other event-bearing transition (the route-publication flows and direct transitions) keeps the compensating all-or-nothing behavior above. If that compensation itself fails, the marker is rewritten to record both causes, the caller gets `TaskEvidenceReceiptRollbackError` (keeping the append error as `cause`), and the live reservation is deliberately NOT rolled back: durable evidence may be advanced without its receipt, so later evidence transactions for the task are refused with `TaskEvidenceRepairPendingError` until the split is repaired. A publication interrupted before its marker is rewritten is fenced the same way, because the marker is written first.

## User-facing changes

- A task durably wedged at `reviewer_run` (all required proof recorded, workflow never advanced — the pre-exemption-fix shape) now unwedges through the documented path: after updating the plugin, **re-dispatch the reviewer once more**; the fresh dispatch binds the reviewer identity, records `stage_b_completed` with `routeComplete: true`, the durable workflow advances to `tests_run`, and `update_task_status` admits the completion. No `/swarm recover` needed.
- The same-process re-dispatch now also unwedges the live state: exactly one fresh live route binding remains for the reclaimed slot, the in-memory workflow advances to `tests_run` without a restart, and the foreground settlement twin leaves the same single fresh binding so `update_task_status` completes the task in-process.
- Re-dispatched Stage-B agents after a host restart no longer lose their route slot claim to the pre-restart attempt, in both the background (Task ledger) and foreground (tool-hook settlement) paths. Durable sibling bindings remain visible when the first live binding is restored, and an in-flight reservation alone can no longer make a task appear fully reviewed.
- The exact identity-count guarantee is unchanged: a re-dispatch re-earns the SAME identity with exact fresh bindings (no extra identity is invented, duplicates still fail closed, and MAC-authenticated receipts still define the required identity set).

## Migration notes

No migration is needed for existing durable requirements chains, which are read with the identity-keyed latest-wins reconstruction; the evidence and receipt formats are unchanged. Two new on-disk artifacts exist: the repair marker `<task>.receipt-repair-pending`, written before the evidence write of every event-bearing workflow transition (not only route-receipt publications) and removed when that publication settles; it is left in place if its removal fails, the publication is interrupted, or an evidence write fails without a provably unchanged evidence file (a clean write failure that left the file byte-identical drops it), and while it exists the task refuses every write of its flat evidence file (gate transactions, council evidence writes, and repair rewrites), and the audit log `<task>.receipt-repair-audit.log`, which is appended only by an audited clear. If a split is left behind, the task refuses those writes until an operator clears it with `clearTaskEvidenceRepairMarker(directory, taskId, auditNote)`, which requires a non-empty note and appends it to `<task>.receipt-repair-audit.log`. No CLI command exists for this yet; until one does, an operator clears the marker only after auditing the evidence and receipt by hand.

## Discovery context

Found in the Wirtschaftssimulation loop (session `e07a3a7a-f3f6-49cc-8a03-d67c15158f0b`, task 1.8): after installing the exemption fix and re-dispatching the reviewer, the dispatch-time receipt was correctly allocation-exemption-aware (`reviewers: 1, testEngineers: 0`), but the background completion ledger recorded `ingestion: { state: "consumed", outcome: "rejected" }` while `.swarm/evidence/1.8.json` stayed at `reviewer_run` with `gates.reviewer` still stamped by the 11:49 dispatch — the fresh verdict was never recorded. The host had also switched the loop session's agent from `astra_architect` to `build` (temporary architect model override), which made `repair_gate_evidence` refuse with `TASK_GATE_EVIDENCE_ARCHITECT_ONLY` and removed every other in-session escape hatch. Pinned by `tests/unit/background/stage-b-redispatch-reclaim.test.ts`: the restart shape (durable chain only), the same-process shape (in-memory route evidence occupied, asserting one fresh live binding plus live advancement to `tests_run`), the foreground settlement twin (one fresh live binding and `update_task_status` completing without a restart), and a fail-closed control (a foreign identity occupying the slot is not reclaimed). The rollback safety of the live supersede (prior binding restored, sibling slots and newer settlements untouched) is pinned by `tests/unit/hooks/issue-2491-direct-route-gate.test.ts`; the overlapping-reservation convergence (any failure order restores the last valid binding; a fully-failed append-rooted chain releases the slot) is pinned by `tests/unit/state/stage-b-route-reservation-overlap.test.ts`; the stale re-record fence (a newer settlement surviving the reviewer-receipt await) is pinned by `tests/unit/background/stage-b-stale-rerecord-fence.test.ts`; pending-reservation exclusion and durable/live winner consensus are pinned by `tests/unit/background/stage-b-route-durable-live-consensus.test.ts`. Both regression tests fail on the pre-fix source with the terminal rejection and pass with the fix; the control passes on both.

# spec_write reconciles the plan specHash before the drift marker materializes

## What changed

A canonical `spec_write` now rebinds the plan's `specHash` to the freshly
written spec even when `.swarm/spec-staleness.json` does not exist yet. The
SPEC_DRIFT_BLOCK and `/swarm status` guidance was also rewritten to name the
agent-executable repair path (canonical `spec_write` via the spec_writer
agent) instead of only pointing at `/swarm clarify`, which is not a
`swarm_command` registry entry.

## Why

Field wedge (Wirtschaftssimulation session, 2026-11-22): the drift marker is
written lazily by the next `loadPlan`, which runs *after* a canonical spec
write. So the natural repair sequence always deadlocked:

1. plan saved with the old spec hash → canonical `spec_write` replaces the
   spec → `reconcileSpecDrift` returns `no_marker` (nothing rebound),
2. the next `loadPlan` (inside `save_plan`) materializes the marker,
3. `save_plan` / `update_task_status` / `phase_complete` wedge with
   `SPEC_DRIFT_BLOCK`, and the error text told the agent to run
   `/swarm clarify` — a TUI slash command that does not exist in the
   `swarm_command` registry, so the architect had no executable repair path
   and had to stop for human intervention (`/swarm acknowledge-spec-drift`).

The documented contract ("accepted changes must be persisted through
canonical `spec_write` to reconcile the plan hash") was only implemented for
the marker-already-exists window; the first canonical spec change could never
reconcile anything.

## How it works

`reconcileSpecDrift` gained an opt-in `reconcilePlanHashWithoutMarker` flag
(set only by `spec_write`). When no marker exists, it synthesizes the drift
state from `plan.json` itself (stored vs current effective-spec hash) and runs
the same audited repair transaction as the marker path: WAL (PREPARED →
COMMITTED), plan-hash rebind through `savePlan`, ledger snapshot event,
`spec_drift_repaired` audit event, verified spec snapshot. With no plan, no
stored `specHash`, or an already-consistent hash it still returns `no_marker`
only when no pending or invalid WAL exists. A PREPARED/corrupt WAL fails closed,
protected plan mutations stay blocked until canonical recovery completes, and
`/swarm reset --confirm` clears the WAL with the plan epoch. Canonical repair
also refuses to report success when the just-published spec is unreadable or
over the native reader's 256 KiB UTF-8 byte limit. `acknowledge-spec-drift`
behavior is untouched (flag unset → marker-only semantics).

  enumeration is incremental (opendirSync), charged before filtering, and
  exhaustion blocks as retryable — never a partial hash, deletion, or admission.

# A finished background coder no longer blocks every later coder dispatch

## What

A background coder delegation whose child session already produced its trusted
terminal event no longer counts as an *active* coder owner for admission
capacity, and the capacity reservation it held is now released on proof as
soon as the terminal is durable.

- `completed` (result waiting to be ingested by the parent) and
  `ingestion_error` (one ingestion attempt failed; the result stays durably
  claimable in the delegations store) are terminal **for the child**: the
  launch is finished and must not occupy a live slot.
- The shared background maintenance pass releases a bound reservation whose
  exact owner record proves the child finished — proof-based, no lease age
  involved. Previously such a record *renewed* the lease forever
  ("exact owner record still active"), so the reservation never went away.
- Admission (`reserveBackgroundCoderSlot`) reconciles the same proof inline,
  so the very next dispatch after a wedged launch is admitted again.
- Preserved settlements and worktree-holding records are unchanged: they own
  recoverable resources and still count as active.
- Checkpoint compaction semantics are unchanged — unconsumed terminal records
  still keep their full bodies (a separate, broader liveness predicate remains
  in place for compaction and health counts), so a released reservation never
  drops or truncates a pending result.

## Why

Observed in the wild (a long-running adoption-audit session): a background
coder finished its work — trusted terminal `completed`, settlement `settled` —
but the single ingestion attempt into the parent session failed, leaving its
delegation record in `ingestion_error` forever. The old admission/renewal
predicate counted that dead child as an active coder owner, so:

1. the reservation lease renewed at every maintenance pass, keeping the
   reservation alive indefinitely, and
2. with `maxConcurrent = 1` (the standard coder path), every later coder
   dispatch of that parent session was denied with `PARALLEL_SLOTS_EXHAUSTED`.

The only release path was the 30-minute stale sweep of the delegation record —
and nothing guaranteed the record would age out (any retry touching it resets
the timer). Net effect: one failed ingestion could stop all coder work of a
session permanently. The result itself was never lost; only the bookkeeping
wedged the capacity accounting.

## Migration

No action required. Sessions that are currently wedged in this state unblock
automatically on their next coder dispatch: the admission-time reconciliation
drops the provably idle reservation before counting capacity.

# `fix(swarm)`: fail loud when a gate-bearing dispatch resumes a completed subagent child

## Summary

- Added a **`SWARM_CHILD_RESUME_UNTRACKABLE` guard** to the delegation gate's `toolBefore` (`src/hooks/delegation-gate.ts`): a canonical-role subagent dispatch that passes `sessionID` to RESUME a child session whose durable delegation record is already terminal is now rejected with an actionable message before the child launches. Previously such a dispatch was admitted, but the resumed round could never be durably tracked — the toolAfter path records a correlation conflict for the new callID and the completion observer rejects the follow-up terminal as a late terminal — so the verdict of the resumed round was **silently lost**.
- Guard scope is deliberately narrow: non-terminal (pending/running) records stay resumable (their single terminal is still consumable), lane/batch/PR-review records (`batchId`/`laneId`/`mode`/`workflowLane` set) are exempt because `dispatch_lanes` owns its own resume semantics, non-canonical agents never block, and an uncertain store read degrades open so a corrupt ledger cannot brick every dispatch.
- Added **"FRESH DISPATCH EVERY ROUND"** guidance to the `critic-gate` skill (`.opencode` + `.claude` mirrors, byte-identical): every CRITIC-GATE round — the first review and every re-review after NEEDS_REVISION or a material plan change — must launch a fresh critic child; never resume a prior critic child session.
- Regression coverage in `tests/unit/hooks/delegation-gate-resume-guard.test.ts` (7 tests, falsification-verified: the refusal tests fail with the guard removed).

## User-facing changes

On OpenCode 2.x native-async hosts, a model that resumes a completed swarm child session for a reviewer/critic/coder-style dispatch now gets an immediate, actionable rejection (`SWARM_CHILD_RESUME_UNTRACKABLE … omit the sessionID argument`) instead of a silently lost verdict that later wedges the workflow at `no_approved_snapshot` / `PLAN_CRITIC_GATE_VIOLATION`.

## Migration notes

None required. Dispatches that previously appeared to work (resume of a terminal child) were already broken downstream; they now fail at dispatch time with recovery instructions.

## Discovery context

Live failure in a consumer project (2026-11-21): a CRITIC-GATE re-review after NEEDS_REVISION resumed the same critic child session (the v2 host's subagent tool invites exactly this: "call subagent again with this sessionID"). The round-2 APPROVED verdict was never recorded (`get_approved_plan` → `no_approved_snapshot`, `.swarm/background-delegations-health.json` → `lateTerminals: 3`), EXECUTE was blocked by the `critic_pre_plan` gate, and the `approve_plan_critic` escape hatch returned NOT_AUTHORIZED because the orchestrator ran as the `build` agent instead of the swarm architect — a total deadlock requiring manual intervention.

# async lifecycle r11–r13 audit repair I: critic verdict, dispatch binding, atomic approval

## What

First batch of the independent source audit repairs for the native
OpenCode-2.3 async subagent lifecycle (r11–r13). This fragment covers the
approval-safety findings; crash-safe closeout and event/policy parity follow
in the sibling fragments.

### P0-1 — plan-critic verdict parser accepted non-verdicts

`extractPlanCriticVerdict` (src/plan/critic-approval.ts) matched the FIRST
`VERDICT: <TOKEN>` prefix anywhere in the text, so all three demonstrable
misclassifications released the `critic_pre_plan` gate:

1. the critic prompt's own rubric enumeration
   (`VERDICT: APPROVED | NEEDS_REVISION | REJECTED`) parsed as APPROVED;
2. a `VERDICT:` line inside a markdown code block (``` and `~~~` fences)
   parsed as APPROVED;
3. contradictory verdicts (an "Example:" APPROVED template followed by the
   real REJECTED) parsed as APPROVED.

The parser now requires a FULLY valid verdict line outside code fences,
blockquotes, and table/enumeration rows; collects every candidate verdict
(strict label, `## Verdict` heading, trailing bare token) and fails closed to
`null` on any disagreement or ambiguity. A host-truncated terminal result
(`resultTruncated`) never records an approval — a cut-off text cannot prove a
final verdict.

### P0-2 — the plan-critic dispatch hash was captured too late

The r11 code captured the plan-structure hash in the `tool.execute.after`
hook — AFTER the critic child had already started. A plan edited between
child start and the record write re-anchored the binding to the edited plan,
and the critic's older APPROVED verdict then released it. The baseline
(plan id, structural hash, and a sha256 digest of the full dispatch prompt)
is now captured in `tool.execute.before`, before the child starts, bound to
the exact parent session and call id, and the after-hook consumes exactly
that baseline — it never re-reads plan.json. Without a provable pre-execution
baseline there is NO binding and an async APPROVED can never auto-approve
(the audited `approve_plan_critic` escape hatch remains).

### P1-1 — plan-critic approval was not atomically deduplicated

The existence check and `takeSnapshotEvent` were two
independent operations; two racing recorders could both pass the check and
both write. The existence check and the commit now run under ONE
serialization boundary — the ledger evidence lock — via
`takeSnapshotEvent`'s (now awaitable) `preCommitCheck`, which re-verifies
both the replay fence (no snapshot for this call id) and the plan-structure
fence immediately before the append. Outcomes distinguish
`already_recorded`, `conflict`, `ledger_unreadable`, and `write_failed`;
an unreadable ledger is no longer silently conflated with "approval exists"
(fail-closed on read errors).

### P2-1 — plan-critic dispatch classification was too generous

Automatic approval recording now requires EXPLICIT plan-gate intent
(`MODE: CRITIC-GATE`, per the critic-gate skill) instead of the #2012
recall-biased substring heuristic. An ordinary critic review that merely
mentions `plan.md` or "review the plan" never auto-approves the coder gate.
The critic-gate skill now instructs the architect to use the explicit marker
(mirrored to `.claude`); a missed marker is recoverable via re-running
CRITIC-GATE or the audited `approve_plan_critic` escape hatch.

## Why

An approval snapshot recorded from a non-verdict (a template echo, a fenced
example, a truncated result) or for a plan the critic never reviewed
releases the EXECUTE-phase coder gate without a real review — the exact
authorization boundary the `critic_pre_plan` gate exists to enforce. The
async transport additionally crossed process boundaries (dispatch →
completion → ledger commit), so every check-then-write window had to close
under a durable serialization boundary.

# async lifecycle r11–r13 audit repair II: crash-safe terminal closeout

## What

Second batch of the independent source audit repairs for the native
OpenCode-2.3 async subagent lifecycle: the terminal claim and the business
closeout effects are now SEPARATE durable concerns.

### P0-3 — completion side effects were lost after a crash

The completion observer ran its business closeout effects (context map,
sounding-board verdict, pipeline advisory, delegation_end telemetry, parent
advisory) only while `isFreshTerminalClaim === true` — an in-process flag. A
crash between the durable terminal claim and any effect permanently lost that
effect; after the restart the replayed completion was a duplicate and the
r12 non-coder failure early-return even lost the failure message to the
parent forever.

This adds a versioned closeout journal on the durable delegation record
(`closeout`: terminal event id + per-effect ack states for `delegation_end`,
`context_map`, `sounding_board`, `pipeline_advisory`, `parent_advisory`).
Each effect is journal-gated instead of fresh-claim-gated, and is only acked
AFTER it was durably established. Failed effects stay re-drivable. A bounded
recovery pass (`reconcileTerminalCloseouts`) runs at every background
maintenance point through a registered reconciler (the live observer), so
recovery does not depend on a new host completion event — and never re-enters
the record currently being processed. Legacy records without a journal are
re-driven once and then journaled.

### P1-2 — the context map reported success before the workflow proved it

The context-map success summary was written before coder settlement and
Stage-B ingestion, with a blanket `final_status: 'completed'` (rendered as
`approved`). It now runs only after settlement AND ingestion proved the
business outcome: a rejected reviewer verdict, a failed test-engineer run, a
failed settlement or worktree merge, or a retryable ingestion never appears
as `approved` (no summary is written for them; a terminally negative
ingestion closes the step so recovery cannot re-drive a success write). A
crash between the ingestion commit and the summary write is re-driven by
recovery (the write itself is idempotent — `task_history` is keyed by task
id). `files_touched` now carries the coder's declared files when available.

### P1-5 — delegation_end / execution-attempt pairing survives crashes

The `delegation_end` pairing observation is journal-gated (exactly-once per
terminal across duplicates, replays, and process restarts; the deterministic
`record_id` keeps cost rollups deduped). Failed and cancelled delegations
keep their failure classification — never `success`.

### P2-2 — sounding-board and pipeline advisories are durable

The r12 closeout pushed sounding-board and pipeline advisories only to a
parent session live in memory. They are now stored in a bounded, eventId-
deduped `closeoutAdvisories` list on the delegation record — independent of
the single `advisoryInbox` slot (a terminal can carry several distinct
messages without clobbering) and of the parent session's liveness. The
prepare/release/ack delivery contract drains both slots.

## Why

A trusted terminal event is not the same as a completed closeout. Between
claim and effect sits ordinary crash surface (process kill, provider
restart, disk full); every effect that silently vanished there was either an
operator message that never arrived or telemetry that broke the
`delegation_begin`/`delegation_end` pairing. The journal makes each effect
individually acked and recoverable without exactly-once claims about
non-transactional sinks (telemetry remains at-least-once per journal step).

## Testing

- tests/unit/background/completion-observer-closeout-recovery.test.ts —
  controlled crash injection (claim→advisory, claim→delegation_end, ingestion
  commit→context-map) with fresh observer instances; journal fence; durable
  advisory dedup and no-clobber.
- tests/unit/background/completion-observer-terminal-closeout.test.ts — the
  P1-2 matrix (real Stage-B success writes exactly one `approved` summary;
  settlement-failure, rejected verdict, and retryable ingestion write none).
- tests/unit/background/async-lifecycle-integration-matrix.test.ts — the
  success and restart scenarios now use real Stage-B fixtures.
- All 173 background suites pass per-file (one pre-existing unrelated
  failure in stage-b-dispatch-binding-store-2829 exists on the base commit
  as well).

# async lifecycle r11–r13 audit repair III: policy parity and bounded event fan-out

## What

Third batch of the independent source audit repairs for the native
OpenCode-2.3 async subagent lifecycle (the explicit plan-gate intent
classification, P2-1, shipped in the first batch's fragment).

### P1-3 — the sounding-board caller category was lost on the async path

The synchronous Task handoff applied
`applySoundingBoardResponsePolicy(rawResponse, afterCtx.args)` — the
architect-owned `category` metadata reached the parser. The async completion
path called the same parser WITHOUT the args, so the explicit category the
architect supplied at dispatch was lost, and model free text decided the
category (including the always-surface stickiness of `UNNECESSARY`).

The validated caller category is now persisted on the delegation record at
dispatch time (`soundingBoardCategory`, bound to the exact call/child
identity; only the explicit `category` field counts, normalized, and only
when it is a real protocol category — invalid or missing values fall back
conservatively). The async closeout feeds it to the SAME shared parser as
the sync transport. The always-surface rules are preserved exactly: an
always-surface caller category surfaces a model `UNNECESSARY` as `APPROVED`;
an ordinary category keeps `UNNECESSARY` sticky; a missing category can
never preserve `UNNECESSARY`.

### P1-4 — a hanging event consumer could starve the completion observer

`dispatchEventConsumerIsolated` contained THROWN errors but awaited each
consumer's promise unboundedly: a consumer whose promise never resolved
(e.g. a wedged `prWorkflowResponseGate.event`) blocked every later consumer —
including the durable background completion observer. The wait is now
bounded (10 s default; 60 s for the completion observer, whose settlement
chain performs real durable work). An abandoned consumer keeps running in the
background; its eventual outcome is observed — a late rejection is reported
through the same bounded warning path, never an unhandled rejection. Recovery
of a completion lost to the budget remains the observer's own durable replay
machinery.

### P2-3 — the architecture documentation now states what is actually proven

`docs/architecture/async-lifecycle.md` gained a durable-closeout-journal
section (new section 6a) describing which transitions are durable, which side
effects are idempotent-durable vs claim-guarded vs at-least-once telemetry,
the recovery triggers (maintenance points, `reconcilePending`, consumed
records with pending steps, the in-flight guard), the behavior on corrupted
stores, and the guarantees NOT claimed (no general exactly-once across
non-transactional sinks; the plan-critic binding verifies against plan.json,
not against a plan copy inlined into the prompt; the async context-map
`task_goal` limitation). The r11–r13 sections were revised to reflect the
audit repairs instead of the superseded fresh-claim semantics.

## Why

Policy parity: the architect's explicit decision metadata is a protocol
input, not a suggestion — losing it on one transport means the two transports
render different verdicts for the identical dispatch. Fan-out: the event hook
is the delivery path for trusted completions; an unbounded await on ANY
independent consumer makes the whole plugin's completion processing
hostage to that consumer.

## Testing

- tests/unit/background/sounding-board-category-parity.test.ts — caller
  category wins over model text, always-surface `UNNECESSARY` matrix,
  conservative fallback, replay/restart determinism, parallel children with
  distinct categories (no swap).
- tests/unit/index-issue-2491-sounding-board.test.ts — the persistence
  validator (`validSoundingBoardCallerCategory`) including the
  never-scavenge-from-prompt rule.
- tests/unit/index-event-fanout-isolation.test.ts — a permanently hanging
  consumer cannot block the fan-out; late settlement reports visibly without
  an unhandled rejection; concurrent events do not serialize on a hung
  sibling.

# OpenCode 2.3 Native-Async Lifecycle: Verified Completions, Approvals, and Closeout Parity

## What

Repairs the native-async subagent lifecycle (OpenCode 2.3 background
subagents) end to end, closing audit findings F1–F6: verified plan-critic
approvals on async completions, correct context-map semantics, sounding-board
and telemetry parity, event fan-out isolation, and a full completeness audit
of terminal-bound actions. Includes the verified r5–r10 OpenCode 2.3
compatibility checkpoint (child-session identity, completion/inbox bridge,
usage events, tool/text adapters, guarded task completion).

Plan-critic approvals (F1):
- A critic child dispatched natively async that returned `VERDICT: APPROVED`
  now records its approval snapshot automatically. Previously the snapshot
  was written only by the synchronous Task path, so the next coder dispatch
  was blocked with `PLAN_CRITIC_GATE_VIOLATION` and required the manual
  `approve_plan_critic` escape hatch.
- One shared approval implementation (`src/plan/critic-approval.ts`) serves
  both transports. Plan-critic dispatches are bound at dispatch time to the
  plan's structural hash (durable `planCriticDispatch` field), so a plan
  edited after the dispatch can never be approved by the old verdict. The
  ledger dedups approvals by call id — replays and crash recovery can never
  approve twice. Failed/cancelled children, wrong identities, and
  unparseable verdicts fail closed.

Context map (F2):
- Starting a native-async child no longer writes a `final_status` summary the
  moment it launches (the running placeholder was misread as a completion).
- A verified async completion now writes the same context-map summary the
  synchronous handoff writes (same feature flag, same mapping); failures and
  cancellations never appear as success.

Sounding board + pipeline (F3):
- Async `critic_sounding_board` completions are evaluated by the exact same
  verdict policy as the sync handoff (`src/agents/sounding-board-policy.ts`);
  unparseable responses surface the treat-as-REPHRASE warning, never a silent
  approval. Pipeline continuation advisories now fire for async
  reviewer/test_engineer/critic/critic_sounding_board completions.

Telemetry + knowledge (F4):
- Native-async Task terminals now close their `delegation_begin`/
  `delegation_end` pair (success, failure, and cancellation) with the
  deterministic Task-shape cost identity, and reconcile knowledge receipts
  (ledger-idempotent, replay-safe). Lane records keep their existing
  `settleDelegationTerminal` path — nothing is double-booked, and the r8
  usage bridge remains the usage authority.

Event fan-out (F5):
- Each independent event consumer (PR-workflow resolver/gate, PR idle
  delivery, terminal-session handling, and the durable background completion
  observer) is now isolated: a throwing sibling can no longer starve the
  completion observer, and failures surface through the operator-visible
  deferred warning buffer with a per-consumer cooldown.

Completeness audit (F6):
- Every terminal-bound after-hook action is mapped to its sync and async
  path in `docs/architecture/async-lifecycle.md` (section 8), with the
  deliberate non-ports documented (async cost draining, micro-reflector,
  trajectory completion marker).

## Why

A live architect–critic–coder run on OpenCode 2.3 wedged on
`PLAN_CRITIC_GATE_VIOLATION` after the critic APPROVED, because the approval
snapshot only existed on the synchronous path. The broader audit showed the
same transport asymmetry across context map, sounding board, telemetry, and
event fan-out — native-async completions ran the durable settlement machinery
but none of the business closeout, and one failing event consumer could
silently suppress completion processing entirely.

# PR monitor: emit terminal PR events once

## What

`pr.merged` and `pr.closed` were re-emitted on every poll cycle while a PR
stayed in a terminal state and its subscription lingered (for example when the
subscription store refused writes because it was over capacity). One merged PR
produced 7+ duplicate `pr.merged` deliveries.

The PR monitor worker now dedupes the terminal event with an in-memory latch,
so each terminal event is emitted once per subscription while the PR stays
terminal. The latch only gates the event: sweep tracking and the auto-unsubscribe retry still run
every cycle while the PR is terminal, so a refused or timed-out cleanup is
retried without re-emitting. The latch is cleared when the PR is seen open
again (reopen), after a successful auto-unsubscribe, and on worker stop. The
event can repeat after a reopen, a re-subscribe, or a worker restart.

## Compatibility

No configuration, schema, or event payload changes. The `auto_unsubscribe_on_merge`
and `auto_unsubscribe_on_close` flags are unchanged.

Fix originally proposed by @thehaven in #3947.
