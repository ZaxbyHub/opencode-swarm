Wire run memory end-to-end so the architect actually sees prior task failures. Task outcomes are now recorded to `.swarm/run-memory.jsonl`: a PASS when a task completes and a FAILED entry when a task is marked blocked (both recorded centrally in `plan/manager.updateTaskStatus`, so the council auto-completion path is covered as well as the `update_task_status` tool), plus a FAILED entry carrying the gate's own reason when a council or QA gate blocks a completion. Previously nothing ever wrote that file, so the cross-session "avoid repeating known failure patterns" block could never appear.

Three defects that kept the feature dead or wrong are fixed alongside it. The store validated the absolute project root with a relative-sub-path validator, so every read and write threw `Invalid directory: absolute path`. The knowledge injector pushed the run-memory block without checking that it fit the remaining character budget, which could overshoot and starve lower-priority context. And the summary reported a task as resolved whenever any pass existed, even one recorded before the failure — a task that completed and later regressed to blocked now correctly reads as still failing.

Blocked tasks record `blocked_reason` when the plan carries one; the `update_task_status` tool has no reason argument, so a task blocked through the tool without a previously-saved `blocked_reason` records an explicit "no blocked_reason recorded" note rather than a bare "unknown". `run-memory.jsonl` is archived and cleaned by `/swarm close` and removed by `/swarm reset`, so one plan's failures are never attributed to the next plan's identically-numbered tasks.

Known limitation: entries count writes rather than logical attempts, so rendered attempt numbers can overstate how many times work was actually retried. Two mechanisms cause this. Repeatedly calling `update_task_status` against an unsatisfied gate appends one FAILED entry per call. And because `updateTaskStatus` is idempotent for an already-completed task with no settled guard on completed-to-completed, a single logical completion can pass through it more than once — the council auto-completion followed by an architect tool call, or the delegation-gate `toolAfter` advance — appending a second PASS. The pass/fail verdict and the recorded reasons stay correct in both cases; only the attempt count inflates.
