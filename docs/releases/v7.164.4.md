## Summary

Resolves 8 audit findings (F-03, F-05, F-06, F-07, F-08, F-09, F-11, F-12) in the
planning system identified by a comprehensive planning-system audit.

## What changed

### Concurrent-write protection (F-03)

- `phase_complete` now acquires a file lock on `plan.json` before writing
- Lock acquisition failures now hard-fail (consistent with `save_plan` and
  `update_task_status`), preventing lost-update races on concurrent phase
  completions
- Lock is released in a `finally` block, guaranteed cleanup

### Atomic file operations (F-05, F-08)

- `writeCriteria` is now async and uses `atomicWriteFile` (temp + rename)
  instead of direct `writeFileSync`
- `phase_complete` fallback plan.json writes now use `atomicWriteFile`
- Prevents data corruption if the process crashes mid-write

### Plan state validation (F-07)

- `acknowledge-spec-drift` now verifies the staleness file's `specHash` still
  matches the current plan before accepting acknowledgment
- Rejects acknowledgment if the spec has changed since staleness detection,
  preventing invalid transitions

### Lock retry resilience (F-09)

- `tryAcquireLock` retry configuration changed from `{retries: 0}` to
  `{retries: 5, minTimeout: 10, maxTimeout: 500, factor: 2}`
- Transient lock contention no longer requires manual retry

### Documentation (F-06, F-11, F-12)

- Added JSDoc to `computePlanContentHash` explaining the difference from
  `computePlanLedgerHash` (Bun.hash vs SHA-256, plan.md drift vs plan state integrity)
- Added comment to `isPlanMdInSync` documenting the fuzzy substring fallback
  rationale and future cleanup intent
- Added JSDoc to `computePlanLedgerHash` explaining the intentional exclusion of
  `specMtime` and `specHash` fields

## Migration notes

No migration required. The changes are backward-compatible: the new lock
acquisition retries 5 times with exponential backoff before failing, so
transient contention resolves automatically.

## Tests

- File locks tests: 17 pass (unchanged)
- Criteria store tests: 6 pass (updated to async)
- Acknowledge spec drift tests: 16 pass (includes new F-07 regression test)
- `phase_complete` locking tests: updated to assert the new hard-fail behavior
  on lock contention

# Wire spec FR/acceptance content into coder and reviewer delegations (#1687)

Coder and reviewer delegations previously had no structured field carrying spec `FR-###`/`SC-###` requirement text, and nothing mechanically re-checked that a delegated task's implementation still satisfied its originating requirement. The one validator that would reject a delegation missing acceptance criteria (`validateDelegationEnvelope`) had no caller in the real coder/reviewer dispatch path — it was already wired advisory-only (post-execution, non-blocking) into a separate, older structured-envelope mechanism (M15, commit `b981e894`) that the real free-text delegation format doesn't parse into.

## Changes

- **`fr_refs` task field (`src/config/plan-schema.ts`):** an optional `fr_refs: string[]` field on plan tasks records which spec `FR-###`/`SC-###` IDs a task maps to. Uses `.optional()`, not `.default([])`, so it serializes to `undefined` (omitted) for tasks that don't set it — preserving byte-for-byte hash stability for every plan persisted before this field existed. `evaluateRequirementCoverage` (`src/tools/save-plan.ts`) now treats a requirement as covered when a task's `fr_refs` includes its ID, in addition to the existing free-text substring match.
- **Hash exclusion (`src/plan/ledger.ts`, `src/plan/manager.ts`):** `fr_refs` is deliberately excluded from `computePlanLedgerHash`, `computePlanStructureHash`, and `computePlanContentHash` — all three enumerate task fields explicitly and are documented with a comment recording the exclusion. It rides through ledger snapshot/replay via the existing generic whole-`Plan`-object embed; no field-by-field wiring was needed.
- **`ACCEPTANCE` field on coder/reviewer delegations (`src/agents/coder.ts`, `src/agents/reviewer.ts`, `src/agents/architect.ts`):** the architect resolves a task's `fr_refs` live against the current `.swarm/spec.md` at delegation time (not a snapshot taken when the plan was saved) and copies the matched requirement text verbatim into a new `ACCEPTANCE:` field on both the coder's and reviewer's delegation input. When a task has no `fr_refs`, the field carries task-derived acceptance criteria instead and is never empty. The reviewer's output format gained a new `ACCEPTANCE_SATISFACTION:` field requiring it to explicitly assess whether the diff satisfies each referenced requirement, not just whether the diff looks correct in isolation.
- **Blocking pre-dispatch enforcement (`src/hooks/delegation-gate.ts`):** a new, named, exported function checks for a non-empty `ACCEPTANCE:` field on coder/reviewer Task-tool dispatches from `toolBefore` (pre-execution) and throws a descriptive error if it's missing or empty, blocking the dispatch. Scoped narrowly to coder and reviewer only — other delegation types (sme, explorer, critic, etc.) are unaffected. The pre-existing M15 advisory mechanism (`appendDelegationEnvelopeAdvisory`, `toolAfter`) is untouched and continues to serve its own, separate purpose for the older structured-envelope format. The non-empty check accepts the field content either inline on the `ACCEPTANCE:` header line (the architect-instructed same-line format) **or** on the lines that follow a bare `ACCEPTANCE:` header, up to the next INPUT-FORMAT field header (`^[A-Z][A-Z0-9_]*:`) or end of input — so a verbatim FR/SC body pasted as a multi-line section is not false-blocked (PR #1864 review feedback), while a bare `ACCEPTANCE:` immediately followed by another field is still correctly rejected as empty.
- **Mechanical verbatim-coverage enforcement (`src/hooks/delegation-gate.ts`, issue #1687 F-007):** beyond the non-empty check, the gate now mechanically verifies that a coder/reviewer dispatch's `ACCEPTANCE` field actually *contains* the verbatim requirement text for **each** spec id in the plan task's `fr_refs`. Three exported helpers do the work — `extractSpecRequirementBodyById` (line-anchored `FR-###`/`SC-###` body extractor), `normalizeAcceptanceText` (symmetric whitespace/markdown/case normalizer applied to both sides), and `checkAcceptanceCoversFrRefs` (per-id normalized-substring coverage). A mismatch throws `ACCEPTANCE_FIELD_COVERAGE_MISMATCH:` naming the uncovered id. The check gates both coder **and** reviewer (it runs above the coder-only return) and is **fail-open on every precondition**: no plan, an unresolvable task id, a task with no `fr_refs` (FR-004), a missing/unreadable `.swarm/spec.md`, or an id absent from the spec all skip the check silently — only a clear, high-confidence coverage miss on an otherwise fully-resolved dispatch blocks.
- **Docs (`docs/plan-durability.md`):** added a section documenting the `fr_refs` field's design (reference-not-snapshot, hash exclusion, round-trip surfaces), per AGENTS.md invariant 5.

## Known caveats

- **Coverage enforcement is a normalized-substring check, not a byte-exact diff.** The mechanical check (F-007) applies one symmetric normalizer to BOTH `spec.md` and the delegation prompt that carries `ACCEPTANCE`, folding whitespace, markdown-emphasis, case, dash-width (em/en dash and `--` → hyphen), and curly-vs-straight quotes, then requires each mapped requirement's normalized body to appear as a substring of the normalized prompt. This catches gross non-copies (placeholder text, paraphrase, truncated copies) and does not block a good-faith verbatim copy that differs only in those respects — a design priority, since a false-positive block would hard-halt a real swarm. (A copy that diverges in ways the normalizer does not fold — e.g. other exotic Unicode punctuation — could still block; the folded set covers the substitutions an LLM copy actually makes against the current spec.) It is deliberately **fail-open**: a task with no `fr_refs`, an id absent from `spec.md`, an unresolvable task id, or a missing/unreadable `spec.md` all skip the check rather than block. Because the check reads `.swarm/spec.md` literally (matching the architect's instruction) rather than the effective-spec projection, verbatim fidelity is now mechanically enforced for the common case, not merely prompt-instructed; the residual gap is that fail-open cases (unresolvable id/task) fall back to the non-emptiness guarantee only.
- **No live end-to-end exercise of a real delegation.** This change was implemented and validated in a session where the swarm's own runtime tools (`save_plan`, a live architect-driven `Task` dispatch, etc.) were unavailable; verification is via targeted unit/integration/adversarial tests and direct code reading, not an observed real coder/reviewer dispatch through the swarm.

## Migration

No migration required. `fr_refs` is optional and additive; existing plans without it continue to work via the pre-existing free-text coverage-matching path.

# Plan-critic baseline drift: one hash definition, no more spurious BASELINE DRIFT

Issue: #2523

## Symptom

Every first phase-critic review after a plan approval opened with a spurious CRITICAL **BASELINE DRIFT — plan mutated after approval** finding, even when nothing had touched the plan. The tampering alarm fired on every healthy run, training operators to ignore the one signal that means "someone edited the plan behind your back."

## Cause

The drift comparison in `get_approved_plan` computed a **status-inclusive** digest (`computePlanHash`) and compared it against the **status-excluded** structure hash (`computePlanStructureHash`) that plan-critic approval snapshots store as their `payload_hash`. Two SHA-256 digests over different field sets can never be equal, so `drift_detected` was always `true` once the newest approval snapshot came from the plan-critic gate. A third writer (`write_drift_evidence` APPROVED) stored the status-inclusive digest instead — a second, inconsistent baseline definition.

## Change

- `computePlanStructureHash` is now **the single approval-baseline hash**. The decision is documented on the function: task/phase status is excluded because the baseline detects *plan edits*, not execution progress.
- `takeSnapshotEvent` enforces this at the write choke point: every `source: 'critic_approved'` snapshot's `payload_hash` is the structure hash, so all three approval writers (plan-critic gate recorder, `approve_plan_critic` override, `write_drift_evidence` APPROVED) store the same definition without having to remember an override.
- `get_approved_plan` compares structure hash against structure hash: a status-only change (task flipped to `in_progress`/`completed`) never reports drift; any structural change (description, acceptance criteria, dependencies, files, tasks/phases added or removed) always does.
- The status-inclusive ledger digest was renamed `computePlanHash` → `computePlanLedgerHash` (byte-identical output) with its own docstring, so the ledger hash chain, replay, epoch identity, and integrity checks are untouched. The old overlapping name is deleted — a grep ratchet (`tests/unit/plan/plan-hash-single-definition-ratchet.test.ts`) fails if a second plan-structure hash or the retired name is reintroduced.

## Migration

Plan-critic approvals recorded since the original #2012 fix already store the structure hash and now compare correctly. A `write_drift_evidence` APPROVED snapshot recorded **before** this release stores the old status-inclusive digest and will read as `drift_detected: true` until the next approval snapshot supersedes it — re-run the phase drift verifier (or `approve_plan_critic` / `/swarm approve-plan-critic`) once to record a fresh approval and clear the flag.
