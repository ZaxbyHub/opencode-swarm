# Consensus mining

The consensus miner reads evidence that already exists under `.swarm/` and reports what several independent runs agree on. It is a **proposals-only boundary**: it activates no skill, writes no knowledge entry, promotes nothing, and edits no project file. The single artifact it produces is an immutable report under `.swarm/evolution/consensus/`, and every recommendation inside that report is a suggestion a human or a separately-gated workflow may act on. Nothing downstream is triggered by mining.

## Corpus

`src/consensus/corpus.ts` normalizes eight existing sources into one flat stream of `CorpusObservation` records — `{ runId, taskId?, taskCategory?, agentRole?, modelId?, seed?, success, signals[], evidenceRef }`. It adds no new store: evaluation runs come from `readEvaluationRun`, gate audits from `listGateAuditResults` and `readGateAuditResult`, gate ground truth from `readGateGroundTruth`, per-task trajectories from `listEvidenceTaskIds` + `readTaskTrajectory`, PRM session trajectories from `readTrajectory`, skill compliance from `readSkillUsageEntries`, knowledge outcomes from `readKnowledge` + `computeOutcomeSignal`, and retrospectives from `loadEvidence`. Only two read-only enumerators are new — `listEvaluationRunIds` over `.swarm/evolution/runs` and `listTrajectorySessions` over `.swarm/trajectories` — because the underlying stores read one artifact at a time and never needed a listing of their own.

Evaluation runs are the only source carrying task category, model id, and seed together; every other source supplies a subset, and a field that a source cannot attribute stays absent rather than being defaulted. `runId` is the *support unit* and is namespaced per source, so per-task trajectories and per-task evidence bundles deliberately share one `task:<id>` identity: they are two views of the same trial, and counting them separately would double the apparent agreement.

Every loader takes an injected `directory`; there is no `process.cwd()` fallback anywhere in the subsystem (AGENTS.md invariant 4). Nothing in the corpus path writes. Prompts and reasoning traces are never read into an observation at all — only outcomes, verdicts, categories, and bounded excerpts. Every free-text fragment that survives into a signal, statement, or evidence reference passes through `redactSecrets` **before** the `consensus.max_excerpt_chars` length bound, so a secret straddling the truncation point is replaced rather than half-copied. The whole corpus is capped at `maxEvidenceItems` against a fixed source order and a deterministic per-source sort, so the same tree always yields the same truncated corpus. A source that throws is recorded in `unreadableSources` and the rest of the corpus still loads; a partial corpus that says so is better than a silently empty one.

## Thresholds and diversity

Support is **distinct runs**, never observations: one chatty run emitting the same signal fifty times contributes exactly one. `successSupport` and `failureSupport` are likewise distinct-run counts, and a single run may appear in both when it carries the signal on a succeeding and a failing observation — they do not have to sum to `support`.

An attribute is emitted when `support >= minSupport` and `successSupport >= minSuccessfulRuns`, defaulting to `consensus.default_min_support` and `consensus.default_min_successful_runs`. It becomes **proposal-eligible** only when it additionally clears `taskDiversity >= 2` and draws support from more than one run. `taskDiversity` counts distinct task identities (`taskId`, else `taskCategory`) among the contributing observations. Below that bar the attribute is still emitted, with `proposedTarget: 'none'`, as an **investigation note**: one anecdote can only create an investigation note, and suppressing it entirely would hide the evidence a human needs in order to go looking for a second task. Knowledge-derived attributes carry no task attribution and therefore surface as investigation notes by construction.

`modelDiversity` counts distinct model ids among the contributing observations and is **0 when no contributing observation carries a model id at all** — the normal case for trajectory-, usage-, and knowledge-derived attributes. Zero means *"not measurable from this corpus"*, **not** *"measured as none"*, and it never gates emission or proposal eligibility on its own. Reading a zero as evidence of single-model agreement is the misinterpretation this rule exists to prevent.

Negative evidence is retained unconditionally. `failureSupport` and `counterexampleRefs` are populated on every attribute that has failing runs, and `ConsensusAttributeV1Schema` **rejects** an attribute that declares failing support while carrying no counterexample references — an attribute may never be emitted with its negative evidence dropped. Failing runs also lower `confidence`, which is a deterministic function of support saturation, the successful-run ratio, and a halving while below the diversity gate.

## Optional LLM restatement

All deterministic work — filtering, counting, gating, negative-evidence retention, proposal construction, and fingerprinting — completes **before** any model is consulted. Summarization, controlled by `consensus.llm_summarization_enabled` and bounded by `consensus.llm_timeout_ms`, runs last through an injected read-only dispatcher and may replace only an attribute's `statement`. It cannot change a count, a gate outcome, a target, a confidence, or a fingerprint. When no dispatcher is wired, the config disables it, the call times out, the dispatcher throws, or the response is empty, every attribute keeps its deterministic statement and the report records `summarization_skipped_reason` — graceful degradation, never a hard dependency. Model output is redacted and length-bounded like any other excerpt.

## Reports, integrity, and retention

`ConsensusReportV1` records `reportId`, `generatedAt`, the `request`, `inputIds`, per-source `corpusHashes`, `configHash`, `integrityHash`, `attributes[]`, `proposals[]`, and `redactionPolicyVersion`. Reports live at `.swarm/evolution/consensus/<reportId>.json` and are written through the shared `writeImmutableArtifact` pipeline (`src/evidence/immutable-store.ts`) that the evaluation store also binds, supplying only their own lock actor, canonical serializer, and conflict-error type.

The integrity hash covers the whole report except three wall-clock-or-derived fields: `integrityHash` itself, `reportId` (which is *derived* from the hash, so including it would be circular), and `generatedAt` — plus each proposal's `provenance.writeOrigin.producedAt`, which the miner stamps from the same clock. That exclusion is what makes **same inputs ⇒ identical hash** true, and therefore identical `reportId` and idempotent re-mining. The hash is computed subtractively so a field added to the contract later is covered automatically. It is verified before persist and again on read: a report whose declared hash does not match its content is refused rather than written, and on-disk tampering is caught rather than trusted. A divergent payload written to an existing report id is rejected with `ConsensusConflictError`; a payload differing only in timestamps is recognized as the same artifact.

`consensus.report_retention` bounds how many reports are kept. Pruning keeps the newest N by `generatedAt`, is a total order (ties broken by id), never deletes a corrupt report — an unparseable artifact is data-quality evidence — and treats a configured `0` as *retention disabled* rather than *delete everything*, so it can never remove the report just written.

## Tool surface

`consensus_mine` (`src/tools/consensus-mine.ts`) is the entry point, available to `architect`, `curator_phase`, and `curator_postmortem`. It accepts optional `run_ids`, `task_categories`, `agent_roles`, and `model_ids` filters plus `min_support`, `min_successful_runs`, and `max_evidence_items` overrides, all defaulting from the `consensus` config block. When `consensus.enabled` is false it returns a disabled result and writes nothing. Because its only write target is its own report, it is classified as a pathless write-like tool in `src/full-auto/policy.ts` alongside `write_retro` and `knowledge_add`, and it is denied in read-only dispatch lanes. It is deliberately absent from `WRITE_TOOL_NAMES`, whose members are the tools that write project file contents, and it deliberately declares no `prWorkflow` capability so it stays fail-closed in PR review and feedback modes.
