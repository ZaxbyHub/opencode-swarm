# `fix(background)`: a workflow-settled coder launch no longer holds its background reservation forever

## Summary

- A background coder launch can be durably finished on the WORKFLOW side — the architect settled its coder settlement (`.swarm/coder-settlements/<task>.json` at `state: 'COMMITTED'`, `accepted: true`, `transitionId: 'coder:<callID>'`) — while the delegation store's owner record never observed the child terminal (observer gap, restart, host event loss). Observed live in the consumer-project loop (task 2.18, 2026-11-27): the repair coder finished, the architect settled and verified the work, but the record stayed `pending` (the store's `lastTerminalAt` predated the dispatch) — so the reservation logic, which consulted ONLY that record, kept the task's reservation bound forever.
- The wedge was self-extending with no lease-based escape: task-keyed reservation ids are minted per parent+task, so every redispatch of the task (fresh call id, same reservation id) was refused as `duplicate_task`; the maintenance sweep renewed the lease every 15 minutes on the still-`pending` owner record ("exact owner record still active"); and even the 30-minute stale sweep could only help while the child looked quiet. Two follow-up dispatches were refused live before the architect gave up and documented the wedge.
- The reservation release logic now accepts the same durable receipt the #2828 settlement-wedge recovery already reads: a COMMITTED accepted coder settlement for exactly the reservation's launch (`coder:<reservation.callID>`). The maintenance sweep releases such reservations on proof (`workflow-settlement-committed`, no age involved — the same class as the proven-terminal-owner arm), and the admission reconciliation removes them before the duplicate check AND stops counting their owner records as active admission slots (the second `duplicate_task` source: the task-keyed owner key matched the pending record even after its reservation was gone).
- Fail-closed by construction: a missing, unreadable, non-terminal (`PREPARED`/`DISPATCHED`/`ABORTED`), or unaccepted WAL proves nothing; a settlement for a DIFFERENT dispatch of the task (a newer launch's WAL) never proves this reservation idle; a call-keyed reservation (`planTaskId: null`) has no settlement-WAL identity at all. The exact-launch identity (task + callID) subsumes the #2104 generation guard because a newer launch mints a new callID and therefore never matches the settled WAL entry.

## User-facing changes

- A swarm task whose background coder was settled by the architect (settlement COMMITTED and accepted) can be re-dispatched immediately — no more `BACKGROUND_CODER_TASK_RESERVED (duplicate_task)` on a launch that is provably finished, no more waiting for lease expiry (which never came) or a user-confirmed `/swarm reset-session`.
- The maintenance pass self-heals existing wedges: the next `maintainBackgroundDelegations` run releases the stale reservation and records the fact in `background-delegations-health.json` (`kind: 'release'`, `reason: 'workflow settlement COMMITTED+accepted for this launch'`).

## Migration notes

None for consumers. The new predicate lives in `src/workflow/coder-settlement-launch-proof.ts` (its own module to avoid the pending-delegations ↔ coder-settlement import cycle) and reads only the shared WAL reader/parser. Delegation records and reservation stores keep their schemas; no state shape changed.

## Discovery context

Found in the consumer-project loop (task 2.18, 2026-11-27; the architect's own diagnosis: "Die Session ist completed, aber die Reservation blockiert neue Coder-Admissions als duplicate_task"). The wedge chain: repair coder completes with NEED-handoff → delegation record never terminalizes (`pending`, no terminalResult) → architect settles the workflow WAL (`coder_settlement settled`, COMMITTED + accepted + cleanupComplete) → two redispatches refused as `duplicate_task` → maintenance renews the lease on the pending owner record. Pinned by `tests/unit/background/background-coder-reservation-workflow-settlement-release.test.ts` (12 tests: proof-based release with no renewal, same-task redispatch admitted with the wedged reservation reconciled away, the DISPATCHED/accepted-false/foreign-transitionId/call-keyed/missing/corrupt fail-closed shapes, duplicate_task preserved when the WAL does not prove, and the WAL predicate's own identity matrix).
