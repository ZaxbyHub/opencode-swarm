# `fix(ci)`: CI failure detection blind to bun 1.3 output; close-suite and pre-existing test failures fixed

## Summary

- **CI failure detection is now exit-code-primary**, not coupled to a specific bun-version output marker string. Both the `unit` job's per-file loop and the `Integration tests` step now gate on the actual process exit code; the marker-grep is kept as a non-gating informational line only.
- **CI now skips a tracked quarantine list of known pre-existing failures** (`scripts/ci/quarantined-tests.txt`, 113 files, issue #1705, plus OS-specific `scripts/ci/quarantined-tests-{macos,windows}.txt` merged in on non-Linux runners) in both the `unit` job's per-shard file collection and the `coverage` job's full-suite run, so the now-honest exit-code-primary gate reflects new regressions rather than the debt backlog the previous broken detection had been silently hiding. The `integration` job gained the same treatment (`scripts/ci/quarantined-integration-tests.txt`, 8 files) once its own failure detection was fixed and it surfaced its own pre-existing debt (see Known caveats).
- **The `unit` and `integration` jobs retry a failing test file up to twice (three attempts total) before gating on it.** Real GitHub Actions runs surfaced a low, shifting baseline of single-shard flakes under the shared runners' resource contention — a different file each run, always passing standalone locally, occasionally failing two attempts in a row. A file now only blocks the gate if all three attempts fail.
- **Fixed a genuine stale-read-after-rename race in the atomic temp+rename write pattern used across `.swarm/` state persistence** (`plan.json`, `plan.md`, session snapshots, scope cache, task evidence, lane evidence, summaries, handoff artifacts). `src/utils/bun-compat.ts`'s Node-fallback write path already had a fix for this — an existing code comment documents that a plain `rename()` can complete before the directory-entry update is flushed (macOS/APFS; the same delayed-visibility gap has also been observed on Linux CI runners) — but that fix only ran on the Node fallback branch of `bunWrite()`. Every call site that does its own separate rename after `bunWrite()` (rather than routing through `bunWrite`'s internal rename) bypassed it entirely, and — critically — `bun test` always takes the `Bun.write()` fast path (since `Bun` is defined under the Bun runtime), so this gap was invisible in every test run, including CI's, even though production (bundled `--target node`) was already protected. Extracted the fix into a shared `atomicRename()` helper and applied it at the call sites that do their own rename after `bunWrite()` in `.swarm/` state persistence (`src/plan/manager.ts` ×7, `src/hooks/agent-activity.ts`, `src/session/snapshot-writer.ts`, `src/scope/scope-persistence.ts`, `src/evidence/task-file.ts`, `src/evidence/manager.ts` ×2, `src/turbo/lean/evidence.ts`, `src/summaries/manager.ts`). This was the root cause of an intermittent CI failure on `tests/unit/tools/save-plan-identity-gate.test.ts` (a second `save_plan` call's new phase data was transiently absent from an immediate on-disk read-back) — verified fixed at this branch's pre-merge commit. `src/commands/handoff.ts` deliberately keeps its original `renameSync` path: `handoff.md`/`handoff-prompt.md` are advisory user-facing artifacts never read back in a tight race (unlike `plan.json`), so the fsync there was defensive-only and cost a substantial temp-cleanup adversarial suite; the durability fix is scoped to the files with the actual read-back race.
- **The `coverage` job no longer silently discards test failures.** Replaced `|| true` (which, combined with `set -e`, could abort the step before the diagnostic ever ran) with `|| test_exit=$?` plus an explicit post-threshold check, so a real test failure fails the job instead of being swallowed.
- **Fixed the close-suite tests named in #1683** (`close-cleanup.test.ts`, `close-terminal-write.test.ts`) that CI's broken detection had been hiding as green on `main`. Root causes: an incomplete mock missing `_internals`/`getGitRepositoryStatus` exports, a stale WAL-sidecar assertion (production preserves `swarm.db-shm`/`-wal` in place, doesn't archive them), an errno-suffix message mismatch, and — the recurring root cause across this whole investigation — call sites that route through `close.ts`'s `_internals` DI seam, which a plain `mock.module()` re-registration from a different test file cannot retroactively intercept. `close-finalizer.test.ts` received the same class of fixes (DI-seam override, errno fix, a fixture gap) but real CI still shows it failing intermittently for a reason not yet fully diagnosed (see Known caveats) — it remains in the quarantine list rather than being claimed as fixed.
- **Fixed 45 additional genuine pre-existing test failures** across 16 files under `tests/unit/commands/` (`memory`, `pr-subscribe`, `knowledge` + adversarial, `dark-matter` + adversarial, `reset-session` + enoent, `cleanup-drift`, `coupling`, `simulate`, `issue-command`, `deprecation-warning`, `design-docs`, `deep-dive-registration.adversarial`, `create-swarm-command-handler.first-run`) that CI's broken detection had also been hiding. Most were stale assertions left behind by legitimate refactors (command-registry restructuring, message-format changes, deprecation aliasing) or incomplete/stale `mock.module()` factories — but three were genuine production bugs:
  - `src/commands/reset-session.ts` — `validateSwarmPath` was called twice (once inside a try/catch, once unguarded), so a gracefully-reported failure on the first call could re-throw uncaught on the second, crashing the entire best-effort session cleanup — contradicting the function's own documented "continue on failure" contract.
  - `src/commands/coupling.ts` — JSON output embedded a `path.relative(...)` result without POSIX-normalizing Windows backslashes, inconsistent with the convention already used at ~18 other call sites in the codebase.
  - `src/hooks/knowledge-validator.ts` — cosmetic comment-only fix so a drift-prevention meta-test's context-window heuristic correctly recognizes an already-accounted-for `.swarm/` write.

## User-facing changes

None. This is a CI-infrastructure and test-suite fix; no runtime command behavior changes for end users, except that `/swarm memory evaluate` and `/swarm reset-session` are now more robust on Windows (see production bugs above).

## Migration notes

None required.

## Known caveats

- The `integration` job (`tests/integration/*.test.ts` + `./test/*.test.ts`) also only ever runs on `merge_group` — skipped entirely on `pull_request`, same as `coverage`. The first real merge_group run this job ever executed (after fixing its own version of the same exit-code-vs-marker-grep bug, and the same silent-output-discard bug the `unit` job had) showed 10 files failing. Reproducing locally in a clean environment confirmed 8 as genuine, deterministic pre-existing failures (now quarantined in `scripts/ci/quarantined-integration-tests.txt`, tracked in #1705); the other 2 (`phase-complete-events.adversarial.test.ts`, `reviewer-verdict-rollup.test.ts`) pass consistently standalone and are CI-runner flakes, now absorbed by the same retry mechanism added to the `unit` job. (A third, larger local-only failure count was traced to a stray `/.swarm` directory this investigation's own test runs had left at the container's filesystem root, confounding `validateProjectRoot`'s parent-directory walk for unrelated tests — an environment artifact, not a repo bug, and unrelated to the 8 quarantined files.)
- Merging latest `main` into this branch brought in two recent `main` refactors whose production changes landed without updating their tests (`main`'s still-broken CI hides the failures). Honest CI here surfaced them:
  - **`main`'s `savePlan` "projectedPlan" change is a real production regression.** `main` now replays the ledger and writes the *replayed* plan to `plan.json` instead of the caller's freshly-`validated` plan. On a full plan restructure or status reset the ledger replay returns a stale projection, so `plan.json` is written with the OLD structure even though `save_plan` returns the new task counts. Verified: `save-plan-identity-gate.test.ts`, `save-plan.test.ts`, and `save-plan-execution-profile.test.ts` all pass at this branch's pre-merge commit and only break after merging `main`. These are quarantined pending a dedicated fix to `main`'s ledger-replay logic (invariant #5, plan durability) — out of scope for this CI-detection PR. `save-plan-identity-gate` in particular was correctly fixed by the `atomicRename` change above (passing pre-merge); `main`'s `projectedPlan` change re-broke it for an unrelated reason.
  - `main` moved `pre-check-batch`'s `qualityBudget` call behind the `_internals` DI seam but left `pre-check-batch.test.ts` mocking it via `mock.module` (which no longer intercepts); `main`'s replacement test uses the seam and passes. Quarantined.
  - `main`'s `checkpoint`/`rollback` refactor left `checkpoint.test.ts`'s end-to-end save/restore workflow asserting the pre-refactor contract. Quarantined.
  - `main`'s Lean Turbo merge-back refactor (success path switched from `mergeLaneBranch` to `attemptMergeBackFromDirty`; merge conflicts now fail the lane; dispatch-failed lanes are preserved without dirty-merge-back) updated the sibling `runner.test.ts` but missed `integration-worktree.test.ts`. **This one was fixed here** — the 6 affected tests were updated to mirror `main`'s own sibling-test changes, matching the new production behavior.
- `tests/unit/commands/close-finalizer.test.ts` remains quarantined, not fixed: an earlier revision of this PR removed it from the quarantine list on the assumption it was fully fixed, but real GitHub Actions runs show it still fails twice in a row (past the retry-once mechanism), for a reason not yet captured in any log (a separate fix in this PR corrects the `unit` job's failure path, which was silently discarding the actual assertion output on every failure — future runs will surface the real error). Re-quarantined pending that diagnosis; tracked in issue #1705.
- CI's OS-matrix behavior (Windows/macOS/Linux runners) was demonstrated for the first time on an actual GitHub Actions merge_group run (previously untested — `pull_request` events only ever run ubuntu-latest). It found 22 files that fail specifically on macos-latest and/or windows-latest while passing on ubuntu-latest; these are now quarantined per-OS via `scripts/ci/quarantined-tests-{macos,windows}.txt`, keyed on the `$RUNNER_OS` env var. Root cause not yet diagnosed (no macOS/Windows environment available to investigate further); tracked in issue #1705.
- That same first merge_group run also showed the `coverage` job's full-suite single-process run (`bun test --coverage` over all ~1167 gated files at once) failing its `test_exit` check. Reproducing locally found **189 of those files (~16%) have at least one failing test only in this combined-process mode** — 1487 individual failing test cases, none of which fail standalone or in the sharded `unit` job. This is consistent with systemic mock/global-state contamination cascading across files sharing one process (several files show 20-48 failures each) rather than 189 independent bugs, and is deliberately **not** patched over with a 189-file quarantine list (which would defeat the coverage job's purpose) — tracked separately in issue #1712 for real root-cause investigation. The `coverage` job will keep failing merge_group runs until that's resolved.
- A sibling test outside this PR's scope, `tests/unit/memory/recall-evaluation.test.ts:120`, asserts the identical stale `noisy_injection_count === 0` check that `memory.test.ts` fixed here, and is genuinely red on current `main` for the same reason (introduced by an earlier commit that added new fixtures without updating this assertion). Now quarantined (see below); worth a small separate follow-up.
- Once exit-code-primary detection went live, a full scan of all 1279 `tests/unit/**` files (each run standalone, matching CI's per-file loop) found **107 genuinely pre-existing failing files** across nearly every subsystem — far more than `tests/unit/tools/` and `tests/unit/hooks/` alone, and all confirmed reproducing identically on `main`. Rather than leave the `unit`/`coverage` jobs permanently red or expand this PR into a 100+-file fix spree, these files are now listed in `scripts/ci/quarantined-tests.txt` and skipped by both jobs' file collection, with the backlog tracked in issue #1705 for incremental follow-up. Two untouched, unrelated pre-existing failures remain quarantined under `tests/unit/commands/`. A second category of 5 CI-environment-flaky files (pass standalone, fail intermittently on GH Actions' shared runners) is quarantined separately — see the retry-once mechanism above.

## Discovery context

Investigating GitHub issue #1683 ("CI failure detection is blind to bun 1.3 output; close-suite tests are red on main") surfaced that CI's failure-marker grep pattern no longer matched bun 1.3's actual failure-line format, so failing tests were silently reported as passing. Once detection was fixed, a regression sweep found a large body of genuinely pre-existing, silently-red tests across the repo — this PR resolves the close-suite tests named in the issue plus the pre-existing failures within `tests/unit/commands/`, since a merge-blocking requirement was that CI's now-honest failure detection not immediately go red on unrelated pre-existing debt in that directory.
