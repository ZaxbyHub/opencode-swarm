## Security hardening: residue quarantine containment, hive promotion provenance, and external-skill approval identity

Three guardrail hardenings land together (collated #3820 + #3822 + #3836, Workstream S slots 3/5/18).

### Residue quarantine rollback + render consistency (#3836, transfers #3596)

- `rollbackResidueQuarantine` no longer aborts an entire batch because one manifest entry carries control characters in its recorded path. Such entries are now **skipped and reported** (`status: 'skipped'`, reason `unsafe-name`), the batch is retained (`drained: false`), and every valid sibling still restores. Previously one poisoned entry threw away the whole rollback and stranded the batch permanently — every retry re-selected it and re-threw, making the stored copies unrecoverable through the tool.
- Tampering stays a hard reject: traversal (`..`), empty segments, absolute paths, and root escapes abort the whole call exactly as before (including when only the stored path is traversal-shaped).
- `validateRelPath` now rejects the full Unicode Cc class (C0 + DEL + C1); previously C1 and DEL passed validation and reached raw output.
- All quarantine/residue-derived names rendered by `swarm config doctor`, the close command (operator warnings and the persisted `.swarm/close-summary.md`), close dry-run, close archive, and the curator post-mortem briefing are neutralized through one shared helper (`neutralizeResidueName`), matching the #3542 renderer treatment.
- The quarantine MOVE path validates each eligible entry's name **before** renaming; unsafe-named residue is preserved in place with reason `unsafe-name` instead of being written raw into a manifest that would later poison rollback.

### Hive promotion is bound to independent provenance (#3820)

- The application-evidence gate is **active by default**: `knowledge.promotion_min_terminal_applications` now defaults to **1** (was 0, which left the gate inert). A lesson is no longer promotable to the cross-project hive on age alone, on a caller-supplied tag, or on retrieval-only phase confirmations without at least one independent terminal receipt. Independent terminal receipts of any outcome (applied, violated or contradicted) satisfy the evidence gate, as defined by the existing #1847 contract; applied-only filtering is not part of this change.
- Independence is an explicit allowlist — only `reviewer`, `architect`, and `test_engineer` receipts count. `delegate` self-report, `architect_marker` acknowledgments, application-gate release records, `manual`, `migration`, `phase_override`, and legacy `unknown` sources are all refused.
- The privileged `hive-fast-track` route is no longer armed by the entry's `tags` array (which any writer could set); it requires a dedicated `hive_fast_track_authorized` field that only the manual promotion path writes, and `knowledge_add` strips the tag from caller input as defense in depth.
- **Compatibility:** ordinary direct-text promotion (`/swarm promote "<text>"`) now requires the audited override (`--force --reason`); `promoteFromSwarm` promotes when the swarm entry has a qualifying independent receipt. Operators who need the old behavior can set `promotion_min_terminal_applications: 0` explicitly.

### External-skill approval is bound to verified content (#3822)

- Promoted external skills are now **digest-bound**: promotion records a canonical content digest (the artifact's own digest line — only an exact `content_digest: <64 hex>` line (or the internal `pending` draft token) — replaced by a fixed placeholder before hashing; a digest line carrying any other value or trailing bytes is hashed as-is, so payload hidden on that line fails verification), and the skill propagation gate recomputes it at discovery/injection time, failing closed on any mismatch — including after an attacker rewrites both body and frontmatter digest, substitutes the candidate id, or strips provenance fields (stripped provenance is still caught whenever the artifact's own promotion record is readable and matches its path; see the next bullet for indeterminate stores). Legacy promoted skills can load when their matching promotion record and verifiable legacy body hash remain available and the candidate-store scan is determinate for a claimed artifact. A promoted skill whose record is missing (for example a clean clone, CI worktree or teammate checkout without the local .swarm store) is refused as an orphaned promotion claim; restore the record or re-promote after resolving the store condition.
- An unreadable candidate store never poisons ordinary skills: a corrupt, oversized, or otherwise unreadable record — or a store whose record count exceeds the synchronous scan cap — only matters to an artifact that itself carries a promoted-provenance claim (a readable record that matches the artifact's own path is enforced, claim or no claim, whenever the candidate store is within the 1,000-record scan cap that bounds the synchronous work done on every delegation; above that cap no record is read and an unclaimed artifact is accepted, so keep the store below the cap — it is far above normal operation — and an artifact whose frontmatter is too long to inspect within the 64 KiB provenance bound is refused when no record matches it), which is refused with a reason naming the cause (for a corrupt, oversized, or unreadable record the reason also names the offending record file; for an over-cap store it reports the record count; for an unreadable store it reports the error code). A generated skill with no provenance claim is accepted even when the scan is indeterminate, so a promoted artifact whose provenance fields were stripped is caught only when a readable record matching its path is found (the scan keeps going past an unreadable record, and a readable match still wins; with no readable match the artifact is treated as an ordinary skill). Threat model: the binding defends the generated **artifact** against tampering; an actor who can already write `.swarm/skills/candidates` can delete or corrupt a record directly, which is outside what this binding guarantees.
- `external_skill_revoke` targets the structured `target_path` + recorded hash instead of regex-scraping a slug from prose, refuses targets outside the project's generated-skill root (including traversal and symlink/junction escapes), and refuses to delete when the on-disk bytes no longer match the recorded hash.
- Promotion refuses slugs that collide with bundled project skills (`reserved`), preventing a same-name external skill from shadowing a bundled one in a different root.
- `external_skill_promote` refuses, before writing anything, a candidate whose final artifact exceeds the 1 MiB verification bound or whose stored record — measured as the exact post-update serialization the store will persist, including the appended promotion history entry — would exceed the 1 MiB record read cap, or whose frontmatter (the promotion fields plus the candidate's `publisher` and `source_url`) would not fit the 16 KiB metadata window the propagation gate reads, or when the candidate store already holds more than 1,000 record files at promotion time (the verifier's scan cap, above which a claimed artifact is refused as indeterminate), so a successful promotion is loadable by the gate, verifiable and revocable. The store-size check is point-in-time: a record added concurrently in the instant between the check and the promotion can still push a store that sits exactly at the cap over it, in which case the gate refuses the skill until old candidate records are removed — keep the store well below the cap.
- `external_skill_promote` accepts an optional `expected_sha256` argument (backward-compatible): when provided, promotion refuses with a stale-base error if the candidate content changed since it was reviewed.

## Breaking changes

- The `knowledge.promotion_min_terminal_applications` default change (0 → 1) also stalls automatic and curator promotion of existing eligible backlog entries that have no independent terminal receipt. Opt out with `knowledge.promotion_min_terminal_applications: 0`, which weakens provenance enforcement back to the legacy ungated behavior. Independent terminal receipts of any outcome (applied, violated or contradicted) satisfy the evidence gate, as defined by the existing #1847 contract; applied-only filtering is not part of this change.
- Ordinary direct-text promotion (`/swarm promote "<text>"`) now needs the audited override `--force --reason "<why>"` when no qualifying independent receipt exists.
- The `hive-fast-track` tag no longer arms the fast-track route; only the dedicated `hive_fast_track_authorized` field (written by the manual promotion path) does.
- `validateRelPath`/`neutralizeResidueName` now reject/strip the full Unicode Cc class (C0 + DEL + C1), so existing quarantine manifests containing DEL/C1 names are skipped-and-retained on rollback rather than restored.
