# Rollback/close pipeline hardening: async checkpoint+align probes, fail-closed destruction enumeration, porcelain path containment

## What

Follow-ups from PR #3426, collated (issues #3427 + #3434):

- The checkpoint tool's entry preflight and `saveCheckpointRecord`'s probe
  now ride the shared async git reader (`readGitRepositoryStatusAsync`)
  instead of the local sync `gitExec` retry chain — on a host whose sync
  child spawns stall (#3275), `/swarm checkpoint` no longer blocks up to the
  transient-retry horizon (~150 s) before refusing. Behavior change to note:
  the entry preflight's refusal now names its cause — `not a git
  repository - …`, `git executable is not available - …`, or
  `git probe failed (<reader message>) - …` — instead of a single uniform
  text; `saveCheckpointRecord`'s probe keeps bounded transient tolerance
  (`readGitStatusAsync` retries a transient spawn failure once) so a
  single EBUSY/EPERM/ETIMEDOUT cannot silently record a SHA-less
  checkpoint. The finalize
  align stage's repository probe moved to the same reader through a new
  `readGitRepositoryStatusDetailedAsync` that preserves the exact
  `GitRepositoryStatus` reason vocabulary (`not_git_repo`,
  `git_unavailable`, `git_error`) the sync probe produced, including the
  #2236 three-way ENOENT cwd/binary split.
- The rollback destruction measurement now fails CLOSED when its
  `ls-tree`/`ls-files` enumeration cannot be read: `measureGitDestruction`
  reports `unreadable` with the structured cause instead of folding an
  empty in-the-way set into an `ok` measurement whose scope silently
  shrank below what `git reset --hard` would actually overwrite.
- Both porcelain parsers (NUL and newline forms) now exclude `../`-bearing
  (or absolute) records from the destroy scope and surface them as a
  bounded diagnostic on every consumer — the `/swarm rollback` preview and
  clean-tree restore, the checkpoint restore preview and clean-tree
  response, and the `/swarm close` early confirmation preview plus close
  summary warnings, and the confirmed destructive restore — instead of
  joining them into the confirm-token scope digest unvalidated. The
  interpolated record bytes are sanitized and bounded before rendering.
- The no-sync-spawn ratchet's `SCANNED_FILES` gains
  `src/commands/close/align-stage.ts` with a runtime membership self-pin —
  this asserts direct-spawn hygiene for that file; the probe conversion
  itself is guarded by dedicated suites (the checkpoint spawn-slot-counting
  suite for `src/tools/checkpoint.ts`, the awaited-call and true-repo legs
  for the align-stage seam), named as the different guards in the ratchet's
  own comment.

## Why

#3427 (priority:high): the two residual sync git probes sat on paths that
cross EVERY checkpoint invocation and the finalize pipeline — under the
#3275 loaded-host condition each probe could block ~150 s and then blame the
repository. #3434: an unreadable enumeration reading as "nothing in the
way" is the exact fail-open class #3317 closed for the status reads
("unreadable must never read as clean"), one call-site deeper — the
confirm token bound a scope smaller than the destruction; and porcelain
records joined the digest with no root-containment check anywhere on the
push path.

# /swarm close and rollback gate reads are async and say why they failed

## What

The git-status gate reads behind `/swarm finalize` (alias `/swarm close`),
`/swarm rollback`, the pre-destruction re-check, and the `/swarm diagnose`
"Git Repository" check now run through one shared async, bounded, killable
reader instead of private blocking `spawnSync`/`execFileSync` wrappers, and
every converted status read passes `--no-optional-locks` so a read-only check
never contends on the git index write lock.

When a gate read fails, the refusal text names the cause instead of the old
generic "Ensure git is available and the repository is readable" hint:

- a timed-out read reports `ETIMEDOUT` and advises restarting the OpenCode
  host (or inspecting the host runtime / security software) — the right
  remedy when git is present and the host could not complete the child spawn;
- a nonzero exit reports the exit status and the git stderr tail (for
  example a damaged `.git/index`), with a repair-the-repository remedy;
- a missing git binary reports `ENOENT` with the install hint (git.binary is
  honored from your USER-level config only);
- output larger than the read safety bound reports `EOUTPUT` and advises
  shrinking the change footprint, and a signal-terminated child reports
  `ESIGNAL` (POSIX signal deaths surfaced through `signalCode` or bun-compat's
  `-1` sentinel) — neither is ever reported as a successful `status 0` exit or
  a repository verdict;
- `/swarm diagnose` distinguishes all of these rows honestly — a hang or a
  signal kill shows as "git state unknown" with the actual cause, a spawn
  failure shows as "could not be spawned", a missing binary names `ENOENT`,
  and a nonzero `git rev-parse` answer says "Not a git repository".

The fail-closed contracts are unchanged: an unreadable status still refuses
the destructive pipeline with "Nothing was closed, archived, or destroyed",
the close gate and the pre-destruction re-check still share one argv and one
parser, and an unreadable rollback measurement still refuses the restore.

`/swarm finalize --dry-run`'s repository probe is a single bounded async
attempt — it no longer falls into the blocking 5-attempt synchronous retry
chain (up to ~150 s of frozen host event loop when git hangs), and the report
now says the probe is a read-only `git rev-parse`, not that "no git command
runs". The git executable resolver's async entry now probes candidates
through an async spawn (never the synchronous probe), and a probe cycle that
timed out is no longer negative-cached as the 60-second bare-`git` fallback.

The no-sync-spawn ratchet now also covers the four converted files
(`src/commands/close/orchestrator.ts`, `src/commands/destructive-purge.ts`,
`src/commands/rollback-gate.ts`, `src/services/diagnose-service.ts`), so the
blocking wrappers it replaced cannot return.

### Known residual (not fixed here)

> **Superseded in this same release by the #3427 follow-up (PR #3441):
> both probe sites below now ride the shared async reader — the checkpoint
> tool's entry preflight and `saveCheckpointRecord`'s probe use
> `readGitRepositoryStatusAsync`/`readGitStatusAsync`, and the align stage's
> mid-finalize probe uses the new `readGitRepositoryStatusDetailedAsync`.
> The residual described here no longer exists once that PR lands.**

Two synchronous git probes remain on adjacent paths and are tracked in
follow-up issue #3427: the checkpoint tool's `isGitRepo` preflight (every
git-checkpoint `/swarm rollback` crosses it first) and the align stage's
mid-finalize `getGitRepositoryStatus` call — both still use the blocking
retry chain and can wedge on a host where synchronous spawns stall. This
change makes the GATE READS async and diagnosable; it does not make those
two probes non-blocking.

A probe terminated EXTERNALLY on Windows (taskkill, Stop-Process, EDR
intervention) exits 1 or 255 with no signal code — indistinguishable from a
plain nonzero exit at the process level — so it renders under the nonzero
path (repair remedy; "Not a git repository" at diagnose) rather than
`ESIGNAL`. The refusal stays fail-closed either way; only the cause label is
coarse for that shape (measured 12/12 at the review round; the
signal-reporting paths above all classify correctly).

## Why

On a loaded Windows OpenCode host (issue #3275 field report), every
synchronous child spawn inside the host timed out while async spawns worked;
`/swarm close` aborted with no cause named and advice that blamed git
availability. The same detail-collapsing wrapper sat in front of the
rollback gate, the diagnose repository check, and the dry-run probe.

# Phase 1 & 2 safety fixes — transient retry, subprocess hardening, and atomic state writes

Phase 1 (HIGH-severity): bounded transient retry (ETIMEDOUT only, up to 5 retries with exponential backoff) to git/gh subprocess calls, plus post-mortem robustness hardening.

Phase 2 (MEDIUM-severity): idempotent finalize, archive stage safety filters, SQLite-safe db copy, per-file error reporting in session cleanup, rollback ledger-lock warning, and atomic temp+rename for all state/config writes.

## What changed

### Transient retry for git/gh subprocess calls

All git and GitHub CLI subprocess calls now implement bounded transient retry for `ETIMEDOUT` errors:

- **`src/git/branch.ts` (`gitExec`)** — ETIMEDOUT errors retry up to 5 times with 200ms base exponential backoff. ENOENT is **not** retried (indicates "git binary not at this candidate path" — the windowsGitCandidates loop handles that).
- **`src/git/pr.ts` (`ghExec`)** — Now follows canonical safety pattern: `result.error` checked first (not `result.status`), `maxBuffer: 5MB`, `windowsHide: true`, and ETIMEDOUT retry with backoff. Also added `spawnSyncWithTransientRetry` helper for `git status` and `git push` in `commitAndPush`.
- **`src/tools/checkpoint.ts` (local `gitExec`)** — Same transient retry pattern applied to the checkpoint tool's internal git calls.

### checkpoint tool warning improvements

> **Superseded in this same release by PR #3441 (issue #3427): the
> checkpoint-local `isGitRepo` helper and its `GitRepoProbe` type described
> below were removed — the checkpoint probes now use the shared async git
> reader, and the empty-SHA warning on `saveCheckpointRecord` is unchanged.**

- **`isGitRepo`** now returns `GitRepoProbe { isRepo: boolean; warning?: string }` instead of a bare boolean. Callers receive a warning message when the git probe fails for transient reasons.
- **`saveCheckpointRecord`** surfaces a warning when the recorded SHA is empty (directory is not a git repository or HEAD is unavailable) instead of silently recording an empty SHA.

### Post-mortem unknown-planId fix

**`src/hooks/curator-postmortem.ts`** — When `plan.json` is absent or unreadable, the post-mortem now uses a timestamped `effectivePlanId` (`"unknown-${Date.now()}"`) instead of the static string `"unknown"`. This prevents a stale `post-mortem-unknown.md` from a prior run from permanently blocking regeneration.

## Phase 2 changes

### `/swarm finalize` is now idempotent

**`src/commands/close.ts`** — Running finalize when no active state remains (already cleaned up or never created) is a clean no-op. A second finalize call during the same session no longer produces an error — it returns success with a `"nothing to finalize"` indicator.

### Archive stage ENOENT filter + EBUSY/EPERM/ENOSPC warnings

**`src/commands/close.ts`** — The archive stage now silently skips `ENOENT` errors (target already removed or never present). `EBUSY`, `EPERM`, and `ENOSPC` errors are surfaced as warnings rather than hard errors, allowing archive to complete for remaining files.

### SQLite-safe `swarm.db` copy with WAL checkpoint verification

**`src/commands/close.ts`** — When archiving `swarm.db`, the file is now copied using a SQLite-safe approach: before copying, a `PRAGMA wal_checkpoint(TRUNCATE)` command is issued via `sqlite3` to ensure the WAL checkpoint is flushed. The copy is verified by checking `sqlite3 CLI stdout` for the expected output format. This prevents corrupt or WAL-hot databases from being archived.

### Per-file session cleanup with reporting

**`src/commands/reset-session.ts`** — Session cleanup now wraps each file operation in an individual `try/catch` and reports success/failure per file. There is no silent short-circuit on the first error — every file attempted is reported.

### Rollback warns on locked ledger

**`src/commands/rollback.ts`** — If the ledger file is locked (e.g., another process holds it), rollback emits a warning suggesting `/swarm reset-session` as the recovery action instead of failing silently.

### Atomic temp+rename for all state writes

**`src/memory/jsonl-migration.ts` and `src/commands/simulate.ts`** — All state and configuration file writes now use atomic temp+rename: write to a temporary file first, then rename over the target. This prevents partial writes from corrupting state files on crash or concurrent access. `simulate.ts` applies this to plan and ledger outputs; `jsonl-migration.ts` applies it to `.swarm/` ledger and plan files.

## Why

- **ETIMEDOUT on subprocess calls** is a transient host contention error — antivirus interception, cold filesystem latency, or network latency can cause git/gh to time out even when the binary is present and working. Retrying resolves these transient failures without user intervention.
- **ENOENT is not transient** — it means the binary was not found at any candidate path. Retrying ENOENT would waste time on every subsequent attempt.
- **ghExec pattern alignment** — `result.error` must be checked before `result.status` because a spawn failure sets `error` but leaves `status` null. The previous order caused silent failures when gh was not on PATH.
- **checkpoint probe warnings** — Silent boolean returns obscured whether a failure was transient or permanent, making debugging difficult.
- **post-mortem blocking** — Without the timestamp suffix, a failed post-mortem run for an unknown plan would leave a stale report that caused all subsequent runs to skip (idempotent dedup check).

## Migration steps

None. The behavior changes are transparent. Git/gh operations that previously failed on transient timeouts will now succeed after retry.

## Known caveats

- The retry budget (5 attempts) is sized for transient host contention. Persistent failures (binary genuinely unavailable, network down) will still fail after all retries exhaust.
- The exponential backoff (200ms × 2^attempt) adds up to ~6 seconds of total retry delay in the worst case. This is bounded and only occurs on ETIMEDOUT.
- SQLite-safe copy requires `sqlite3` CLI to be available on PATH. If unavailable, the copy falls back to a plain file copy without WAL checkpoint.
- Atomic writes require filesystem rename support. On some network-mounted filesystems, rename may not be atomic; the temp+rename pattern still provides best-effort durability.
- Archive EBUSY/EPERM/ENOSPC warnings indicate files that could not be archived. These do not block finalize, but the warnings should be reviewed if archival completeness is required.

## Phase 3 — bare-catch sweep (FR-009)

All bare `catch` blocks in `src/commands/` are now either ENOENT-filtered or documented with a justification comment explaining why the catch is intentionally broad.

### What changed

- **`src/commands/close.ts`** — 6 bare catches converted to ENOENT-filtered pattern. ENOENT is silently skipped; all other errors are surfaced with context.
- **10 files across `src/commands/`** — bare catches documented with inline justification comments explaining the safety rationale for catching broadly (e.g., "must not throw — called from finally block", "idempotent cleanup — errors are advisory").

### Files affected

`src/commands/close.ts`, `src/commands/reset-session.ts`, `src/commands/reset.ts`, `src/commands/rollback.ts`, `src/commands/handoff.ts`, `src/commands/write-retro.ts`, `src/commands/acknowledge-spec-drift.ts`, `src/commands/full-auto.ts`, `src/commands/post-mortem.ts`, `src/commands/_shared/url-security.ts`

### Why

Bare catches that swallow all errors silently can mask real failures and make debugging difficult. FR-009 requires that every catch block either:
1. Filters expected non-errors (ENOENT for missing files) and re-throws the rest, or
2. Documents why catching all errors is the correct behavior

### Migration steps

None. This is a documentation and defensive-coding improvement with no behavior changes.

# Reset-session partial failures are loud and name the working recovery

## What

A partially-failed `/swarm reset-session` (SQLite row clear, projection
unlink, or state.json unlink failing) now tells the operator what happened
and how to recover, instead of stopping silently and pointing at a recovery
command that refuses exactly that state.

- The moment a reset leaves the closing coordination guard intentionally
  installed, exactly one always-visible operational advisory is emitted
  (`/swarm diagnose` channel, never chat-visible): durable session-snapshot
  persistence is stopped until a reset-session run succeeds — re-run
  `/swarm reset-session` (or restart the host) to recover.
- As belt-and-braces, `writeSnapshot` also emits one bounded advisory per
  project root per stop episode if a write fails while the guard is closed
  (the strand-time warning could have been missed in a long-lived process).
- `/swarm recover --coordination` now distinguishes the failure classes
  instead of printing one refusal for everything: a settled cleanup-stranded
  closing names the reset re-run recovery; an entry that is still settling
  keeps the "wait for the underlying attempt to settle" advice (which is
  correct there, and only there); ordinary initialization failures no longer
  carry that advice; shutdown-marked and in-flight-reset windows state their
  own truthful guidance.
- `/swarm status` renders origin-specific recovery lines for the same
  classes (previously one generic unsettled-timeout line for every state,
  including `closing (settled)`).
- The `/swarm reset-session` help entry documents partial failure: which
  steps can fail, that the closing guard intentionally stays installed
  (fail-closed containment), and the actual recovery path.

## Why

The closing guard left behind by a partially-failed reset is intentional
containment (#2481); the defect was the operator contract around it — the
persistence stop was silent (one debug-gated log line whose docstring said
"silently swallows errors"), the dedicated recovery command refused exactly
that state with advice that assumed an unsettled attempt, and status printed
the same generic recovery line for every non-succeeded coordination state
(frontier-audit finding `t1s1-r1-K2`, dual-review HIGH-borderline, Workstream
J slot J-14 / issue #2963).

## Migration

No breaking changes. The containment design is untouched: the closing guard,
its release gates, and the coordination state machine transitions behave
exactly as before — classification metadata, advisory emission, and
operator-facing text were added (the new metadata is mutated by the
settlement lifecycle, which is what flips an entry from the settle-wait
contract to the stranded contract once a prior attempt settles).
`ensureSnapshotCoordinationReady`'s rejection messages are unchanged;
`retrySnapshotCoordinationInitialization`'s closing refusals now name the
origin and recovery (the reset-session-origin refusals keep the
`closing for reset-session` marker; the shutdown and in-flight refusals carry
`closing for host shutdown` / `closing for an in-flight /swarm reset-session`).

## Caveats

- The writer-path advisory is bounded to one emission per project root per
  stop episode (re-armed only when readiness succeeds again), with a hard cap
  of 256 tracked roots; beyond the cap, new roots fall back to the debug log.
- The advisory rides the `/swarm diagnose` deferred-warning buffer, which
  caps at 50 entries and appends a truncation sentinel when full — "always
  visible" means surfaced by `/swarm diagnose`, never chat-visible.
- An in-flight reset's closing window with no pending prior attempt
  deliberately stays silent — that window is transient and owned by the
  running command. (When a prior initialization attempt is still settling,
  the writer's paused advisory does fire in that window.)
